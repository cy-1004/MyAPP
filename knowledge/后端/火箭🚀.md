# 一、基础篇

## 1、String、StringBuffer 和 StringBuilder 的区别

- 它们都可以用来表示字符串对象

- String是不可变的，线程安全，但是效率低，每次操作都会创建新的字符串对象，占用更多的内存，大部分场景下String够用。

- StringBuilder 是可变的，操作时不会产生新的对象，内部使用字符数组实现，性能高效，但线程不安全，适用于单线程下，大量字符串拼接的场景

- StringBuffer 也是可变的，是线程安全的，大体来说就是StringBuilder内部实现的基础上加锁使之同步。适用于多线程下，大量字符串拼接。

## 2、equals与==的区别

- ==可以比较任意类型的对象，基本类型就是比较的值，引用类型则是判断两个对象是否指向同一内存地址

- equals方法通常用于比较两个引用类型对象，其默认实现与‘==’相同，可自定义比较逻辑，不同的对象内部实现方式有所不同



## 3、final、finally 和 finalize区别

`final` 是一个关键字，用于声明常量、禁止重写方法、禁止继承类等。

- **常量**：用于声明常量，表示变量的值一旦赋值后不可改变

- **方法**：用于方法声明，表示该方法不能被子类重写

- **类**：用于类声明，表示这个类不能被继承



`finally` 是一个关键字，通常与异常处理（`try-catch`）一起使用。它用于定义一块代码，不论是否发生异常，这段代码都会执行。常用于资源清理操作，如关闭文件、释放数据库连接等。



`finalize` 是 `Object` 类中的一个方法，它在对象被垃圾回收之前由垃圾回收器调用。`finalize` 方法已经过时且不推荐使用，因为垃圾回收器并不保证会调用它，且其使用可能导致资源释放不及时

## 4、Arraylist和Linkedlist区别

ArrayList是动态数组的数据结构，LinkedList是双向链表的数据结构。

对于随机访问，ArrayList更快，因为LinkedList要遍历指针。

对于新增和删除操作，LinedList比较快，因为ArrayList要移动数据。



ArrayList和LinkedList都不是线程安全的

## 5、HashTable和HashMap的区别

**线程安全性**：`Hashtable`是线程安全的，而`HashMap`不是线程安全的

**null键和null值**：`Hashtable`不允许键或值为null，而`HashMap`允许一个null键和任意数量的null值。

**性能**：由于`Hashtable`提供了线程安全，因此在单线程环境下，`HashMap`通常比`Hashtable`具有更好的性能。

总的来说，如果你需要线程安全或不希望有null键或值，可以选择`Hashtable`。但在大多数情况下，`HashMap`是一个更好的选择，因为它提供了更好的性能和更多的功能。对于需要线程安全的情况，可以考虑使用`ConcurrentHashMap`，它专门为多线程环境设计，提供了更好的性能和扩展性。

## 6、HashMap原理

**JDK 1\.7 及以前**

HashMap 的基本数据结构是**数组加链表**。每个数组元素（桶）指向一个链表的头节点。当发生哈希碰撞时，新的键值对会被添加到链表的末尾。`HashMap` 的初始数组长度是 16（默认值）



**JDK 8 以后**

HashMap 的基本数据结构是：**数组\+链表/红黑树**。

- 当数组容量大于等于 64：当链表长度达到 8 并且数组容量至少为 64 时，HashMap 会将链表转换为红黑树，以提高查找效率。

- 当数组容量小于 64：在这种情况下，即使链表长度达到了 8，HashMap 也不会将链表转换为红黑树，而是选择进行数组扩容操作。



> 默认负载因子是 0\.75。负载因子决定了当 `HashMap` 中的元素数量达到桶数组容量的 75% 时，`HashMap` 会进行扩容（resize）。也就是说，`HashMap` 会在元素个数达到 `容量 * 0.75` 时触发扩容。
> 
> 例如，如果初始容量是 16，当元素数量达到 12（16 \* 0\.75）时，就会扩容为 32。当元素数量达到新容量的 75% 时，继续扩容。

## 7、红黑树

红黑树是一种自平衡的二叉查找树，它在插入和删除操作后通过重新着色和旋转来保持树的平衡，确保查找、插入和删除操作的时间复杂度最坏情况下为O\(log n\)。每个节点除了存储数据外，还包含一个颜色属性，可以是红色或黑色。

基本性质：

1. 根节点是黑色。

2. 每个节点是红色或者黑色。

3. 所有的叶子节点（NIL节点，通常不显示）是黑色。

4. 如果一个节点是红色，则它的两个子节点都是黑色。（即不能有两个连续的红色节点）

5. 从任一节点到其每个叶子的所有路径都包含相同数量的黑色节点。



## 8、ConcurrentHashMap实现原理

在数据结构上，ConcurrentHashMap 和 HashMap 是一样的实现方式（可以参考上一题）；但是它在并发操作上添加了线程安全的处理机制。比如：



**在 JDK 1\.7 及以前**，ConcurrentHashMap 的设计主要基于分段锁（Segment）机制。这种机制通过将整个哈希表划分为多个段（Segment），每个段都独立管理自己的锁（ReentrantLock），这表示不同的线程可以同时访问不同段的数据，从而提高了并发性能。（对于读操作，不需要加锁；对于写操作，只需要锁定相关的段而不是整个Map）



**在 JDK 8 以后**，ConcurrentHashMap采用了更细粒度的锁机制 CAS（Compare\-And\-Swap） 操作结合 synchronized 实现并发操作或扩容。使用 CAS 操作来进行无锁更新，比如插入、删除和更新操作。这样的话大部分操作都可以在不加锁的情况下完成，并发性能更好。当需要扩容的时候会使用 synchronized 锁来确保线程安全。

## 9、面向对象三大特性

- **封装**：将对象的状态（字段）和行为（方法）封装在一起，隐藏实现细节。

- **继承**：一个类可以继承另一个类的属性和方法。

- **多态**：允许不同的对象以相同的接口进行交互，即使它们的实现不同。

## 10、什么是CAS

CAS（Compare\-and\-Swap  不会说英文的话；就说 **比较与交换** ）是一种无锁算法，用于实现多线程环境下的原子操作。CAS的实现思路的话；大概是：

1. 记录 没有操作 之前的值A。

2. 在执行操作之后；如果当前值 和 刚刚记录起来的值A 相等，则说明值没有被修改，则将值修改为 新值 B。



> 追问：有没听过ABA问题？
> 
> 答：就是那个\.\.\. 一个变量的值从A变到B再变回A，CAS操作会误认为变量没有变化的这个问题吗？
> 
> 解决ABA的话；可以引入版本号来区分值的变化次数；这样每一次值的变化都会有版本的变化，即使修改为原来的值，版本号也已经变化了；变化了的话就更新失败。

## 11、什么是多态

多态指的是允许一个接口或基类引用指向不同类型的对象，并且在运行时根据实际对象类型来决定调用哪个方法实现的能力。

多态主要体现在以下几个方面：

1. **向上转型（Upcasting）**：

    - 将子类对象赋值给父类引用的过程称为向上转型。这是隐式的，不需要显式转换。

    - 例如：`Animal animal = new Dog();` 这里 `animal` 是父类引用，但它指向的是 `Dog` 子类的对象。

2. **接口与实现**：

    - 接口定义了一组行为（方法签名），但不提供具体实现。多个类可以实现同一个接口，并提供自己特有的方法实现。

    - 这样可以通过接口引用调用实现了这个接口的不同对象的方法，体现了多态性。

> 项目里面使用的话；可以是：Map\<String,String\> map = new HashMap\<\>\(\);

## 12、深拷贝和浅拷贝

**浅拷贝** ：**只是复制了对象中的基本数据类型的值，对于引用数据类型，复制的是引用地址而不是引用指向的对象本身**。因此，如果原对象的数据发生了变化，通过浅拷贝得到的新对象也会受到影响。

**深拷贝**： **不仅复制对象本身，还会递归地复制对象包含的所有对象，直到所有层次的数据都被复制**。也就是说，通过深拷贝得到的新对象**与原对象完全独立，任何一方的变化都不会影响到另一方**。

## 13、重载和重写的区别

**重载\(Overloading\)**是指同一个类中定义多个方法，它们的**方法名相同**，但**参数列表不同**。参数可以是数量不同、类型不同或者顺序不同。

**重写\(Overriding\)**是指子类在继承父类时，可以**重新实现**父类的方法。

## 14、接口和抽象类有什么区别

**定义方式**：抽象类使用** ****`abstract`**** **关键字定义，而接口使用 **`interface`** 关键字定义。

**实现方式**：

- 一个类可以通过使用 `extends` 关键字继承一个抽象类，并且如果这个类不是抽象的，则必须实现抽象类中的所有抽象方法。

- 一个类可以通过使用 `implements` 关键字实现一个或多个接口，并且必须实现接口中声明的所有方法。

**构造器**：

- **抽象类可以有构造器，而接口不能有构造器。**

**成员变量**：

- 抽象类可以有各种类型的成员变量（包括私有的、受保护的、公共的等），而接口只能包含常量（默认是 `public static final`）。

**方法实现**：

- 抽象类可以有抽象方法（没有方法体的方法）和具体方法（有方法体的方法）。从Java 8开始，接口也可以包含默认方法（使用 `default` 关键字）和静态方法（使用 `static` 关键字）。

一个类只能继承一个抽象类，但是可以实现多个接口。



## 15、Java集合/容器或数据结构

`Collection` 接口是所有集合类的顶级接口，它定义了一些通用的方法，如 `add`, `remove`, `contains`, `size`, `iterator` 等。它的子类集合关系如下：

```JavaScript
Collection
|
+-- List
|    |
|    +-- ArrayList
|    +-- LinkedList
|    +-- Vector  不推荐，所有方法都是同步的，如要线程安全的集合，更推荐 **CopyOnWriteArrayList**
|
+-- Set
|    |
|    +-- HashSet
|    +-- LinkedHashSet
|    +-- TreeSet
|
+-- Queue 可以不说
     |
     +-- PriorityQueue
     +-- LinkedList (实现了 Queue 和 Deque)
     +-- BlockingQueue (接口)

Map  --- 没有继承 Collection
|
+-- HashMap
+-- LinkedHashMap
+-- TreeMap
+-- Hashtable
```

根据不同的需求，可以选择不同类型的集合：

- **如果需要快速查找**：使用 `HashSet` 或 `HashMap`，它们基于哈希表，查询效率高。

- **如果需要有序**：使用 `LinkedHashSet` 或 `TreeSet`（对 `Set`）和 `TreeMap`（对 `Map`），它们会保持插入顺序或对键进行排序。

- **如果需要访问顺序或按索引访问**：使用 `ArrayList`（对 `List`），它允许通过索引访问元素。

- **如果需要队列操作（先进先出）**：使用 `Queue` 接口及其实现类，如 `LinkedList` 或 `PriorityQueue`。



Java 提供了一些线程安全的集合类，适用于多线程环境下使用：

- **CopyOnWriteArrayList**：线程安全的 `List` 实现，适合于读多写少的场景。

- **CopyOnWriteArraySet**：线程安全的 `Set` 实现。

- **ConcurrentHashMap**：线程安全的 `Map` 实现，支持高并发的读写操作。

## 17、\&和\&\&的区别

`&` 和 `&&` 都是逻辑运算符； `&` 在两个条件判断的时候，不管第一个条件是否为true，第二个条件都会进行执行判断； 而  `&&`  属于短路逻辑运算符，第一个条件如果为false的话；第二个条件就不会执行，最终的结果为false。

## 19、Exception与Error区别

**问题**：请对比Exception和Error，另外，运行时异常与一般异常有什么区别?

`Exception` 和 `Error` 都是 `Throwable` 类的子类。

- **`Exception`**：表示可以被程序捕获和处理的异常，通常是由编程错误或外部条件引起的。常见的有：

    - `IOException`: 表示输入输出操作中的异常。

    - `SQLException`: 表示数据库操作中的异常。

    - `NullPointerException`: 表示空指针引用异常。

    - `IllegalArgumentException`: 表示传递了非法参数的异常。

    - `RuntimeException`: 这是一个特殊的 `Exception` 子类，表示编程错误，如空指针异常、数组越界等。`RuntimeException` 及其子类不需要显式捕获或声明（非检查异常）。

- **`Error`**：表示严重的系统错误，通常不应由程序捕获和处理，因为这些错误往往是不可恢复的。

    - `OutOfMemoryError`: 表示内存不足。

    - `StackOverflowError`: 表示栈溢出。

    - `NoClassDefFoundError`: 表示找不到类定义。

    - 

异常分为两大类：运行时异常（Runtime Exceptions）和一般异常（Checked Exceptions）。

- **运行时异常（Runtime Exceptions）**： 

    - 非检查异常，编译器不要求必须捕获或声明。

    - 通常表示编程错误，应通过合理的设计和验证来避免。

- **一般异常（Checked Exceptions）**： 

    - 检查异常，编译器要求必须捕获或声明。

    - 通常表示外部条件导致的异常，需要在代码中处理或声明。

## 20、常见的五种运行时异常

运行时异常是 **非检查异常**（Unchecked Exceptions），编译器不要求必须捕获或声明这些异常。下面的不好读英文就说中文就可。

- `NullPointerException`: 空指针异常；尝试访问空对象的属性或方法。

## 27、线程池的7个核心参数

1. corePoolSize **核心线程数**。这是线程池中始终保持的最小线程数，即使这些线程处于空闲状态也不会被销毁。

    - 一般设置为CPU的核数；这样可以避免线程上下文切换带来的开销；比如系统有8核CPU，那么核心线程数可以设置为8

2. maximumPoolSize**最大线程数**。这是线程池中允许的最大线程数。当活动线程数达到 核心线程数 且任务队列已满时，线程池会创建新的线程，直到达到 最大线程数。

    - 如果任务是CPU密集型，最大线程数可以设置为核心线程数的1\-2倍（减少上下文切换）；

    - 如果任务是IO密集型，可以设置为核心线程数的2\-4倍（IO耗时比较久，避免过久的等待）。

3. keepAliveTime **线程空闲时间**。当线程池中的线程数大于 核心线程数 时，多余的空闲线程在等待新任务时的最长等待时间。

4. unit **空闲时间单位**； **线程空闲时间 的时间单位**。常见的值有 秒、分钟 等。

5. workQueue **任务队列**。用于存储等待执行的任务，队列大小可以设置为核心线程数的100\-1000倍。常见的实现有：

LinkedBlockingQueue：基于链表的阻塞队列，容量为 Integer\.MAX\_VALUE。

ArrayBlockingQueue：基于数组的有界阻塞队列。

SynchronousQueue：不存储元素的阻塞队列，每个插入操作必须等待一个移除操作，反之亦然。

PriorityBlockingQueue：具有优先级的无界阻塞队列。

6. threadFactory **线程工厂**。 用于创建新线程。默认情况下，线程池使用 Executors\.defaultThreadFactory\(\) 创建线程。

7. handler **拒绝策略**。当线程池和任务队列都已满时，新的任务将被拒绝。常见的拒绝策略有：

AbortPolicy：默认策略，直接抛出 RejectedExecutionException 异常。

DiscardPolicy：静默丢弃被拒绝的任务。

DiscardOldestPolicy：丢弃任务队列中最老的任务，然后重新尝试提交被拒绝的任务。

CallerRunsPolicy：由调用线程（提交任务的线程）执行被拒绝的任务。

## 28、线程池的流程或任务调度过程

1. 先调用 `execute(Runnable command)` 方法**提交任务**。

2. 如果当前线程数小于 核心线程数，小于的话则创建一个新的线程来执行任务。

3. 如果当前线程数等于或大于 核心线程数，则尝试将任务添加到任务队列 `workQueue` 中。

4. 如果任务队列已满；则判断当前线程数有没小于 最大线程数；

    小于最大线程数的话；则创建一个新的线程来执行任务。

5. 如果任务队列已满且当前线程数等于或大于 最大线程数，则调用拒绝策略处理任务。

## 30、线程安全

**线程安全（Thread Safety）**指的是在多线程环境下，多个线程同时访问某个资源或执行某个操作时，该资源或操作的行为仍然是正确的，并且不会出现数据竞争（race condition）或者数据不一致的情况。

简单来说，线程安全就是指当多个线程同时访问和修改同一个数据时，程序能够保证数据的一致性和正确性，而不会出现因并发导致的错误。

**为什么需要线程安全？**

在多线程编程中，多个线程可能同时读取和写入共享的数据，如果不加以控制，就可能导致数据的竞争和错误。例如，两个线程同时对一个变量进行修改，可能会导致最终结果不符合预期。



**怎么实现线程安全？**

1. **互斥锁**（Lock）：
使用同步机制，如 `synchronized` 关键字或 `ReentrantLock`，确保在同一时刻只有一个线程能够访问共享资源。通过互斥锁，可以避免多个线程同时修改数据，从而确保线程安全。

2. **原子操作**（Atomic Operations）：
对于一些简单的操作，可以通过原子操作来实现线程安全。例如，Java 提供了 `java.util.concurrent.atomic` 包中的原子类（如 `AtomicInteger`、`AtomicLong` 等），这些类的操作是原子的，能够保证在多线程环境下的正确性。

3. **并发集合**（Concurrent Collections）：
Java 提供了一些线程安全的集合类，例如 `ConcurrentHashMap`、`CopyOnWriteArrayList` 等，这些集合类通过内部机制保证了并发环境下对数据的安全操作。

4. **无锁编程**（Lock\-Free Programming）：
通过使用 CAS（Compare\-And\-Swap）等技术，可以实现无锁并发编程。这种方式可以避免使用传统锁（如 `synchronized`），减少性能开销，适用于高并发环境。Java 提供了 `java.util.concurrent.atomic` 包中的类来实现这种技术。

5. **线程局部变量**（ThreadLocal）：
如果每个线程都需要独立的数据副本，可以使用 `ThreadLocal` 来为每个线程提供独立的存储空间，从而避免多个线程之间的干扰。每个线程访问其自己的 `ThreadLocal` 变量时，不会受到其他线程的影响。

## 31、线程死锁及避免、防止

线程死锁是指两个或多个线程无限期地等待对方持有的资源，从而导致它们都无法继续执行的情况。这样的话；我可能会尝试这些方法：避免请求与保持条件、破坏循环等待条件、破坏不剥夺条件、使用死锁检测工具。

避免或者预防死锁的方式大概有：

1. **避免嵌套锁（按顺序加锁）**

这是最有效的预防死锁的方法之一。确保所有线程以相同的顺序获取多个锁。

2. **使用超时机制（tryLock）**

使用 ReentrantLock\.tryLock\(timeout\) 方法，尝试在指定时间内获取锁，如果超时则放弃，避免无限等待。

3. **避免持有锁时调用外部方法**

在持有锁的代码块中，不要调用可能被外部重写或调用其他同步方法的方法，因为这可能间接导致获取其他锁，增加死锁风险。

4. **使用工具类和并发容器**

Java提供了许多线程安全的工具类（如 ConcurrentHashMap、CopyOnWriteArrayList、BlockingQueue 等），避免手动加锁。

5. **减少锁的粒度和作用范围**

尽量缩小同步代码块的范围，只在真正需要同步的地方加锁，避免长时间持有锁。

6. **使用死锁检测工具**

利用JVM工具（如 jstack）分析线程堆栈，检测死锁。

在开发和测试阶段使用 ThreadMXBean\.findDeadlockedThreads\(\) 检测死锁。

7. **设计上避免“循环等待”**

确保系统中不存在“线程A等待线程B，线程B等待线程C，线程C又等待线程A”这样的循环依赖。

8. **使用无锁编程（Lock\-Free）**

在高并发场景下，考虑使用 AtomicInteger、AtomicReference 等原子类，通过CAS（Compare\-And\-Swap）实现无锁并发。

## 33、线程的状态有几种

Java 线程在其生命周期中可以处于以下几种状态：

- **NEW新建**：线程被创建但尚未启动。此时调用了构造方法创建了线程对象，但还没有调用 `start()` 方法。

- **RUNNABLE运行**：线程正在 JVM 中执行，但它可能正在等待获取 CPU 资源（例如，在多线程环境中等待调度）。这包括操作系统中的“运行”和“就绪”状态。

- **BLOCKED阻塞**：线程阻塞并等待监视器锁。当一个线程试图进入同步代码块或方法时，如果这个监视器锁已经被其他线程持有，则当前线程将进入此状态直到它获得锁。

- **WAITING等待**：线程无限期地等待另一个线程执行特定操作。例如，使用 `Object.wait()`、`Thread.join()` 或 `LockSupport.park()` 方法可以使线程进入这种状态。

- **TIMED\_WAITING限时等待**：类似于 `WAITING` 状态，但是有一个时间限制。这可以通过调用带超时参数的方法来实现，如 `Thread.sleep(long)`、`Object.wait(long)`、`Thread.join(long)` 或 `LockSupport.parkNanos(Object, long)`。

- **TERMINATED结束**：由于返回自调用的 run 方法的结果或者因为抛出了一个未捕获的异常，线程已经结束执行。

以下是线程状态转换的大致过程：

1. 当通过 `new Thread()` 创建一个新的线程实例时，它处于 `NEW` 状态。

2. 调用 `start()` 方法后，线程进入 `RUNNABLE` 状态，准备开始执行。

3. 在执行过程中，线程可能会根据条件变化进入 `BLOCKED`、`WAITING` 或 `TIMED_WAITING` 状态。

4. 当线程完成其任务或遇到错误而终止时，它进入 `TERMINATED` 状态。

## 34、虚拟线程

虚拟线程是 Java 19 引入的一项新特性，主要是在通过减少线程创建和上下文切换的开销，来实现高效的并发编程。

虚拟线程的关键点：

1. 轻量级： 传统的 Java 线程（平台线程）是由操作系统管理的，每个线程都需要操作系统分配资源，如堆栈、调度等，这对内存和CPU的开销比较大。虚拟线程则由 Java 虚拟机（JVM）管理，具有非常低的内存开销，可以创建成千上万个线程而不会占用大量系统资源。

2. 易于编程： 使用虚拟线程，开发者可以像使用普通线程一样进行并发编程，但不需要担心过多的资源管理和线程调度问题。

3. 非阻塞： 虚拟线程的调度和执行由 JVM 来管理，能够在 IO 操作或等待时自动切换，避免了传统线程在等待期间的资源浪费。

4. 适用于高并发场景： 虚拟线程特别适合用于处理大量的 IO 密集型任务或需要高并发的服务器应用。

在 Java 中使用虚拟线程，你可以通过 `Thread.ofVirtual().start()` 来创建虚拟线程。

```Java
//实现一个线程
Runnable task = () -> System.out.println("Hello from virtual thread!");
//使用虚拟线程，启动线程
Thread virtualThread = Thread.ofVirtual().start(task);

```

## 35、ThreadLocal

`ThreadLocal` 是线程局部存储机制，通常用于在多线程环境下为每个线程提供独立的变量副本。每个线程可以访问它自己独立的变量副本，而其他线程无法访问。它通常用于解决并发编程中的共享资源问题，使每个线程能够保持独立的状态，避免线程间的竞争和不必要的同步。



**你们使用在哪里？** 我们使用在项目中存储用户的信息的（项目中使用了UserContext 存储用户id）；主要用来在项目中减少方法的参数传递；在需要使用到用户信息的时候直接从ThreadLocal中获取当前用户的信息。



**它怎么做到的？或者说原来是什么？**

`ThreadLocal` 是通过每个线程维护一个独立的变量副本来工作的。每个线程都有一个与之关联的 `ThreadLocalMap`，这个 `ThreadLocalMap` 存储了线程局部变量的副本。

- 每个线程（由 `Thread` 类表示）都会有一个 `ThreadLocalMap`。

- 当线程首次访问某个 `ThreadLocal` 变量时，会在 `ThreadLocalMap` 中创建该变量的副本。

- 当线程访问 `ThreadLocal` 时，实际上访问的是它自己的副本，而不是全局共享的实例。

- 每个线程的 `ThreadLocalMap` 是独立的，因此线程之间不会发生相互干扰。



**可能导致什么问题**？

使用不当的话可能会发生**内存泄漏**问题，比如：线程池中的线程复用而 `ThreadLocal` 变量没有被清理，这样 `ThreadLocalMap`中的数据就会越来越多，占用内存就越来越大，最终一直不释放占有的内存导致内存泄漏。所以，在使用 `ThreadLocal` 时，通常需要显式调用 `remove()` 方法来清理不再使用的变量。



## 36、什么是AQS

AQS（AbstractQueuedSynchronizer）是 Java 并发编程





中的一个抽象类，它为实现阻塞式同步器提供了一个框架。AQS 位于 `java.util.concurrent.locks` 包中，如 `ReentrantLock`、`CountDownLatch`、`Semaphore` 等都是基于AQS。AQS 通过内部的 队列 来管理线程的等待和唤醒机制。

**工作原理**：

- AQS 通过维护一个整型的 同步状态 来表示当前的同步器状态（例如锁是否被占用）。当线程请求同步器时，AQS 会判断同步器的状态：

    - 如果当前状态允许线程获取同步资源，线程直接获取资源并进行处理。

    - 如果当前状态不允许线程获取资源，线程会被加入到等待队列中，并阻塞直到其他线程释放资源并唤醒它。

- 通过内部的 CAS（Compare\-And\-Swap）操作来保证在高并发情况下同步器状态的原子性。



应用示例：

1. `ReentrantLock`：通过 AQS 实现了一个可以重入的独占锁。

2. `CountDownLatch`：通过 AQS 实现一个计数器同步工具，允许多个线程等待，直到计数器的值减到零。

3. `Semaphore`：通过 AQS 实现了一个信号量同步工具，控制对某个资源的访问权限。

4. `ReadWriteLock`：通过 AQS 实现读写锁，允许多个线程并发读取，但写入时独占。



## 37、sleep和wait区别

**两者都会让出 CPU**：无论是 `Thread.sleep()` 还是 `Object.wait()`，它们都会导致线程暂时停止执行，让出 CPU 给其他线程。

- **区别在于锁的处理**：

    - `Thread.sleep()` 不会释放任何锁，线程保持持有所有已获取的锁。

    - `Object.wait()` 会释放当前对象的锁，并且只有当线程再次获得锁后才会继续执行。

- **唤醒机制**：

    - `Thread.sleep()` 是通过时间到期自动唤醒。

    - `Object.wait()` 则依赖于其他线程调用 `notify()` 或 `notifyAll()` 来唤醒，并且可能存在虚假唤醒的情况。

## 38、Synchronized和 Lock 的区别

1. **使用方式**

- **Synchronized**：使用关键字，编译器自动处理同步。

- **Lock**：使用接口和实现类，需要手动获取和释放锁。

2. **锁的释放**

- **Synchronized**：自动释放锁。

- **Lock**：需要显式调用 `unlock()` 方法释放锁。

3. **锁重入**：都属于可重入锁

## 39、什么是可重入锁

**可重入锁**：允许同一个线程多次获取同一把锁而不会发生死锁。

**Java中的实现**：`synchronized` 关键字和 `ReentrantLock` 类都支持可重入锁。

## 40、Synchronized 实现，锁的升级、降级

锁有四种状态，从低到高分别是：

1. **无锁状态**：没有任何线程持有锁。

2. **偏向锁**：偏向某个线程，减少锁的竞争。

3. **轻量级锁**：使用自旋锁，减少线程切换的开销。

4. **重量级锁**：传统的锁，使用操作系统互斥量，线程切换开销较大。



**锁升级**：无锁状态——》同一个线程再次申请锁时，锁会有偏向当前线程也就是升级到了偏向锁 ——》有其他线程尝试获取同一个对象的锁时，偏向锁会升级为轻量级锁 ——》如果自旋等待的线程数量较多，或者自旋时间过长，轻量级锁会升级为重量级锁



**锁降级**：如果当前没有其他线程在等待锁，锁可以降级为轻量级锁 ——》当轻量级锁被释放时，如果当前没有其他线程在等待锁，锁可以降级为偏向锁 ——》偏向锁被释放时，如果没有其他线程在等待锁，锁可以降级为无锁状态。



## 41、Synchronized锁类对象与锁实例对象的区别



**锁定实例对象**

当在一个实例方法或同步代码块中使用当前实例（`this`）作为锁时，实际上是对这个特定对象进行加锁。这时候如果多个线程试图访问同一个实例上的同步方法或代码块，它们会被串行化执行，即一个接一个地进入。



**锁定类对象**

当你在一个静态方法或同步代码块中使用`.class`作为锁时，实际上是锁定了整个类的所有实例。

锁定的是整个类级别的资源，所有对该类的实例访问同步方法或代码块时都会受到这个锁的影响。也就是说，即使不同的线程操作的是不同的实例，只要它们尝试进入相同的静态同步方法或代码块，它们也会被串行化执行。

## 43、AIO,BIO,NIO是什么

**JAVA BIO：同步并阻塞**，每个I/O操作都会阻塞当前线程，直到操作完成。

## 44、Java中类加载器的类型有哪几种

1. **启动类加载器**（Bootstrap ClassLoader）：

    - 启动类加载器是JVM的一部分，负责加载Java标准库中的核心类（如 `java.lang.*`、`java.util.*` 等）。这些类通常存放在 `JRE/lib` 目录下的 `rt.jar` 文件中。

2. **扩展类加载器**（Extension ClassLoader）：

    - 扩展类加载器负责加载JVM扩展目录中的类。它会加载 `JRE/lib/ext` 目录或由系统属性 `java.ext.dirs` 指定的目录中的类。

    - 扩展类加载器是 `ClassLoader` 类的一个子类，它加载的类通常是由JVM提供的扩展库。

3. **系统类加载器**（System ClassLoader，也叫**应用程序类加载器**）：

    - 系统类加载器负责加载应用程序的类，通常是 `CLASSPATH` 环境变量所指定路径中的类。

    - 它加载的是用户自己编写的应用程序类和第三方库类。

4. **自定义类加载器**（Custom ClassLoader）：

    - 自定义类加载器是指开发人员根据需要实现自己的类加载器，通常继承自 `ClassLoader` 类并重写 `findClass` 方法来加载类文件。自定义类加载器常用于动态加载类、隔离类加载、热部署等场景。

## 45、类加载过程，什么是双亲委派模型

1. **加载请求**：当一个类加载器收到类加载请求时，它首先不会自己去尝试加载这个类，而是把这个请求委托给父类加载器。

2. **逐层委托**：父类加载器再委托给它的父类加载器，直到最顶层的启动类加载器。

3. **加载类**：如果顶级的启动类加载器可以找到并加载这个类，就成功返回；如果找不到，就逐层向下委托。

4. **子类加载**：如果所有父类加载器都无法加载这个类，那么最开始的类加载器才会尝试自己去加载这个类。

> **追问**：能打破这种委派机制吗？
> 
> **答**：可以，如果自定义类加载器的话，可以直接由当前加载器加载而不委派

## 47、TCP和UDP的区别

**TCP（传输控制协议）**：提供可靠的数据传输服务。数据包发送后，接收方会发送确认（ACK）消息，发送方如果没有收到确认消息，会重新发送数据包。此外，TCP还负责数据包的排序和错误检测。

**UDP（用户数据报协议）**：不保证数据的可靠传输。数据包发送后，不等待确认，也不进行重传。如果数据包丢失或损坏，接收方不会得到通知。

## 48、三次握手四次挥手

TCP 协议的三次握手和四次挥手是连接建立和断开的过程：

**三次握手（建立连接）：**

1. **SYN**：客户端发送一个带 SYN 标志的数据包（请求建立连接）。

2. **SYN\-ACK**：服务器收到后，回复一个带 SYN 和 ACK 标志的数据包（确认连接请求）。

3. **ACK**：客户端收到服务器的 SYN\-ACK 数据包后，发送一个带 ACK 标志的数据包，确认连接建立。

**四次挥手（断开连接）：**

1. **FIN**：客户端发送一个带 FIN 标志的数据包，表示希望关闭连接。

2. **ACK**：服务器收到后，回复一个带 ACK 标志的数据包，确认客户端的关闭请求。

3. **FIN**：服务器准备好关闭连接时，发送一个带 FIN 标志的数据包。

4. **ACK**：客户端收到服务器的 FIN 数据包后，回复一个带 ACK 标志的数据包，确认关闭连接。

## 49、为什么TCP比UDP可靠

TCP 比 UDP 更可靠，主要是因为以下几个原因：

1. **连接导向**：

    - TCP 是面向连接的协议，确保通信双方在传输数据之前先建立连接（通过三次握手）。

    - UDP 是无连接的协议，不会进行连接建立过程，数据可以直接发送。

2. **数据包顺序**：

    - TCP 确保数据包按发送顺序到达接收端。如果数据包乱序，TCP 会重新排序。

    - UDP 不保证数据包顺序，数据包可能会乱序到达接收端。

3. **错误检测和修复**：

    - TCP 提供可靠的错误检测与重传机制。若数据包丢失或出现错误，TCP 会请求重传。

    - UDP 仅提供基本的错误检测（校验和），但不处理丢包和重传。

4. **流量控制和拥塞控制**：

    - TCP 具备流量控制和拥塞控制机制，确保网络不被过载，避免丢包。

    - UDP 没有流量控制和拥塞控制，可能导致数据丢失或网络拥塞。

5. **数据完整性保证**：

    - TCP 确保数据完整性，如果数据损坏，接收端会请求重传。

    - UDP 不提供数据完整性检查机制，仅提供简单的错误检测。



## 50、JVM内存模型或组成

包括：方法栈（虚拟机栈）、堆、方法区、本地方法栈、程序计数器

**1\. 堆（Heap）**

- 作用：堆是 JRE 中最大的一块内存区域，主要**用于存放对象实例以及数组**。所有通过 `new` 创建的对象都会在堆中分配内存。

- 特点：堆内存是线程共享的，所以它的并发访问必须考虑线程安全。垃圾收集器（GC）主要在堆内存中工作，负责回收不再使用的对象。

- 分代：堆通常被分为两个主要区域：年轻代（Young Generation） 和 老年代（Old Generation）。年轻代存放新创建的对象，而老年代存放长时间存活的对象。随着对象的存活时间变长，可能会从年轻代晋升到老年代。

**2\. 虚拟机栈（Stack）**

- 作用：栈是线程私有的，**用于存储方法的局部变量、操作栈和方法调用的状态**（包括返回地址、方法调用和方法返回的现场数据等）。每个线程在执行时会有自己的栈空间。

- 特点：栈是后进先出（LIFO）的结构，每调用一个方法时，都会在栈上压入一个栈帧，方法执行完毕后，栈帧会被销毁。栈中的数据包括局部变量（包括基本类型和对象引用）、操作数栈和方法的返回地址。

**3\. 方法区（Method Area）**

- 作用：方法区（在 JDK 8 之后被称为 "元空间"）**用于存储类的结构信息**（如运行时常量池、字段、方法数据、方法和构造器的代码等）。每个类的元数据都会存储在方法区中。

- 特点：方法区是所有线程共享的，在方法区中存储的是类信息、常量、静态变量等内容。随着 JVM 加载更多的类，方法区的内存会逐渐增加。方法区的大小通常由 `-XX:PermSize` 和 `-XX:MaxPermSize` 参数控制（JDK 8 之后，元空间替代了方法区，且不再受到这些参数的控制，取而代之的是 `-XX:MaxMetaspaceSize`）。

**4\. 程序计数器（PC寄存器）**

- 作用：程序计数器是每个线程私有的一块内存区域，它**保存着当前线程所执行的字节码的地址**。每当程序切换线程时，CPU 会通过程序计数器来确定当前执行的指令。

- 特点：程序计数器对线程切换至关重要，因为它保存了每个线程的执行位置，保证了多线程执行的正确性。如果线程执行的是 Java 方法，它保存的是当前执行字节码的地址；如果是本地方法，则会保存当前线程在本地方法中的执行位置。

**5\. 本地方法栈（Native Method Stack）**

- 作用：本地方法栈与 Java 栈类似，不同的是它**用于执行本地方法**（Native Method）。本地方法是通过 Java 与其他编程语言**（如** **C 或 C\+\+）编写的代码交互**。

- 特点：本地方法栈主要存储的是本地方法执行的相关信息，并且每个线程都会有一个本地方法栈。

## 51、JDK垃圾回收器与垃圾回收算法

**垃圾回收器**：

- **Serial GC**：适合小型应用，单线程，停顿较长。

- **Parallel GC**：适合多核环境，多个线程并行，回收效率高。**这是JDK 8默认的**

- **CMS GC**：适合需要低停顿时间的应用，通过并发标记和清除减少停顿时间。

- **G1 GC**：适合大内存系统，通过分区管理来控制停顿时间。**这是JDK 11默认的**

- **ZGC / Shenandoah GC**：适合大内存和低延迟要求的应用，减少垃圾回收带来的停顿。

**垃圾回收算法**：

- **标记\-清除**：简单，但存在碎片问题。

- **复制**：高效，但需要两倍的内存空间。

- **标记\-整理**：避免碎片，但对象移动代价高。

- **分代收集**：针对不同生命周期的对象进行不同处理，效率高，但可能需要更多内存。

- **增量回收**：减少停顿，但实现较复杂。

- **并发回收**：降低停顿时间，但开销较大。

## 52、动态代理实现

**JDK 动态代理**

只能代理实现了接口的类；使用反射机制，通过 `Proxy` 和 `InvocationHandler`；相对较慢，因为使用了反射技术。但是它无需引入第三方库。



**CGLIB 动态代理**

可以代理任何类，不需要接口；通过字节码技术，生成目标类的子类；性能相对较快，因为直接生成子类并调用父类方法；不能代理 `final` 类和 `final` 方法（因为无法继承）；需要引入 CGLIB 库。

## 53、IO流类型

1. **字节流（Byte Streams）**

    - 字节流用于处理8位字节的数据。它们是最基本的I/O流类型。

    - InputStream 和 OutputStream 是所有字节输入流和输出流的基类。

        - 常见的子类包括：

            - **ByteArrayInputStream **和 **ByteArrayOutputStream**：用于操作字节数组。

            - **FileInputStream** 和 **FileOutputStream**：用于读取和写入文件。

            - BufferedInputStream 和 BufferedOutputStream：提供缓冲功能以提高效率。

2. **字符流（Character Streams）**

    - 字符流用于处理16位Unicode字符，适用于文本数据的处理。

    - Reader 和 Writer 是所有字符输入流和输出流的基类。

        - 常见的子类包括：

            - FileReader 和 FileWriter：用于读取和写入文件中的字符数据。

            - **CharArrayReader** 和 **CharArrayWriter**：用于操作字符数组。

            - BufferedReader 和 BufferedWriter：提供缓冲功能以提高效率。

            - InputStreamReader 和 OutputStreamWriter：作为桥梁，将字节流转换为字符流。

3. **对象流**

    - 用于序列化和反序列化对象。

    - 如 **ObjectInputStream** 和 **ObjectOutputStream**。

## 54、 Java 对象的生命周期

1. **创建**：对象通过构造函数创建，初始化时放入堆内存。

2. **使用**：对象通过引用变量被使用，方法调用时对象传递。

3. **准备销毁**：对象没有被任何引用所引用时，成为垃圾回收的候选对象。

4. **垃圾回收**：JVM 在适当的时机清理不可达对象，释放内存。

5. **销毁**：对象在垃圾回收时被销毁。

## 7、创建索引注意事项或原则

**高选择性列**：为具有高选择性的列（如唯一标识符）创建索引，以加速查询，避免在低选择性列（如性别、状态）上创建索引。也就是说要在区分度高的列上创建索引会更合适；

**频繁查询条件**：对经常出现在 `WHERE` 子句中的列创建索引，特别是主键和外键，以提高查询效率。

**排序和分组字段**：如果列经常用于 `ORDER BY` 或 `GROUP BY`，考虑为其创建索引，减少排序和聚合计算的时间。

```SQL
表的主键、外键必须有索引
数据量大的表应该有索引；比如**常用的查询条件**可以创建索引
经常与其他表进行连接的表，在连接字段上应该建立索引
经常出现在Where子句中的字段，特别是大表的字段，应该建立索引
索引应该建在区分度高的字段上（sex 性别，status状态等这种就不适合，但适当可创建联合索引达到覆盖索引效果）
索引应该建在小字段上，对于大的文本字段甚至超长字段，不要建索引；比如text，varchar、json等类型的字段
频繁进行数据操作的表，不要建立太多的索引。比如经常insert /update/delete 表需要重新建立索引，这样比较耗时，所以不建议在这样的表上创建太多的索引
```



**覆盖索引**：创建包含查询所需列的索引，使 MySQL 不需要回表查找额外信息，从而提升查询速度。

**组合索引**：对于多列查询，创建组合索引而非单列索引，优化多条件查询性能；索引列顺序应根据查询频率安排。

**前缀索引**：对长文本列使用前缀索引，节省空间并加快查询速度，尤其适用于只需要匹配开头部分字符的情况。

## 8、覆盖索引

通过确保查询所需的所有列都在索引中，避免回表查询，提高查询性能。

也就是；当查询的所有列都可以从索引中直接获取时，数据库引擎就不需要再访问表中的数据行，减少了I/O操作，所以查询速度会很快。

在 `EXPLAIN` 的输出中，如果看到 `Extra` 列中有 `Using index`，则表示这个查询使用了覆盖索引。

## 10、MySQL索引有哪些类型

## 11、聚簇与非聚簇索引

- **聚簇索引**：每个表只能有一个，通常用于主键或经常用于排序和范围查询的列。

- **非聚簇索引**：每个表可以有多个，用于提高特定查询的性能。非主键索引属于非聚簇索引，对应的索引结构中叶子节点中保存了对应键值的主键，如果要查具体的数据行，需要根据主键再到 聚簇索引 中查询；这个过程也称为回表。

5. 什么是聚集索引和二级索引，什么是回表查询？

- 聚集索引：一张表一定有而且只会有一个聚集索引

如果有主键字段，就基于主键字段构建聚集索引

如果没有主键字段，会找第一个唯一索引构建成聚集索引

如果没有主键字段，也没有唯一索引，会使用隐藏的rowid构建聚集索引

- 聚集索引的特点：叶子节点存储的是索引值和行数据

- 二级索引：一张表可以有任意个二级索引

- 二级索引的特点：叶子节点存储的是索引值和主键值

- 什么是回表查询：

先根据二级索引查询得到主键值

然后再根据聚集索引查找主键值对应的行数据

## 13、创建索引的原则

- 创建的列里面的值要区分度比较高的；比如`id`、`email` 这些列的每个值几乎都不一样，区分度很高，就非常适合创建索引。

- 考虑那些频繁用于查询的条件列，如 WHERE 子句中的列、JOIN 子句中的列和 ORDER BY 或 GROUP BY 中使用的列

- 频繁进行 INSERT、UPDATE 和 DELETE 操作的表不应创建过多索引，因为这些索引会增加写操作的负担。

- 如果某个列的值重复度很高，比如 `gender` 列（通常值为 `male` 或 `female`），则即使它出现在查询条件中，也不建议为它创建索引。因为索引对于重复值的效率较低，反而可能会降低性能。

- 同一张表中避免创建过多的索引；建议2\-3个就差不多了；过多的索引会影响数据修改（如 `INSERT`、`UPDATE`、`DELETE`）的性能，因为每次数据修改时，MySQL 都需要更新索引。

- 避免对字段内部内容很大的字段创建索引；比如字段的类型是TEXT 和 BLOB 类型字段就不建议创建索引



## 14、MySQL索引数据结构 B\+树

B\+树；为什么使用B\+树呢？因为

- B\+树 中的数据是有序的，适合用于范围查询和排序操作。

- 每个分支的高度相同，保证了查询的高效性。

- 通过多级索引结构，可以在较短的时间内找到目标数据。

- 节点可以存储多个键值，提高了空间利用率。

- **叶子节点**：存储实际的数据行指针（对于非聚簇索引）或数据行（对于聚簇索引）。

- **非叶子节点**：存储索引键值和指向子节点的指针。

【知多滴】

B\+树 索引的层数并不是固定的，而是取决于表的大小和索引的设计。

B\+树索引的层数会随着表中数据量的增加而增加，通常情况下，层数并不会很高。

对于大多数实际应用场景，B\+树索引的层数通常在3到4层之间

## 15、B\+树与B树的区别，为什么快

1. **数据存储位置**：

    - **B树**：数据既可以存储在内部节点（非叶子节点）中，也可以存储在叶子节点中。

    - **B\+树**：所有数据都存储在叶子节点中，内部节点只存储键值，作为索引使用。

2. **叶子节点的结构**：

    - **B树**：叶子节点之间没有直接的连接。

    - **B\+树**：叶子节点之间通过指针相互连接，形成一个链表结构，便于范围查询。

3. **查询效率**：

    - **B树**：由于数据可以存在内部节点和叶子节点，查询时需要在多个层级中查找数据，可能相对较慢。

    - **B\+树**：数据只存在于叶子节点，查询时只需要查找叶子节点，且叶子节点按顺序链表排列，支持高效的范围查询。

4. **插入与删除操作**：

    - **B树**：插入和删除操作时，可能涉及到内部节点和叶子节点的调整。

    - **B\+树**：插入和删除操作通常仅涉及叶子节点，结构更为简洁。

5. **范围查询**：

    - **B树**：范围查询不如B\+树方便，因为没有叶子节点的链表结构。

    - **B\+树**：由于叶子节点之间有链表连接，B\+树的范围查询更加高效。

## 16、MySQL的锁有哪些

1. **表锁**：

- 表级锁是MySQL中最基本的锁策略，也是最粗粒度的锁。当一个事务获得某个表的锁后，其他试图访问这个表的事务将被阻塞，直到第一个事务释放锁。表级锁分为读锁（共享锁）和写锁（排他锁）两种。

- **读锁**：多个事务可以同时获取同一张表的读锁，但如果有事务正在对表进行写操作，则其他事务不能获取这个表的读锁或写锁。

- **写锁**：如果一个事务获得了某张表的写锁，那么在这个事务释放写锁之前，其他事务既不能对这个表进行读操作也不能进行写操作。

2. **行锁**：

- 行级锁是比表级锁更细粒度的锁，它只锁定满足条件的行，而不是整个表。行级锁可以大大减少锁定资源的数量，提高并发性能。

- InnoDB存储引擎支持行级锁，通过索引对数据行加锁。如果SQL语句没有利用索引，可能会导致锁住全表的数据行。

3. **意向锁**：

- 意向锁是一种表明事务准备在表的哪一行上设置锁的锁。InnoDB使用意向锁来实现多粒度锁定，允许事务在请求更低级别的锁之前先获取一个高级别的锁。

4. **自动增长锁**：

- 这种锁是在插入包含自动增长列的记录时使用的。为了保证自增ID的唯一性，MySQL会对表的自增值进行锁定。



> 一般情况下 Innodb 有索引的时候就是行锁，没有索引的时候就是表索。
> 
> 在MySQL中；默认使用InnoDB；则锁的情况如下：
> 
> select \.\.\. for update，insert，update，delete操作都会触发锁，只要涉及到表的改动，都会触发锁；
> 
> select \.\.\. for update 等待行锁释放之后，返回查询结果

## 17、MySQL死锁

在 MySQL 中，死锁（Deadlock）发生的原因是多个事务在相互等待对方释放资源，导致这些事务无法继续执行。

**死锁的常见原因**

1. **多个事务的锁顺序不一致**：

    - 两个或多个事务试图以不同的顺序访问相同的资源（如表、行），从而相互等待，形成死锁。

2. **锁类型冲突**：

    - 例如，两个事务都尝试对同一行或表加 `FOR UPDATE` 锁，导致一个事务无法获取所需的锁。

3. **长时间持有锁**：

    - 如果一个事务在持有锁时进行长时间的计算或操作，可能会导致其他事务无法获取锁，最终发生死锁。

## 18、内、外、左、右连接

**内连接（INNER JOIN）**

内连接返回两个表中满足连接条件的所有行。只有当连接条件为真时，结果集中才会包含来自两个表的行。也就是说，内连接只会返回那些在两个表中都有匹配的数据行。



**外连接（OUTER JOIN）**

外连接返回所有左表和右表中的记录，无论它们是否在另一表中有匹配的记录。如果一条记录在另一表中没有匹配项，那么结果集中对应的位置将填充NULL值。这样，结果集将包含所有可能的组合，而不仅仅是满足连接条件的记录。（虽然MySQL不直接支持全外连接，但可以通过UNION操作实现）。



**左连接（LEFT JOIN 或 LEFT OUTER JOIN）**

左连接会返回所有左表（FROM子句中指定的表）中的记录，即使在右表中没有匹配的记录。如果左表中的某一行在右表中没有匹配，则结果集中对应的右表字段将包含NULL值。



**右连接（RIGHT JOIN 或 RIGHT OUTER JOIN）**

右连接与左连接相反，它会返回所有右表中的记录，即使在左表中没有匹配的记录。如果右表中的某一行在左表中没有匹配，则结果集中对应的左表字段将包含NULL值。



## 19、MySQL的隔离级别

1. **Read Uncommitted（读未提交）**

所有事务都可以看到其他未提交事务的执行结果。读取未提交的数据，也被称之为脏读（Dirty Read）。会出现脏读。



2. **Read Committed（读已提交）**

一个事务只能看见已经提交事务所做的改变。不会出现脏读，但会出现不可重复读和幻读。



3. **Repeatable Read（可重复读）** —— MySQL默认

这是MySQL的默认事务隔离级别，它确保同一事务的多个实例在并发读取数据时，会看到同样的数据行。不过理论上，这会导致另一个棘手的问题：幻读 （Phantom  Read）。简单的说，幻读指当用户读取某一范围的数据行时，另一个事务又在这个范围内插入了新行，当用户再读取这个范围的数据行时，会发现有新的“幻影”  行。不会出现脏读和不可重复读，但会出现幻读。



4. **Serializable（可串行化）**

这是最高的隔离级别，它通过强制事务排序，使之不可能相互冲突，从而解决幻读问题。简言之，它是在每个读的数据行上加上共享锁。在这个级别，可能导致大量的超时现象和锁竞争。不会出现脏读、不可重读、幻读等问题，但是性能比较差。

## 20、事务特性ACID

1. **原子性 \(Atomicity\)**：事务中的所有操作要么全部成功执行，要么全部不执行。如果事务过程中发生错误，整个事务将被回滚到初始状态。

2. **一致性 \(Consistency\)**：事务应始终保持数据库处于一致的状态，即事务执行前后，数据库中的所有约束和规则都必须得到满足。

3. **隔离性 \(Isolation\)**：多个事务并发执行时，每个事务的操作应该是相互隔离的，不能互相干扰。一个事务的中间状态对其他事务是不可见的，直到该事务成功提交。

4. **持久性 \(Durability\)**：一旦事务成功提交，其结果将是永久性的，即使系统发生故障也不会丢失已提交的数据。



## 21、MySQL怎么保证ACID

MySQL 数据库的 ACID 特性有：原子性、一致性、隔离性和持久性；怎么保证这些特性，大概如下：

- **原子性**：确保事务中的所有操作要么全部完成，要么一个也不执行。如果在事务过程中发生错误或系统崩溃，事务应该回滚到初始状态。**这个特性的实现是利用 Redo Log 和 Undo Log 实现事务的提交和回滚**。



- **一致性**：是指事务执行前后数据库从一个一致状态转移到另一个一致状态。 **它的实现是通过约束、触发器、合适的事务隔离级别以及两阶段提交来维护数据的一致性**。



- **隔离性**：确保并发执行的事务不会相互干扰，即每个事务都感觉不到其他事务的存在。**它采用锁定机制和 MVCC ，提供不同程度的隔离级别**。InnoDB 引擎使用 MVCC 来提高并发性能。它通过保存数据的历史版本来实现非阻塞读取，使得不同事务可以读取同一数据的不同版本而不会互相干扰。



- **持久性**：是保证一旦事务提交成功，其对数据库的修改将永久保存，即使数据库重启、发生故障也不会丢失。**它是通过 Redo Log、双写缓冲区以及 Binlog 来确保已提交事务的持久化**。

## 22、MVCC、快照读、当前读

**MVCC（多版本并发控制）**它主要是通过维护数据的多个版本，允许读操作和写操作并行进行，通过保存数据的历史版本来实现非阻塞读取，使得不同事务可以读取同一数据的不同版本而不会互相干扰。



1. **每个事务在开始时会被分配一个唯一的版本号，这个版本号用于标识事务的时间顺序。**

2. **MySQL 在每行数据中添加了两个隐藏列**：一个是 **最新事务ID字段**（DB\_TRX\_ID）；一个是 **回滚时候的记录链地址** 字段（DB\_ROLL\_PTR）；这个字段是用来存储旧版本的数据。也正因为两个字段，才提供了MVCC多版本并发控制的进行，它可以根据需要，到记录链中回滚不同版本的数据。

3. **MVCC 支持多种事务隔离级别**，比如：

在 读已提交 READ COMMITTED 隔离级别下，每次查询都会看到已经提交的最新数据。

在 可重复 REPEATABLE READ 隔离级别下，事务在整个生命周期内看到的数据是一致的，不会因为其他事务的提交而发生变化。



（如果被追问到快照读、当前读的话；可以参考如下：）

**快照读**：读取操作不会阻塞写操作，会读取事务开始时的数据版本，提供一致性视图。快照读 不会看到未提交的事务数据。



**当前读**：某些查询（如 SELECT \.\.\. FOR UPDATE 或 UPDATE）需要获取最新的数据，会执行当前读，可能会加锁以保证数据的一致性。



## 23、MySQL分页与分包

1. **分页（Pagination）**：在MySQL中，通常通过`LIMIT 起始索引号，本次查询总条数（页大小）`子句实现分页。例如，要获取第2页的数据，每页10条记录，可以使用`LIMIT 10 10`。

2. **分包（Sharding）**：这是数据库拆分技术的一种，用来水平分割数据库或表。可以通过分包将数据分布到多个数据库实例或服务器上。可以使用 mycat、 sharding\-jdbc 进行分库分表。



## 24、Mybatis的缓存级别

## 28、Mybatis的一级缓存与二级缓存

**一级缓存**是 SqlSession 级别的缓存，它的作用范围局限于当前 `SqlSession（读这个单词的时候分开读，SQL Session）` 内部。只要 `SqlSession` 没有关闭，缓存就会持续有效。当你执行相同的查询时，MyBatis 会先检查一级缓存，如果缓存中有结果，则直接返回缓存的结果；如果缓存中没有，则会访问数据库并将查询结果放入缓存。

公用表表达式（Common Table Expression，简称 CTE）是一种在 SQL 查询中临时创建的结果集，可以在查询的 `SELECT`、`INSERT`、`UPDATE` 或 `DELETE` 语句中多次引用。CTE 通常在 `WITH` 关键字后面定义，并且可以包含一个或多个子查询。基本的语法结构如下：

```SQL
WITH cte_name AS (
    -- 这里是 CTE 定义的查询
    SELECT column1, column2
    FROM table_name
    WHERE condition
)
SELECT column1, column2
FROM cte_name
WHERE another_condition;
-- cte_name 是 CTE 的名字。
-- 在 WITH 子句内定义的查询（子查询）会被临时创建为一个虚拟表，可以在查询的后续部分使用。
```

## 34、数据库三范式

数据库的三范式（3NF）是关系型数据库设计的基本原则，用于确保数据的结构和关系合理，避免数据冗余和更新异常。具体三范式如下：

**1\. 第一范式（1NF） \- 原子性**

第一范式要求数据库表中的每个字段值都必须是原子值，也就是说每列的数据必须是不可再分的基本数据项。例如，如果一个字段存储多个值（如“电话”字段存储多个电话号码），这违反了第一范式。

要求：

- 每个列都必须包含不可再分的数据单元。

- 列中的每个值必须是单一的（即原子性）。

- 每一列的值必须是同类型的数据。



**2\. 第二范式（2NF） \- 消除部分依赖**

第二范式建立在第一范式的基础上，要求**数据库表中的每一列都完全依赖于主键，而不是仅依赖于主键的部分列**。比如：主键是由多个列组成的联合主键，那么表中的非主键列必须依赖于整个主键，而不能只依赖其中的一部分。

要求：

- 满足第一范式。

- 表中的非主键列必须完全依赖于主键，而不是依赖于主键的一部分。



**3\. 第三范式（3NF） \- 消除传递依赖**

第三范式要求消除非主键列之间的传递依赖关系。也就是说，**表中非主键字段不应该依赖于其他非主键字段**。

要求：

- 满足第二范式。

- 表中的每个非主键列直接依赖于主键，且不依赖于其他非主键列。



**总的来说：**

- 1NF 确保表的每个字段是原子性的。

- 2NF 消除部分依赖，确保非主键列依赖于整个主键。

- 3NF 消除传递依赖，确保非主键列直接依赖于主键。

## 1、cookie和session的区别

- **Cookie**：存储在客户端，可以设置过期时间，过期后会被浏览器自动删除。每次 HTTP 请求都会携带 Cookie 数据，增加了请求携带的数据量。

## 6、http请求与响应结构

超文本传输协议 \(HyperText Transfer Protocol，HTTP\)： 是一种无状态的，以请求 / 应答方式运行的应用层协议。

**HTTP 请求报文**由请求行（request line）、请求头部（header）、请求数据 3 个部分组成

- **请求行** 由请求方法字段、URL 字段和 HTTP 协议版本字段 3 个字段组成，它们用空格分隔。例如，GET /index\.html HTTP/1\.1。

- **请求头部** 由关键字 / 值对组成，每行一对，关键字和值用英文冒号 “:” 分隔。例如：User\-Agent：产生请求的浏览器类型。 Accept：客户端可识别的内容类型列表。 Host：请求的主机名

- **请求数据**（请求体）不在 GET 方法中使用，而是在 POST 方法中使用。



**HTTP 响应报文**由三个部分组成，分别是：状态行（包含响应状态码）、消息报头、响应正文



## 7、http响应状态码

状态代码由三位数字组成，第一个数字定义了响应的类别，且有五类可能取值。

•     1xx：指示信息–表示请求已接收，继续处理。    

•     2xx：成功–表示请求已被成功接收、理解、接受。    

•     3xx：重定向–要完成请求必须进行更进一步的操作。    

•     4xx：客户端错误–请求有语法错误或请求无法实现。    

•     5xx：服务器端错误–服务器未能实现合法的请求。    



常见状态代码、状态描述的说明如下：

•     **200** OK：客户端请求成功。    

•     400 Bad Request：客户端请求有语法错误，不能被服务器所理解。    

•     401 Unauthorized：请求未经授权，这个状态代码必须和 WWW\-Authenticate 报头域一起使用。    

•     403 Forbidden：服务器收到请求，但是拒绝提供服务。    

•     **404** Not Found：请求资源不存在，举个例子：输入了错误的 URL。    

•     **500** Internal Server Error：服务器发生不可预期的错误。    

•     503 Server Unavailable：服务器当前不能处理客户端的请求，一段时间后可能恢复正常，举个例子：HTTP/1\.1 200 OK（CRLF）

## 10、什么是XSS？后端怎么预防XSS

**XSS（Cross\-Site Scripting，跨站脚本攻击）** 是一种常见的Web安全漏洞。攻击者通过在网页中注入恶意的JavaScript脚本，当其他用户浏览该页面时，脚本会在其浏览器中执行，从而窃取用户信息（如Cookie、Session）、篡改页面内容，甚至进行钓鱼攻击。

XSS通常分为三类：

- 反射型XSS（Reflected XSS）：恶意脚本作为请求参数发送给服务器，服务器未做处理直接返回给前端并执行。

- 存储型XSS（Stored XSS）：恶意脚本被提交并存储在服务器数据库中（如评论、用户资料），之后被展示给其他用户时执行。

- DOM型XSS：不经过服务器，通过前端JavaScript操作DOM导致脚本执行。

**防御措施**：

**（1）输入过滤与验证**

- 对所有用户输入进行严格校验，使用白名单机制（如正则表达式）限制输入内容。

- 使用Java Bean Validation（如`@NotBlank`, `@Pattern`）进行字段校验。

**（2）输出编码**

- 在将数据输出到HTML页面前，进行HTML转义，将特殊字符（如 `<`, `>`, `&`, `"`, `'`）转换为HTML实体

**（3）设置HTTP响应头（辅助手段）**

- 添加 `Content-Security-Policy (CSP)` 头，限制页面可以加载的资源，防止执行内联脚本



## 11、对称加密与不对称加密

**对称加密**指的是加密和解密使用相同的密钥。在这种加密方法中，发送方和接收方共享同一个密钥。因为加密和解密都使用同一个密钥，所以如何安全地传递和管理密钥是一个大问题。如果密钥泄露，整个通信过程的安全性就会被破坏。**常见算法**：**AES**、DES、3DES、Blowfish 等。



**不对称加密**使用一对密钥：公钥和私钥。公钥用于加密，私钥用于解密。公钥可以公开，而私钥必须保密。

发送方可以公开其公钥，接收方使用私钥解密。**常见算法**：**RSA**、ECC（椭圆曲线加密）、DSA 等。



## 12、数字签名

数字签名是用于验证信息的完整性、身份认证和防止篡改的加密技术。它是通过使用非对称加密实现的，主要用来确保消息或文档在传输过程中没有被篡改，并验证信息的发送者身份。

数字签名的过程分为两个主要部分：签名生成和签名验证。

- 签名生成：

    1. 发送方使用私钥对消息进行加密，生成数字签名。私钥是保密的，只有发送方拥有。

    2. 消息本身通常通过哈希函数生成一个固定长度的哈希值，签名是这个哈希值的加密结果。这样可以确保数字签名不仅验证了发送方的身份，还保证了消息内容的完整性。

- 签名验证：

    1. 接收方使用发送方的公钥来解密数字签名，从中提取出消息的哈希值。

    2. 接收方对收到的消息进行哈希运算，得到该消息的哈希值。

    3. 如果接收方计算出的哈希值与数字签名解密得到的哈希值一致，说明消息未被篡改且确实是发送方发出的。

## 2、Spring怎么解决循环依赖/三级缓存

Spring使用了一种称为“延迟解析”的策略来解决循环依赖问题。也被称为使用三级缓存来解决循环依赖问题的：



当Spring容器初始化时，它会先实例化Bean（但不会调用其初始化方法），然后将Bean放入一个临时的Map中。

当一个Bean请求另一个Bean作为其依赖时，Spring会首先检查这个临时Map中是否有已经实例化但未完全初始化的Bean。

如果有，就会直接返回这个Bean的引用，从而解决了循环依赖问题。



追问：三级缓存的话：

Spring 使用三级缓存机制来解决循环依赖问题。这三级缓存分别是：

1. **一级缓存（Singleton Cache）**：存放完全初始化好的单例 Bean。

2. **二级缓存（Early Singleton Cache）**：存放尚未完全初始化的 Bean，这些 Bean 已经完成了构造函数的调用，但还没有调用初始化方法。

3. **三级缓存（Prototype Cache）**：存放原型 Bean 的缓存，与循环依赖无关，主要用于提高原型 Bean 的创建效率。

## 3、Spring的IOC

**IOC（控制反转）**主要是用于减少代码间的耦合度。通过 IOC，对象的创建和管理不再由程序代码直接控制，而是交给外部容器（如 Spring 容器）来管理。这样的话，对象之间的依赖关系可以通过配置文件或注解来声明，而不是硬编码在程序中。

## 4、Spring的AOP

AOP（Aspect\-Oriented Programming，面向切面编程）是一种编程范式，用于通过预定义的规则或切面对横切关注点（cross\-cutting concerns）进行模块化，统一添加不同的业务逻辑。常见的应用场景包括日志记录、事务管理、安全控制、性能监控等

AOP 使得这些横切关注点与核心业务逻辑解耦，从而提高代码的可维护性、可重用性和可扩展性。



**核心概念**：

- 切面（Aspect）：一个模块，定义了横切关注点的实现，比如日志记录、事务管理等。切面可以包含一个或多个增强（Advice）。

- 连接点（Join Point）：程序执行过程中的一个特定点，通常是方法的调用。Spring AOP 中的连接点是方法执行时。

- 通知（Advice）：在特定的连接点执行的代码，包含了具体的横切逻辑。通知有几种类型：

    - Before：在目标方法执行之前执行。

    - After：在目标方法执行之后执行（无论方法是正常执行还是抛出异常）。

    - After\-throwing：如果目标方法抛出异常时执行。

    - After\-returning：如果目标方法成功返回时执行。

    - Around：在目标方法执行前后执行，可以控制目标方法的执行，甚至可以完全拦截目标方法的执行。

- 切入点（Pointcut）：定义了在哪些连接点上执行通知。切入点通过表达式来定义，比如可以指定某些方法或类上的方法需要应用通知。

- 目标对象（Target Object）：被代理的对象，通常是被 AOP 拦截的业务类。



**AOP实现示例**：

```Java
// 定义一个切面类；添加 @Aspect注解
@Aspect
@Component
public class LoggingAspect {
    //前置通知；并设置切入点
    @Before("execution(* com.example.service.*.*(..))")
    public void logBefore(JoinPoint joinPoint) {
        System.out.println("Before method: " + joinPoint.getSignature().getName());
    }
    //后置通知；并设置切入点
    @After("execution(* com.example.service.*.*(..))")
    public void logAfter(JoinPoint joinPoint) {
        System.out.println("After method: " + joinPoint.getSignature().getName());
    }
    //环绕通知；并设置切入点
    @Around("execution(* com.example.service.*.*(..))")
    public Object logAround(ProceedingJoinPoint joinPoint) throws Throwable {
        System.out.println("Around method before: " + joinPoint.getSignature().getName());
        Object result = joinPoint.proceed();
        System.out.println("Around method after: " + joinPoint.getSignature().getName());
        return result;
    }
}
```

## 5、AOP失效的场景有哪些

Spring AOP 失效场景及其原因：

1\. **自我调用问题**

- **描述**：当一个类中的方法内部调用了同一个类的另一个被代理的方法时，AOP 代理不会拦截这个内部调用。

- **原因**：这是因为 Spring AOP 默认使用的是基于代理的机制（JDK 动态代理或 CGLIB）。在这种情况下，只有通过代理对象进行的方法调用才会被拦截。对于同一对象内的直接方法调用，不会经过代理，因此 AOP 切面不会生效。

- **解决方案**：可以通过重构代码来避免这种情况，例如将需要拦截的方法移到不同的类中；或者使用 AspectJ 编译时织入来处理自我调用的问题。

2\. **私有方法**

- **描述**：Spring AOP 不会拦截私有方法。

- **原因**：由于 Java 的访问控制规则，私有方法不能被外部类（包括代理类）访问，因此 AOP 框架无法为这些方法创建代理。

- **解决方案**：如果确实需要对私有方法应用 AOP，可以考虑将其改为受保护（`protected`）或包级私有（默认访问级别），然后再根据具体需求调整设计。

3\. **静态方法**

- **描述**：Spring AOP 也无法拦截静态方法。

- **原因**：静态方法属于类级别的成员，不属于任何实例对象。而 Spring AOP 主要是针对对象实例的方法调用进行增强的，所以它不能应用于静态方法。

- **解决方案**：避免在需要 AOP 增强的地方使用静态方法，或者寻找其他方式实现类似的功能。

4\. **非公共方法**

- **描述**：除了私有方法外，非公共但不是 `protected` 的方法（即默认访问级别）也可能不会被正确拦截。

- **原因**：这取决于具体的代理机制。JDK 动态代理只支持公共接口的方法，而 CGLIB 代理则可以处理更多类型的方法，但仍有一些限制。

- **解决方案**：尽量确保需要 AOP 增强的方法是公开的（`public`），以保证兼容性。

5\. **绕过代理**

- **描述**：如果直接通过 `new` 关键字创建了一个目标对象而不是通过 Spring 容器获取，则这个对象不会被 AOP 代理所包装，因此其上的 AOP 切面也不会生效。

- **原因**：Spring AOP 是基于 Spring 容器管理的对象（Bean）工作的。只有那些由容器创建和管理的对象才会受到 AOP 规则的影响。

- **解决方案**：始终从 Spring 应用上下文中获取 Bean 实例，而不是自行实例化它们。

6\. **错误配置**

- **描述**：如果 AOP 配置不正确，例如切入点表达式写错、缺少必要的依赖注入等，也会导致 AOP 不起作用。

- **原因**：配置错误会导致 Spring 无法正确识别哪些方法应该被增强，或者根本就没有启动 AOP 支持。

- **解决方案**：仔细检查 AOP 配置文件（XML 或注解），确保所有设置都是准确无误的，并且已经启用了 AOP 支持（例如通过 `<aop:aspectj-autoproxy/>` 或 `@EnableAspectJAutoProxy` 注解）。

## 6、事务的传播行为

Spring 定义了七种主要的事务传播行为：

1. **REQUIRED\-需要有事务**（默认）

    - **描述**：如果当前存在事务，则加入这个事务；如果当前没有事务，则创建一个新的事务。

    - **适用场景**：最常见的场景，适用于大多数情况。

2. **SUPPORTS\-支持事务，可有可无**

    - **描述**：如果当前存在事务，则加入这个事务；如果当前没有事务，则以非事务方式执行。

    - **适用场景**：适用于那些不需要事务支持的操作，但如果存在事务也不会影响结果的情况。

3. **MANDATORY\-必须要有事务，没有就抛出异常**

    - **描述**：如果当前存在事务，则加入这个事务；如果当前没有事务，则抛出异常。

    - **适用场景**：适用于那些必须在事务中执行的操作，如果不在事务中执行则会失败。

4. **REQUIRES\_NEW\-起一个新事务**

    - **描述**：创建一个新的事务，如果当前存在事务，则将当前事务挂起。

    - **适用场景**：适用于那些需要独立事务的操作，即使在已有事务中也需要创建新的事务。

5. **NOT\_SUPPORTED\-不需事务内运行，有则挂起**

    - **描述**：以非事务方式执行操作，如果当前存在事务，则将当前事务挂起。

    - **适用场景**：适用于那些不应该在事务中执行的操作，例如查询数据库状态的操作。

6. **NEVER\-非事务方式执行**

    - **描述**：以非事务方式执行操作，如果当前存在事务，则抛出异常。

    - **适用场景**：适用于那些绝对不能在事务中执行的操作。

7. **NESTED\-嵌套事务**

    - **描述**：如果当前存在事务，则在嵌套事务内执行；如果当前没有事务，则创建一个新的事务。

    - **适用场景**：适用于那些需要在一个更大的事务中执行部分操作，但这些操作可以独立回滚的情况。

## 7、Spring事务失效

1. **在类里面，使用没有事务控制的方法 调用有事务控制的方法**：

    - **总结**：内部方法调用不会触发事务管理，因为事务管理是基于代理的。

2. **在事务控制的方法内部，如果将异常捕获而且不抛出的话；不会进行正常的回滚，也属于事务失效**：

    - **总结**：捕获异常但不重新抛出会阻止事务管理器检测到异常并回滚事务。

3. **事务方法不是使用 public 修饰符的话，也会导致事务失效**：

    - **总结**：`@Transactional` 注解只能作用于 public 方法。

4. **如果调用事务方法的实力；是使用了 ****`new`**** 关键字手动创建的，也会导致事务失效**：

    - **总结**：手动创建 Bean 会绕过 Spring 容器，导致事务管理失效。

5. **使用了错误的事务传播行为**：

    - **总结**：某些事务传播行为（如 `NOT_SUPPORTED`、`NEVER`）会禁用事务管理。

## 10、Spring中常用注解

核心基础注解

1. **@Component**：通用的注解，用来标记一个类为Spring容器中的一个Bean。

2. **@Repository**：专门用于数据访问层（DAO层），标记这个类是一个持久化操作组件，通常处理数据库相关逻辑。

3. **@Service**：用于业务逻辑层，表示这个类是服务层组件，负责处理业务逻辑。

4. **@Controller**：用于表示控制层组件，通常是Web应用程序的控制器类，处理HTTP请求。

5. **@RestController**：组合了`@Controller`和`@ResponseBody`，用于构建RESTful Web服务。

6. **@Autowired**：自动装配依赖，可以标注在字段、构造函数或setter方法上，让Spring自动注入依赖。

7. **@Qualifier**：当有多个相同类型的Bean时，使用此注解指定具体的Bean名称。

8. **@Value**：注入外部配置文件的值或者简单的字符串、数字等基本类型的数据。

9. **@Scope**：定义Bean的作用域，默认是单例（singleton），也可以设置为原型（prototype）或其他作用域。

配置与启用特性

10. **@Configuration**：标记一个类为配置类，可以包含@Bean方法来定义Spring容器中的Bean。

11. **@Bean**：在`@Configuration`类的方法上使用，返回的对象将注册为Spring容器中的Bean。

12. **@ComponentScan**：指定哪些包需要进行组件扫描，以发现带有@Component等相关注解的类并注册为Spring Bean。

AOP（面向切面编程）

14. **@Aspect**：定义一个类为切面，可以包含通知（Advice）来横切业务逻辑。

15. **@Pointcut**：定义切入点表达式，确定在哪些连接点应用通知。

16. **@Before, @After, @AfterReturning, @AfterThrowing, @Around**：分别定义前置通知、后置通知、返回后通知、异常抛出通知和环绕通知。

测试

17. **@SpringBootTest**：用于启动整个Spring应用上下文来进行集成测试。

## 11、Spring Bean的作用域

Spring提供的几种主要的Bean作用域：

1. **Singleton（单例）**：

    - 这是Spring容器默认的作用域。当一个Bean被定义为Singleton时，Spring容器只会创建该Bean类的一个实例，并且这个实例会被所有对该Bean的请求共享。

    - 适用于无状态的Bean。

2. **Prototype（原型）**：

    - 当一个Bean被定义为Prototype作用域时，每次对该Bean的请求都会创建一个新的实例。

    - 适用于有状态的Bean。

3. **Request（请求）**：

    - 在Web应用环境中使用，针对每一个HTTP请求都会创建一个新的Bean实例。不同请求之间不会共享Bean实例。

4. **Session（会话）**：

    - 同样在Web应用环境中使用，针对每一个HTTP会话创建一个新的Bean实例。这意味着在一个会话期间内，Bean实例是共享的。

5. **Application（全局会话）**：

    - 主要用于portlet应用环境。对于整个portlet应用来说，每个portlet之间的Bean实例都是独立的，但同一个portlet内的多个请求间共享同一个Bean实例。

## 12、Spring的优缺点

**Spring 优点**

1. **依赖注入（DI）**：

- 提供了强大的依赖注入机制，使得对象之间的依赖关系更加清晰，提高了代码的可测试性和解耦性。

2. **面向切面编程（AOP）支持**：内置对AOP的支持，允许将横切关注点（如日志、事务管理等）与业务逻辑分离，从而提高代码的模块化程度。

3. **声明式事务管理**：支持通过简单的注解或XML配置实现声明式事务管理，减少了样板代码的编写。

4. **MVC架构支持**：提供了一个强大的Web MVC框架，便于构建Web应用程序，并且易于与前端技术集成。

5. **易于测试**：因为依赖注入和组件的松耦合，使得单元测试变得更容易，同时也提供了Mock对象的支持。

6. **广泛的社区支持和文档**：拥有一个庞大而活跃的社区，有大量的教程、文档和技术支持，方便学习和解决问题。

7. **丰富的生态系统**：包含了大量的子项目和扩展，如Spring Boot、Spring Cloud、Spring Data等，几乎涵盖了企业级应用开发的所有方面。

## 17、Spring中设计模式有哪些

Spring中使用的一些主要设计模式：

### 1\. **工厂模式**

**工厂模式 **是创建型设计模式的一种，它通过提供一个创建对象的接口，让子类决定实例化哪一个类。工厂模式主要解决的问题是：在不暴露对象创建逻辑的情况下，如何将对象的创建与使用分离。

*工厂模式的类型*：简单工厂模式、工厂方法模式、抽象工厂模式

- **应用场景**：Spring的核心——IoC容器本身就是一个工厂模式的应用。它负责创建和管理Bean的生命周期。

- **具体实现**：`BeanFactory`和`ApplicationContext`接口都是工厂模式的体现，它们提供了获取Bean实例的方法。

### 2\. **单例模式**

**单例模式 **是一种创建型设计模式，它确保一个类只有一个实例，并提供一个全局访问点来访问该实例。这个模式在系统中只允许创建一个实例，通常用于控制访问共享资源的情况，例如数据库连接、线程池、配置管理等。

- **应用场景**：默认情况下，Spring中的Bean是以单例模式创建的，这意味着在整个应用程序上下文中只有一个实例。

- **具体实现**：通过`@Scope("singleton")`注解或默认配置（因为单例是默认作用域），确保每个Bean在应用上下文中只存在一个实例。

### 3\. **代理模式**

**代理模式 **是一种结构型设计模式，它为其他对象提供一种代理以控制对这个对象的访问。

- **应用场景**：Spring AOP（面向切面编程）大量使用了代理模式，以实现非侵入式的横切关注点处理，如事务管理、日志记录等。

- **具体实现**：Spring提供两种代理方式：基于JDK动态代理（适用于实现了接口的类）和基于CGLIB代理（适用于没有实现接口的类）。

### 4\. **模板方法模式**

**模板方法模式**是一种行为型设计模式，定义了一个操作的算法骨架，将一些步骤的实现延迟到子类中。通过这种方式，模板方法模式使得子类可以在不改变算法结构的情况下，重新定义算法中的某些步骤。

- **应用场景**：Spring JdbcTemplate、RestTemplate等模板类就是模板方法模式的典型例子，它们封装了重复的操作逻辑，同时允许子类或使用者自定义特定步骤。

- **具体实现**：比如`JdbcTemplate`简化了数据库操作，隐藏了繁琐的JDBC细节，但允许用户通过回调函数定制SQL查询。

### 5\. **观察者模式**

**观察者模式**是一种行为型设计模式，它定义了一种一对多的依赖关系，当一个对象的状态发生变化时，所有依赖于它的对象（观察者）都会得到通知并自动更新，也就是说，它让一个对象的状态变化能够自动通知并更新多个相关对象。

- **应用场景**：Spring事件驱动模型实现了观察者模式，允许组件之间通过事件进行松耦合的通信。

- **具体实现**：可以通过发布/订阅机制，在应用上下文中广播事件，并让感兴趣的监听器响应这些事件。

### **策略模式**

**策略模式 **是行为型设计模式之一，主要是通过**定义一系列的算法，并将每个算法封装起来，使它们可以互换**。策略模式让算法的变化独立于使用算法的调用者

- **应用场景**：策略模式允许用户的行为可以在运行时改变，这在Spring中用于选择不同的实现方式来执行某个任务。

- **具体实现**：例如，`TransactionManager`接口的不同实现可以根据配置选择合适的事务管理策略。

### 门面模式

**门面模式** 是一种结构型设计模式，提供了一个统一的接口，用来访问子系统中的一群接口。这种模式遵循了“最少知识原则”，即只与最高抽象层次的对象交互，简化了接口的复杂度，使得外部系统可以通过一个简化的接口来操作复杂的子系统。

Spring框架本身广泛使用了门面模式，例如`JdbcTemplate`就是一个很好的例子。它简化了JDBC操作，隐藏了底层数据库操作的复杂性，如资源管理、异常处理等。使用者不需要直接与JDBC API交互，而是通过`JdbcTemplate`提供的简化方法来执行数据库查询和更新操作。

### **适配器模式**

**适配器模式** 是结构型设计模式的一种，主要用于解决接口不兼容的问题。它的目的是将一个类的接口转换成客户端希望的另一个接口，从而使得原本由于接口不兼容而无法一起工作的类能够协同工作。

- **应用场景**：当需要将一个接口转换成另一个接口时，适配器模式就派上了用场。Spring MVC中的HandlerAdapter就是这种模式的一个应用。

- **具体实现**：`HandlerAdapter`接口允许控制器方法以不同方式处理HTTP请求，而不需要修改原始控制器代码。

### **装饰器模式**

**装饰器模式**是一种结构型设计模式，它允许动态地给一个对象添加一些额外的职责，而不影响其他对象的功能。通过将功能增强的代码包装在装饰器类中，能够在运行时通过组合方式来扩展对象的行为，而不需要修改对象的代码。

- **应用场景**：用来给对象添加额外的功能而不改变其接口。Spring Security中的过滤链就是装饰器模式的一种应用。

- **具体实现**：Spring MVC中通过一系列的装饰过滤器（decorator）包装原始的请求处理过程，每个过滤器可以添加安全检查或其他预处理逻辑。

### **责任链模式**

**责任链模式 **是一种行为型设计模式，它使得多个处理对象能够按顺序处理请求。每个处理对象都包含对下一个处理对象的引用，当一个请求到来时，责任链中的每个处理者都有机会去处理该请求。如果当前处理者无法处理请求，它会将请求传递给链中的下一个处理者，直到请求被处理或链的末端。

- **具体实现**：Spring WebFlux中的路由和过滤机制体现了这一模式。

## 4、缓存问题三兄弟——缓存雪崩

缓存雪崩是指由于某种原因（如电力故障、机器宕机等），Redis中大量缓存数据在同一时间内失效或丢失，导致所有请求都访问数据库，给数据库带来巨大压力。

**解决方案**：

- **合理设置过期策略**：不要让所有的缓存key同时过期，而是根据实际情况设定不同的过期时间和策略。

## 5、缓存问题三兄弟——缓存穿透

缓存穿透指的是查询一个不存在的数据，如果每次请求都直接访问数据库，而数据库中也没有这个数据，则会导致大量的无效查询，从而增加了数据库的负担。

**解决方案**：

- **布隆过滤器（Bloom Filter）**：在请求到达缓存之前，先通过布隆过滤器检查数据是否存在。

- **缓存空结果**：对于查询到的空结果也进行缓存，但设置较短的有效期（TTL），以防止长期占用缓存空间。这样即使后续有相同的请求，也可以直接从缓存中获取“不存在”的信息，而不必每次都查询数据库。

## 6、缓存问题三兄弟——缓存击穿

缓存击穿是指某个热点key即将过期时，大量并发请求几乎同时到达，导致这些请求不得不直接打到数据库上，造成瞬间的数据库的高负载。

**解决方案**：

- **加锁机制**：当一个key即将过期或已过期时，第一个请求尝试更新缓存时加锁，其他请求等待锁释放后再读取新缓存。这种方式可以避免多个线程同时重建缓存的情况。

- **异步预热**：提前异步加载可能成为热点的数据到缓存中，确保缓存总是最新的，减少因key过期带来的冲击。

- **逻辑过期**：热点key不要设置过期时间，在活动结束后手动删除。

## 7、布隆过滤器的实现，怎么用

redis中布隆过滤器的实现主要使用到了它的 位图bitmaps 的数据结构；核心思想是使用多个哈希函数将元素映射到位图中的不同位置。每个哈希函数的结果指向位图中的一个特定位。当插入一个新元素时，所有对应的位都会被设置为1。查询一个元素是否存在时，只需要检查这些位是否都为1。如果任何一个位为0，则可以确定这个元素不在集合中；但如果所有位均为1，则只能说明这个元素可能存在于集合中，因为存在误判的可能性。



在使用了**redisson**操作布隆过滤器的话；大概如下：

```Java
// 创建一个新的布隆过滤器，预计最多插入100万个元素，允许的最大错误率为0.03%
RBloomFilter<String> bloomFilter = redisson.getBloomFilter("myBloomFilter");
//设置最大元素个数，错误率
bloomFilter.tryInit(1000000, 0.0003);

// 向布隆过滤器中添加元素
bloomFilter.add("some-key");

// 检查元素是否存在
boolean mightContain = bloomFilter.contains("some-key"); // 返回 true 或 false

System.out.println("Does the Bloom filter contain 'some-key'? " + mightContain);
```

## 8、Redis为什么快

1. 完全基于内存的操作：Redis将所有数据存储在内存中，避免了磁盘I/O带来的延迟。内存访问速度远超磁盘读写，这使得Redis能够在微秒级别完成大多数操作。

2. Redis采用单线程操作；避免了不必要的上下文切换和竞争条件，也不存在多进程或者多线程导致的切换而消耗CPU，不用去考虑各种锁的问题，不存在加锁释放锁操作，没有因为可能出现死锁而导致的性能消耗。

3. 采用异步I/O复用机制：Redis使用epoll（Linux）等高效的I/O多路复用技术来管理连接和事件，确保即使有大量的并发连接也能高效地处理每个请求。

## 9、Redis是单线程的吗

Redis 6\.0之前是单线程；不过

从 Redis 6\.0 版本开始，Redis 引入了多线程 I/O 来加速网络读写操作。所以从6\.0开始不严格属于单线程的；

但 Redis 核心数据结构和命令执行逻辑仍然是单线程处理的

## 12、Redis主从复制

- `slave`节点请求增量同步

- `master`节点判断`replid`，发现不一致，拒绝增量同步

- `master`将完整内存数据生成`RDB`，发送`RDB`到`slave`

- `slave`清空本地数据，加载`master`的`RDB`

- `master`将`RDB`期间的命令记录在`repl_baklog`，并持续将log中的命令发送给`slave`

- `slave`执行接收到的命令，保持与`master`之间的同步

## 13、Redis数据持久化策略

Redis 提供了两种主要的数据持久化策略：RDB（Redis Database Backup）和 AOF（Append Only File）。



**RDB** 是通过创建 Redis 数据库在某一时间点的快照来实现持久化。它会将内存中的数据集写入磁盘上的二进制文件（默认名为 `dump.rdb`）。默认触发快照写的策略有：

- 如果在过去900秒（15分钟）内至少有1个键发生变化，则触发一次快照。

- 如果在过去300秒（5分钟）内至少有10个键发生变化，则触发一次快照。

- 如果在过去60秒内至少有10000个键发生变化，则触发一次快照。



**AOF** 持久化通过记录服务器接收到的每个写命令到一个追加只读的日志文件（默认名为 `appendonly.aof`）中。重启时，Redis 会重新执行这些命令以恢复数据状态。

**AOF的写回策略**：

- **每秒fsync** \(`everysec`\)：默认情况下，每秒一次将缓冲区的内容同步到磁盘。这种模式提供了较好的性能和安全性之间的平衡。

- **每次写入fsync** \(`always`\)：每次写命令都会立即同步到磁盘，确保最高的数据安全性，但会对性能产生较大影响。

- **从不fsync** \(`no`\)：依赖操作系统来决定何时将缓冲区内容刷新到磁盘，虽然提高了性能，但增加了数据丢失的风险。

**重写机制**：

- **AOF 重写**：为了防止 AOF 文件变得过大，Redis 支持 AOF 重写功能，即在不影响现有数据的前提下，压缩冗余的命令序列。重写过程也是在子进程中完成的，不会阻塞主进程。

我们项目的话；会使用RDB和AOF混合持久化的模式；在这种模式下，AOF 文件不仅包含所有写命令，还会定期插入 RDB 快照作为基准点。这使得 AOF 文件更加紧凑，并且可以在启动时更快地加载数据。

## 14、过期key处理策略

- **惰性删除**：Redis会在每次访问KEY的时候判断当前KEY有没有设置过期时间，如果有，过期时间是否已经到期；过期的话则删除。

- **周期删除**：通过一个定时任务，周期性的**抽样**部分过期的key，然后执行删除。

## 15、内存淘汰策略

Redis支持8种不同的内存淘汰策略：

- `noeviction`： 不淘汰任何key，但是内存满时不允许写入新数据，默认就是这种策略。

- `volatile-ttl`： 对设置了TTL的key，比较key的剩余TTL值，TTL越小越先被淘汰

- `allkeys-random`：对全体key ，随机进行淘汰。也就是直接从db\-\>dict中随机挑选

- `volatile-random`：对设置了TTL的key ，随机进行淘汰。也就是从db\-\>expires中随机挑选。

- `allkeys-lru`： 对全体key，基于LRU算法进行淘汰

- `volatile-lru`： 对设置了TTL的key，基于LRU算法进行淘汰

- `allkeys-lfu`： 对全体key，基于LFU算法进行淘汰

- `volatile-lfu`： 对设置了TTL的key，基于LFU算法进行淘汰

比较容易混淆的有两个算法：

- **LRU**（**`L`**`east`**`R`**`ecently`**`U`**`sed`），最近最久未使用。用当前时间减去最后一次访问时间，这个值越大则淘汰优先级越高。

- **LFU**（**`L`**`east`**`F`**`requently`**`U`**`sed`），最少频率使用。会统计每个key的访问频率，值越小淘汰优先级越高。

在redis中可以使用 `setNX + 过期时间` 的方式来实现分布式锁。

> 
>

## 19、Redisson看门狗

Redisson 的**看门狗**（**Watchdog**）是一个用于自动延长分布式锁过期时间的机制，主要解决在分布式环境下，持有锁的客户端在执行任务时出现故障或崩溃的情况，防止其他客户端长时间等待锁释放。看门狗的机制通过自动刷新（默认30秒过期时间，**每隔10秒会自动续期到30秒**，从而保持分布式锁不过期）锁的过期时间，确保锁在任务执行过程中始终保持有效。



追问：如果自动续期会不会导致一直不释放锁而产生死锁？

- 业务正常处理的话，是会释放锁的

- 如果业务不正常，我们也有异常处理，在finally里面会释放

- 如果是业务宕机，那么分布式锁也有过期时间，默认是30秒；所以怎么样都不会死锁

## 25、红锁RedLock

**RedLock** 是 Redisson 提供的一种分布式锁算法，主要作用是解决在多个 Redis 实例上执行加锁，如果发生了单个 Redis 节点故障时仍能保证锁的可用性和一致性的解决方案。它的主要实现思想是在多个 Redis 实例之间进行协作来确保锁的一致性和高可用性。



RedLock 的实现流程如下：

1. **多个 Redis 实例**：至少需要 5 个独立的 Redis 实例部署在不同的机器或节点上，来确保高可用性。

2. **获取锁的过程**：

    - 客户端尝试在每个 Redis 实例上获取锁。客户端会依次向每个 Redis 节点发送请求，会尝试在每个节点上设置锁，并且记录每次请求的时间。

    - 只有当锁在 **多数** Redis 实例（至少 3 个 Redis 节点）上成功设置，且整个过程在一个合理的时间窗口内完成时，才认为锁被成功获取。

3. **获取锁的条件**：

    - 客户端必须在短时间内（通常是毫秒级别）向多个 Redis 节点请求并成功获得锁。

        这个过程需要保证：

        - 锁的设置时间不会过长（避免单点故障）。

        - 客户端必须至少成功获取到大多数 Redis 节点上的锁（通常是 3 个节点及以上）。

        - 锁的获取操作必须具备足够的时间容忍度。

4. **释放锁**：

    - 客户端获取锁后，在完成任务时，客户端会从它成功获取锁的 Redis 节点上释放锁。

    - 释放锁时，需要检查当前客户端是不是还持有锁，避免误释放锁。

## 2、消息重复消费/幂等

1. 设置消息唯一ID，对已处理消息进行记录

    发送消息时给消息指定一个唯一的ID

    消费消息完成将消息ID记录在数据库或Redis中

    消费时根据消息ID查询数据库或Redis判断是否已经消费，如果已经消费则不再消费。

2. 通过业务状态判断

    业务判断就是基于业务本身的逻辑或状态来判断是否是重复的请求或消息，通过业务状态判断如果已经处理则不再重复处理。

    比如：更新订单状态为由未支付更新为已支付，可以在执行更新时判断订单状态是否是未支付，如果不是则证明订单已经被处理过，无需重复处理。

## 3、消息怎么可靠的消费

保证MQ消息的可靠性可从几个方面去处理。

1. 保证**生产消息的可靠性**

    - 重连机制：在发送消息时可以开启重试机制，避免因为短暂的网络问题导致发送消息失败。

    - 生产者确认机制：RabbitMQ还提供生产者确认机制保证发送消息到MQ的可靠性。

        - Confirm回调：消息投递成功到交换机，则返回ack，否则返回nack。

        - Return回调：消息投递成功但路由失败会将消息退回来。

    - 最终处理：

    发送消息时给每个消息指定一个唯一ID，并设置Confirm和Return回调方法

    如果消息发送不成功，我们在回调方法中解析失败消息，并**记录到失败消息表，然后由定时任务尝试重发**

2. 设置**中间件持久化**存储

    - 设置交换机持久化：将交换机的定义信息\(元数据\)持久化到RabbitMQ的数据库中

    - 队列持久化：将队列的定义信息\(元数据\)持久化到RabbitMQ的数据库中

    - 消息持久化：发送消息设置delivery\_mode=2，消息进行持久化。

3. 保证**消费消息的可靠性**

    - 消费者确认机制：

        消费者获取消息后，应该向RabbitMQ发送ACK回执，表明自己已经处理完成消息，RabbitMQ收到ACK后删除消息，在处理失败后向MQ发送NACK那么消息会重新投递到消费者。

        RabbitMQ提供三个确认模式：manual（手动ack），auto（自动ack）、none（不需要ack）

    - 我们项目使用的是自动ack模式：

    当消费消息失败后， 会进行消费者本地重试

    重试3次如果还失败，会将消息投递到固定的交换机，通过交换机将消息转发到失败消息队列

    程序监听失败消息队列，将失败消息存入失败消息表，通过定时任务进行处理。

4. 最终补偿

消息队列无法百分百保证可靠性，一定要提供补偿机制。可以由消费者反向主动查询的方式达到最终的一致

比如：支付通知消息发送失败，我们可以在业务层提供支付结果查询接口，由消息消费方调用接口去查询支付结果。

## 4、消息怎么可靠生产

我们会在发送消息的时候，开启生产者重试机制；如果发送失败就重试，发送到成功为止，如果重试几次还是失败；那就抛出异常，要么就是将消息记录到一张表里面；启动定时任务定时发送，发送到成功为止 



**定时任务怎么做？**：

1. 把消息数据写入数据库，用状态码来控制消息发送状态。

2. 开启定时任务，间隔时间比如3秒，查询未发送的消息。

3. 调用消息生产者，发送消息到MQ中间件。

4. 消息生产者，设置confirmCallback确认回调对象，判断ack

\-\- true:  消息发送成功，修改消息发送状态为: 已发送。

\-\- false: 消息发送失败。

## 5、RabbitMQ自身可靠

所有的交换机、队列、消息都可以设置为持久化模式（重启后还在）

RabbitMQ可以做集群，实现镜像队列和仲裁队列（即使RabbitMQ其中一个节点挂了；也还有其它节点提供服务；不仅如此，因为做了镜像或仲裁队列，所以交换机、队列、消息也都是不会丢失的，每个节点都会有副本。）

### 镜像队列

核心思想：主从复制

1. 是什么？
镜像队列就是一个主从模式的集群。你创建一个队列时，它会在一个节点上作为主队列，然后将其内容和操作（如消息的发布、确认）完全复制到其他一个或多个节点上的从队列。

2. 如何工作？

    - 所有的写操作（生产者发消息）都首先进入主队列，然后由主队列将消息和状态同步给所有的从队列。

    - 所有的读操作（消费者收消息）虽然可以从任何副本连接，但最终都是通过主队列来处理的，以确保一致性。

    - 当主节点宕机时，资历最老的那个从队列会自动升级为新的主队列，服务继续，对客户端几乎无感。

3. 优点与缺点

    - 优点：数据安全，消息不会因为单个节点宕机而丢失。

    - 缺点：性能开销大。每一次消息操作都需要在所有镜像间完成同步，这会增加网络延迟，是一种牺牲性能换取可靠性的方案

### 仲裁队列 \(RabbitMQ 3\.8版本后引入\)

核心思想：Raft共识算法

1. 是什么？
仲裁队列是RabbitMQ新推出的默认高可用方案。它不再采用传统的主从复制，而是基于 Raft共识算法 实现的。

2. 如何工作？

    - 队列的所有副本（节点）组成一个Raft集群。

    - 任何操作（读或写）都必须得到多数节点的确认才算成功。这保证了数据的强一致性。

    - 领导者选举是Raft协议内置的机制，当主节点宕机时，集群会自动、快速地进行选举，选出新的主节点。

3. 优点与缺点

    - 优点：

        - 性能更好：由于其算法设计，特别是在网络延迟较高的环境中，性能通常优于镜像队列。

        - 更轻量：避免了镜像队列复杂的同步逻辑。

        - 自动安全处理：默认行为更安全，例如当节点失联后恢复时，能自动处理数据冲突。

    - 缺点：需要奇数个节点（如3、5、7）来形成“多数派”，以确保选举能正常进行。





## 6、消息积压/堆积问题

1. **消息过多，消费者消费速度太慢。那么可以**

    - 增加多个消费者并发消费

    - 每个消费者中使用多线程并发消费

    - 设置消息存活时间\(TTL\) Time To Live

    - 设置队列中存储消息的界限\(Lim\) limit

消息队列（MQ）中的消息堆积问题，通常是指消息发送速度远大于消息处理速度，导致消息积压的情况。这可能导致消息延迟处理、资源耗尽等问题。

- 增加消费者数量：通过增加更多的消费者实例来提高消费能力。

- 提高单个消费者的处理能力：优化业务逻辑，减少不必要的网络调用或数据库操作。

- 异步处理：对于一些耗时的操作，考虑使用异步方式处理，以减少处理单条消息的时间。

- 多线程处理：消费者通过多线程接收消息并处理。

- 批量处理：尽可能批量处理消息，减少每次处理的开销。

- 限流：限制消息发送速率，例如采用漏桶算法或令牌桶算法控制生产者发送速度。

- 增加服务器资源：根据实际情况增加服务器的CPU、内存等硬件资源。

- 优先级队列：如果支持，可以使用优先级队列来保证重要的消息能够被优先处理。







2. **消费者消费失败，消息还在业务队列中。**

    - 再重试一次，如果还不行，扔到死信队列，避免队列阻塞。

## 7、死信队列

当我们的业务队列处理消息失败\(业务异常重试次数达到上限、消息被拒绝、消息过期、队列已满\)，就会将这些消息重新投递到一个新的队列，这个队列存储的都是处理失败的消息，这个队列就叫死信队列DLQ\(Dead Letter Queue\)。



什么是死信？或者说为什么叫死信？因为这些消息大概是因为：

- 消息发送的时候被拒绝 \(basic\.reject or basic\.nack\)

- 或者 消息过期 TTL\(Time To Live\)

- 也可能是 队列已满 消息进不了队列；那这些消息都被称为死信



使用场景：只要是需要发送延迟消息的地方都可以使用死信队列实现；如：清理垃圾附件、超时取消合同、超时支付等

## 10、 RabbitMQ 中实现顺序消费消息

1、**基于单个队列实现顺序消费**

- **单队列模型：** 最直接的方式是使用一个队列来保证消息顺序。RabbitMQ 会按照生产者发送消息的顺序，将消息逐个传递给消费者，消费者会按照队列中的顺序来消费这些消息。确保消费者一个接一个地消费消息就可以保证顺序消费。 

2、**使用消息的唯一标识符和分区**

如果有多组消息需要按顺序消费，但这些消息是独立的（例如：每组消息对应某个特定的用户、订单或其他对象），可以根据消息的分区键（例如：用户ID、订单ID等）将消息路由到不同的队列。

3、**配置 ****`prefetch`**** 参数**

在 RabbitMQ 中，`prefetch` 使得每个消费者一次只处理一个消息，从而保证了消息的顺序性。

- 随机选择一个服务器实例。

**WeightedResponseTimeRule（加权响应时间）**

- 根据每个服务器的平均响应时间计算权重，响应时间越长权重越小，被选中的几率也越小。

**RetryRule（重试）**

- 先按照 RoundRobinRule 获取服务实例，如果获取失败，则在指定的时间间隔内重试。



## 5、Nacos服务注册与发现

Nacos是一个服务注册与发现的组件，用在分布式微服务系统间作为注册中心。服务的注册与发现的流程如下：

- 服务启动时就会注册自己的服务信息（服务名、IP、端口）到注册中心

- 调用者可以从注册中心订阅想要的服务，获取服务对应的实例列表（1个服务可能多实例部署）

- 调用者自己对实例列表负载均衡，挑选一个实例

- 调用者向这个实例发起远程调用



当服务提供者的实例宕机或者启动新实例时，调用者如何得知呢？

- 服务提供者会定期向注册中心发送请求，报告自己的健康状态（心跳请求）

- 当注册中心长时间收不到提供者的心跳时，会认为这个实例宕机，将其从服务的实例列表中剔除

- 当服务有新实例启动时，会发送注册服务请求，其信息会被记录在注册中心的服务实例列表

- 当注册中心服务列表变更时，会主动通知微服务，更新本地服务列表



## 6、Nacos 心跳机制

Nacos 通过**心跳机制**来实时监控服务实例的健康状态。当服务实例出现问题（如宕机、网络中断、负载过高）时，Nacos 会根据心跳超时规则快速发现并更新服务实例的状态。

- 服务实例：启动后向 Nacos 注册自己，并周期性**每隔5秒**发送心跳信息到nacos。

    - 心跳信息是使用http的put请求发送，包括：服务名称、IP、端口、集群名称、权重、是否为临时实例等

- Nacos 服务端：接收心跳，如果 Nacos 在** 15 秒**内（也就是3 次心跳）没有收到心跳，将实例标记为 不健康。如果连续** 30 秒**（6 次心跳）未收到心跳，Nacos 将该实例从服务列表中 删除（Deregister）

## 8、令牌桶、漏桶、滑动窗口

1. **令牌桶（Token Bucket）**

**令牌桶**算法用于控制请求的流量，允许在一定时间内突发流量，但也会限制整体流量的平均速率。其基本原理如下：

- **令牌的产生**：系统按固定的速率（如每秒生成一定数量的令牌）生成令牌，这些令牌放入一个桶中。

- **桶的容量**：桶有最大容量限制，当桶满时，新生成的令牌将被丢弃。

- **请求的处理**：每次请求到达时，如果桶里有令牌，允许该请求通过，并从桶中取走一个令牌。如果桶里没有令牌，则拒绝该请求，或者根据策略延迟请求。



2. **漏桶**算法通过模拟一个漏水的桶来实现限流。其基本原理如下：

- **请求进入桶中**：每个请求到达时都会进入桶中。

- **桶的容量**：桶有一个固定的容量限制，桶一旦满了，后续的请求就会被丢弃。

- **漏桶的漏水速率**：桶里的请求以固定的速率（与请求的处理速率相同）流出。也就是说，不管桶中积累了多少请求，桶的处理速度是恒定的。



3. **滑动窗口（Sliding Window）**

**滑动窗口**算法是对请求进行时间窗口切割的一种限流算法。它将时间划分为多个小时间片段，采用一个滑动的时间窗口来限制请求数量。其基本原理如下：

- **时间窗口**：将时间划分为固定大小的窗口（如1秒、1分钟等），并记录每个窗口内的请求数。

- **滑动窗口**：每当请求到达时，都会检查当前时间所在的窗口，如果该窗口内的请求数未超过设定的最大限制，允许请求通过；如果超过，则拒绝请求。

- **滑动**：随着时间的推移，窗口会向前滑动，过期的请求将从窗口中移除，新的请求会进入当前窗口。

## 12、Seata的模式

Seata 支持的主要模式：

1. **AT 模式**（Automatic Transaction）

AT 模式是 Seata 默认支持的分布式事务模式，它通过 AOP（面向切面编程）的方式，对数据库操作进行拦截，并自动生成全局事务的分支事务。

- **特点**: 

    - 对业务代码无侵入性，只需要在业务方法上添加 `@GlobalTransactional` 注解即可开启全局事务。

    - 基于 SQL 解析实现，自动解析并生成回滚日志。

    - 支持 MySQL、Oracle、PostgreSQL 等多种主流关系型数据库。



2. **TCC 模式**（Try\-Confirm\-Cancel）

TCC 模式要求业务方为每个参与分布式事务的服务定义三个接口：`try`、`confirm` 和 `cancel`。

- **特点**: 

    - `try` 阶段做资源检查和预留；`confirm` 阶段提交资源，此过程应幂等且非阻塞；`cancel` 阶段释放资源。

    - 更适合不支持事务的数据库；也可以使用这种模式。

3. **XA 模式**

XA 模式是传统的两阶段提交协议，Seata 提供了兼容 XA 的 API 来集成现有的 XA 数据源。

- **特点**: 

    - 强一致性保证，但是性能较低，因为需要锁定资源直到事务结束。

    - 主要用于遗留系统中已有 XA 数据源的情况。

4. **Saga 模式**

Saga 模式是一种长事务管理模型，适用于涉及多个服务调用的长时间运行的业务流程。

- **特点**: 

    - 将整个长事务拆分为若干个补偿事务（Compensable Transactions），每个步骤都有一个正向操作和一个补偿操作。

    - 如果任何一个步骤失败，则会依次执行之前的补偿操作来回滚已经完成的操作。

## 13、Seata的原理

SEATA包含三个角色：TM 事务管理器，RM 资源管理器，TC 事务协调器

如果是采用 **AT****模式的话，原理大概是**：

1. **全局事务开始**：当某个业务发起一个全局事务时，也就是标注了`@GlobalTransactional`（全局事务注解） 的那些方法，TM 会向 `事务协调器` 注册这个全局事务，并生成一个全局事务 ID（XID）。所有参与这个全局事务的服务，也就是分支事务都将使用这个 XID 来标识其属于同一个事务上下文。

2. **本地事务执行**：每个服务（分支事务）作为 RM 参与到全局事务中，在执行本地数据库操作时，Seata 的 AT 模式会在 SQL 执行前后自动拦截并记录 操作前的数据快照 和 操作后的数据快照 。这些快照用于后续的冲突检测或回滚操作。然后它就直接提交了。

3. **分支事务 提交 或者 回滚**：RM 在执行本地事务后，会将本地事务的执行结果（包括上述的快照信息）上报给 TC，TM在业务都执行完后发起全局事务提交或者回滚；`事务协调器` 检测每个分支事务的执行结果决定是提交还是回滚全局事务。如果所有 RM 都上报成功，`事务协调器` 发出提交的指令，也表示全局事务成功；如果有任何一个 RM 上报执行异常，那么`事务协调器`发出回滚指令，整个全局事务都会被回滚。

AT模式下；如果是全局发出提交的指令，那么分支要做的就是删除快照；如果是全局发出回滚的指令就根据快照回滚数据。



如果是采用 **XA****模式的话，原理大概是**：

1. **全局事务开始**：当某个业务发起一个全局事务时，也就是标注了`@GlobalTransactional` 的那些方法，TM 会向 TC 注册这个全局事务，并生成一个全局事务 ID（XID）。所有参与这个全局事务的服务，也就是分支事务都将使用这个 XID 来标识其属于同一个事务上下文。

2. **本地事务执行**：每个服务（分支事务）作为 RM 参与到全局事务中，在执行本地数据库操作时，Seata 的 XA 模式会在 SQL 执行后，不直接提交本地事务，会等待TC的指令进行统一的提交或者回滚。

3. **分支事务 提交 或者 回滚**：RM 在执行本地事务后，会将本地事务的执行结果上报给 TC，TM在业务都执行完后发起全局事务提交或者回滚；TC检测每个分支事务的执行结果决定是提交还是回滚全局事务。如果所有 RM 都上报成功，TC发出提交的指令，也表示全局事务成功，这个时候RM才真正的提交事务；如果有任何一个 RM 上报执行异常，那么TC发出回滚指令，整个全局事务都会被回滚，这个时候RM就执行回滚。



**两阶段提交（2PC）**：在AT或XA模式中，Seata采用了两阶段提交协议来保证分布式事务的一致性。

- **准备阶段**（Prepare Phase）：在这个阶段，所有的 RM 会锁定必要的资源（XA模式才会锁定资源），并向 TC 报告它们是否准备好提交。TC 收集所有 RM 的准备状态。

- **提交或回滚阶段**（Commit or Rollback Phase）：基于所有 RM 的准备状态，TM发起提交或回滚的请求，TC 决定全局事务是提交还是回滚。如果决定提交，TC 会通知所有 RM 提交本地事务；如果决定回滚，TC 会通知所有 RM 回滚至最初的状态。

## 16、OpenFeign原理

在使用OpenFeign时，需要定义一个接口，并使用@FeignClient用于指定服务名称，@RequestMapping等注解指定HTTP方法和路径。在服务器启动时，Feign会为每个标注了@FeignClient的接口创建一个动态代理。这个代理负责处理所有的HTTP请求。

在这个动态代理对象中，会根据服务名在本地缓存中查找对应的服务实例列表；再基于默认的spring cloud loadbalancer负载均衡策略，它默认使用轮询；从服务实例列表中选择一个实例，与Feign客户端中调用方法路径进行拼接一个完整的地址，再利用 okHttp、HttpClient等对这个地址发起请求获得响应数据。 但如果在本地缓存中没有找到服务实例的话那么它会到注册中心中根据服务名拉取实例列表再缓存到本地。

## 17、熔断降级

**熔断**是一种**保护机制**机制的主要目的是防止系统在依赖的服务发生故障时，出现连锁反应，从而导致整个系统的崩溃。在某个服务出现异常时，**熔断器会中断对服务的调用**，避免继续调用故障服务而导致系统性能进一步下降。

**工作原理**：

- 关闭状态（Closed）：服务正常时，熔断器是关闭的，正常请求可以通过。

- 打开状态（Open）：当服务请求失败率达到一定阈值（比如超时、500错误等），熔断器进入打开状态，拒绝对该服务的所有请求，短时间内不再尝试调用该服务。

- 半开状态（Half\-Open）：熔断器进入半开状态，允许部分请求尝试连接服务。如果部分请求成功，熔断器会恢复到关闭状态；否则，熔断器会继续处于打开状态。

熔断器可以通过设置失败次数、错误率、超时时间等条件来决定何时触发熔断。



**降级**是**应急方案**，在系统出现故障时，提供备用的解决方案，尽量减少对用户的影响。与熔断器不同，**降级是提供一种后备应急方案，确保服务能够在故障发生时还有可用的功能。**

**工作原理**：

- 当目标服务调用失败时，降级机制会返回预设的备用结果或执行其他替代方法。降级通常会减少功能的复杂性，而不是完全中断服务。

- 例如，在外部服务无法访问时，可以返回一个静态的默认值，或者给出友好的错误提示，减少用户体验的负面影响。

降级的实现：

- 硬降级：直接返回一个默认的值，或者一个错误提示。

- 软降级：降低服务的处理能力，例如返回简化的内容或者限制功能范围。

## 23、XXL\-JOB的模式（路由策略）有哪些

路由策略也就是在XXL\-JOB执行任务的时候，这些任务在哪些执行器上执行；怎么选择执行器的；它的路由策略有如下的这些（加粗的是常见的，可以优先说）：

- FIRST（**第一个**）：任务在调度的时候固定选择第一个执行器；

- LAST（**最后一个**）：任务在调度的时候固定选择最后一个执行器；

- ROUND（**轮询**）：所有执行器实例轮询执行任务；

- RANDOM（**随机**）：随机选择在线的执行器；

- SHARDING\_BROADCAST\(**分片广播**\)：广播触发对应集群中所有执行器执行一次任务，同时系统自动传递**分片参数**；可根据分片参数开发分片任务；

- CONSISTENT\_HASH（一致性HASH）：每个任务按照Hash算法固定选择某一台执行器，且所有任务均匀散列在不同执行器。

- LEAST\_FREQUENTLY\_USED（最不经常使用）：使用频率最低的执行器优先被选举；

- LEAST\_RECENTLY\_USED（最近最久未使用）：最久未使用的执行器优先被选举；

- FAILOVER（故障转移）：按照顺序依次进行心跳检测，第一个心跳检测成功的执行器选定为目标执行器并发起调度；

- BUSYOVER（忙碌转移）：按照顺序依次进行空闲检测，第一个空闲检测成功的执行器选定为目标执行器并发起调度；

## 25、时间轮（Time Wheel）原理

时间轮是一种基于环形结构的数据结构，它的核心思想是将任务按时间间隔进行划分，然后利用环形队列将任务按照时间周期分配到不同的槽中。当任务的时间到达时，时间轮会触发对应的任务。



一般答到上面的内容就可以了；如具体问再具体说，时间轮的工作流程如下：

1. 时间轮的结构：时间轮通常由若干个槽（Slot）组成，每个槽代表一个时间段（例如，1秒、5秒等）。时间轮会循环滚动，当时间指针滚动到某个槽时，会触发该槽中存储的任务。

2. 任务分配到时间槽：定时任务的执行时间会被计算并映射到对应的时间槽中。例如，某个任务的执行时间是10秒后，时间轮会把该任务安排到10秒钟的槽里。

3. 时间轮滚动：时间轮会定时地滚动，每次滚动时，时间指针会从当前槽滚动到下一个槽，直到完成整个周期。每次滚动时，时间指针会触发与当前槽对应的任务。

4. 任务触发与执行：当时间指针滚动到某个槽时，系统会检查该槽中是否有任务。如果有任务，则立即执行。

## 7、倒排索引

**倒排索引（Inverted Index）**。在倒排索引中，**词条（Term）** 和它出现的 **文档 ID** 会形成映射关系。它记录词条出现在哪些文档，在什么位置，出现多少次；这样查询的时候会先对搜索的关键字进行分词，再根据分出的词条找到对应的文档id，直接再根据文档的id找到文档并返回；所以是很快的。



**倒排索引的构建过程**大致如下：

- **文档拆分**：将待搜索的文档（例如一篇文章或网页）拆分成词条（也就是单词）。

- **去除停用词**：去除一些常见但不具有搜索价值的停用词（如 "的"、"是" 等）。

- **词频统计**：对于每个词条，记录它在文档中的出现频率，以及它出现在那些文档中。

- **倒排索引表**：最终，倒排索引表会将词条映射到它出现的文档列表中。



**查询流程**

当用户提交查询请求时，Elasticsearch 会解析查询语句，将其转换为相应的内部表示形式，然后利用倒排索引来快速定位相关文档。具体步骤如下：

- **解析查询**：根据查询语法分析输入，提取出关键词或其他条件。

- **查找匹配项**：利用倒排索引迅速找到与关键词对应的文档集合。

- **评分排序**：基于多种因素（如TF\-IDF、BM25等算法），计算每个候选文档的相关性得分，并按分数高低排列结果。

- **返回结果**：最终，按照评分顺序返回最相关的文档。

## 8、正排索引/正向索引

正排或者说正向索引；意思是将**文档内容**与其**唯一标识符**（一般是文档ID）进行映射的索引结构。在正排索引中，索引的重点是每个文档的内容本身，而不是词条与文档之间的关系。 也就是说；它要先根据文档ID查询到文档之后，然后再使用搜索的关键字与文档的内容进行对比；判断文档内容是否有包含当前的搜索关键字。

## 9、ES的分词策略是什么

创建索引（也就是插入数据到es的时候）的时候使用ik\_max\_word最细粒度；

搜索的时候使用 ik\_smart 智能分词（最粗粒度）



为什么？

\-\- 创建的时候希望更多的词条能够关联到某个文档，这样在搜索的时候更有可能被检索到

\-\- 搜索的时候希望更加能够贴近用户的搜索期望，而不要分词太细

例如：创建的时候有内容为：智能的华为手机； 我们希望搜索华为、手机、华为手机都能将这个文档搜索出来，在用户没有更明确的搜索关键字的情况下，给用户更多可以查看的数据；

而 当搜索的时候；输入 智能的华为手机； 这时候用户是更希望能搜到到 华为手机 的，这时候分词就尽可能不要分那么细，分成 智能、华为手机就更好。搜索出来的答案比较符合用户的预期。

## 10、深度分页

针对深度分页，elasticsearch提供了两种解决方案：

- `search after`：分页时需要排序,第二次查询时候携带上一次查询的排序值作为 search\_after的值就可以了；原理是从上一次的排序值开始，查询下一页数据。官方推荐使用的方式。

- `scroll`滚动查询：原理将排序后的文档id形成快照，保存下来，基于快照做分页。官方已经不推荐使用。

## 10、Docker容器的copy on write

Docker容器的copy\-on\-write（写时复制，CoW）特性是docker容器底层存储机制的一部分，主要用于用于管理镜像层与容器层之间的文件系统操作，特别是当需要对文件进行修改时。

**工作原理**

- **共享基础镜像层**：Docker镜像是由一系列只读层组成的，每个层代表了镜像的一个变更集。当创建一个容器时，Docker会在这些只读层之上添加一个可写的容器层。多个容器可以共享相同的底层镜像层，这减少了磁盘空间的占用并加快了容器的启动速度。

- **写时复制**：当某个容器内的进程试图修改任何它下面的只读层中的文件时，Docker会执行`写时复制`操作。也就是说Docker不会直接在原始文件上进行修改，而是将该文件复制到容器的可写层，然后在新的副本上进行更改。这样做既保持了镜像层的不可变性，也确保了各个容器间的隔离性。



## 11、虚拟化和容器化有什么区别

- **虚拟化**：创建的是完整的虚拟机（VM），每个虚拟机都包含一个独立的操作系统内核和用户空间。是一个完全隔离的环境，具有自己的操作系统实例。每个虚拟机都需要分配一定的内存、CPU 和磁盘空间。

- **容器化**：容器共享宿主机的操作系统内核，拥有独立的用户空间。容器之间的隔离性不如虚拟机强，但启动速度更快且占用更少的资源。容器共享宿主机的内存、CPU和磁盘等资源。



## 12、什么是火焰图

火焰图（Flame Graph）是一种用于可视化分析性能数据的工具；可以通过图形展示程序或系统的运行状态，帮助识别性能瓶颈、CPU 使用热点等问题。常见的火焰图有：

1. **CPU 火焰图**：

    - 显示 CPU 的使用情况，帮助识别哪些函数占用了大量的 CPU 时间。

2. **内存火焰图**：

    - 显示内存分配情况，帮助识别内存泄漏或频繁分配内存的代码段。

3. **I/O 火焰图**：

    - 显示磁盘 I/O 或网络 I/O 的使用情况，帮助识别 I/O 瓶颈。

4. **锁等待火焰图**：

    - 显示线程等待锁的情况，帮助识别死锁或高锁争用的问题。

## 13、并发与并行的区别

**并发：**是指系统能够同时处理多个任务的能力，这里的“同时”并不是说这些任务就是在同一时刻执行，而是指系统能够在不同任务之间快速切换，使得从外部观察来看像是同时进行的。比如：在单核处理器上运行多个线程或进程。

**并行：**则是指真正的同时执行多个任务，通常需要多个处理器核心或分布式系统来实现。并行的目标是通过同时执行多个任务来提高系统的吞吐量和性能。例如：在多核处理器上同时运行多个线程或进程。

## 14、Linux系统的用户态和核心态

**用户态：**是指应用程序通常运行的状态。在这种状态下，程序的只能访问有限的内存空间，不能直接访问硬件资源或执行特权指令（如控制中断、修改系统时钟等）。



**核心态：**则是操作系统内核运行的状态。在这种状态下，程序拥有对所有系统资源的完全访问权限，包括硬件设备、内存管理单元、文件系统等。核心态下的代码可以执行任何特权指令。



这两种状态是**可以相互进行转换**的。

## 15、程序局部性原理

局部性原理主要分为两大类：时间局部性和空间局部性。

**时间局部性：**指的是如果某一个数据项被访问了一次，那么在不久的将来它很可能再次被访问。

**空间局部性：**指的是如果某一个数据项被访问了一次，那么与这个数据项相邻或附近的其他数据项在未来也有可能被访问。

## 16、Linux系统的文件描述符

**文件描述符（File Descriptor）**是一个用于访问文件或其他输入/输出资源的抽象标识符。文件描述符是一个非负整数，通常用int类型表示。当进程打开文件或创建文件时，操作系统会返回一个文件描述符，供进程后续使用来操作这个文件。



- Linux为每个进程预分配了三个标准文件描述符：

    - 0（标准输入，stdin）：通常与键盘输入相关联。

    - 1（标准输出，stdout）：通常与终端屏幕输出相关联。

    - 2（标准错误，stderr）：通常也与终端屏幕输出相关联，但专门用于错误信息。

## 17、Linux系统中的信号量

**信号量（Semaphore）**：是一种用于控制多个进程或线程对共享资源访问的同步机制。信号量可以防止竞争条件，确保在多任务环境下资源的安全访问。信号量分为两种类型：二进制信号量（Binary Semaphore）和计数信号量（Counting Semaphore）。



**二进制信号量（Binary Semaphore）**：

- 类似于互斥锁（Mutex），其值只能是0或1。

- 当值为1时，表示资源可用；当值为0时，表示资源已被占用。

**计数信号量（Counting Semaphore）**：

- 允许更广泛的值范围，不仅可以表示资源是否被占用，还可以表示有多少个资源可用。

- 初始值表示可用资源的数量，每次获取资源时减1，释放资源时加1。

## 18、灰度发布、蓝绿发布、金丝雀发布

**灰度发布：**是一种逐步将软件的新版本推向用户的软件部署方式。它从一个较小的用户群体开始测试部署，然后根据反馈和性能监控情况逐步扩大到更大的用户群体，直到完全替换旧版本。

**金丝雀发布：**是一种逐步推出新版本的策略，类似于灰度发布，但更注重通过小范围的早期用户来验证新版本的稳定性。在金丝雀发布中，系统的某一小部分用户（通常是通过某些特定标识）首先体验到新版本，确保新版本在低风险下验证无误后，再逐步向其他用户推出。

**蓝绿发布：**是一种通过使用两套完全相同的环境（蓝环境和绿环境）来实现无缝切换的发布策略。在蓝绿发布中，蓝环境是当前生产环境，绿环境是新版本的环境。

## 7、VUE2 和 VUE3 的区别

**性能优化**

- 虚拟DOM重写：Vue 3对虚拟DOM进行了全面重写，使其在性能上有了显著提升。

- 更高效的编译器：引入了更多优化措施，如静态树提升、静态属性提升等，减少了不必要的渲染。

**生命周期钩子调整**

- 部分生命周期钩子名称有所变化，并新增了一些用于配合组合式API的新钩子，比如`onMounted`、`onUpdated`等。

**更好的TypeScript支持**

- Vue 3从一开始就考虑到了与TypeScript的良好集成，提供了更好的类型推断能力和更多的类型定义支持，提升了开发体验。

**组合式API（Composition API）**

- Vue 3引入了一种新的逻辑复用和代码组织机制——组合式API，它提供了一种更加灵活的方式来组织组件逻辑，特别适合于复杂或大型应用。

**响应式系统改进**

- Vue 3使用Proxy对象代替Vue 2中的Object\.defineProperty来实现响应式数据绑定，这使得Vue 3能够检测到对象属性的添加或删除，并且在某些情况下拥有更好的性能表现。

**全局API和内部模块化**

- 在Vue 3中，许多全局API被重构为可以按需导入的形式，例如`Vue.nextTick()`现在可以直接通过`import { nextTick } from 'vue'`来使用，这种方式有助于减少打包体积并提高灵活性。

**片段\(Fragments\)支持**

- Vue 3允许一个组件拥有多个根节点（即不再强制要求单个根元素），这对于某些布局设计非常有用。

**Teleport特性**

- Vue 3引入了Teleport功能，使你可以将子组件的内容渲染到DOM中的任何位置，这对于模态框、提示框等场景尤其有用。

**更小的核心库尺寸**

- Vue 3的核心库经过优化后变得更小巧，同时借助tree\-shaking技术，未使用的特性不会被打包进最终的应用程序中，从而进一步减小了打包后的文件大小。

## 8、v\-if 和 v\-show 的区别

`v-if`是一个“真实的”条件渲染指令，它会根据表达式的值决定是否将节点插入DOM中。

`v-show`只是简单地通过CSS的`display`属性来切换元素的可见性。无论初始条件是什么，元素都会被渲染，也就是说它是简单的CSS样式切换。

## 8、项目有哪些git的分支

我们项目的话；有主分支、开发分支、修复分支、发布分支；大概这四个分支吧；我一般都在开发哪个版本就在哪个版本的开发分支下推拉代码的。



1\. **主分支（Main 或 ****Master****）**

- **`main`**** 或 ****`master`**：这是项目的默认分支，代表了稳定版本的历史记录。通常只有经过充分测试并通过审核的代码才会合并到此分支。

- **注意事项**：应保持这个分支始终处于可部署状态。

2\. **开发分支（****Dev****elop）**

- **`develop`**：用于集成所有功能分支的代码。它包含了最新的开发改动，但可能还不完全稳定。

- **用途**：在此基础上创建新的功能分支，或者从这里拉取最新的更改以确保自己的工作是最新的。

3\. **功能分支（****Feature ****Branches）**

- **格式**：`feature/[描述]` 或 `features/[描述]`

- **用途**：每个新功能或特性都应该有自己的分支。这样可以让多个并行工作而不互相干扰。完成的功能需要通过代码审查后才能合并回 `develop` 或其他适当的分支。

4\. **修复分支（****Hotfix**** Branches）**

- **格式**：`hotfix/[描述]`

- **用途**：当生产环境中发现紧急问题时，直接从 `main` 或 `master` 分支创建一个 `hotfix` 分支来快速修复问题。修复完成后，应该将更改同时合并到 `main/master` 和 `develop` 分支，以保证未来的版本也包含这个修复。

5\. **发布分支（****Release**** Branches）**

- **格式**：`release/[版本号]`

- **用途**：当准备发布新版本时，从 `develop` 分支创建一个 `release` 分支。在这个分支上可以进行最后的调整、文档更新等操作。一旦准备好，就将其合并到 `main/master` 和 `develop` 分支，并打上标签（tag）作为正式版本。

6\. **实验性分支（Experimental 或 Sandbox Branches）**

- **格式**：`exp/[描述]` 或 `sandbox/[描述]`

- **用途**：用于尝试性的开发工作，比如探索新技术或实现不确定能否被采纳的功能。这些分支不一定最终会被合并到主分支中。

7\. **临时分支（Temporary Branches）**

- 这类分支可能是为了特定任务而创建，如解决某个特定的问题或参与一次性的合作项目。它们通常会在任务完成后被删除。

## 15、WMS的仓内作业流程

WMS（Warehouse Management System，仓库管理系统）是用于管理和优化仓库操作的软件系统。仓内作业流程参考如下：

1\. **收货（Receiving）**

- **定义**：接收来自供应商或制造商的商品，并将它们录入系统。

- **流程**： 

    - 验证货物是否符合采购订单上的规格。

    - 检查数量、质量和包装完整性。

    - 使用扫描设备（如条形码或 RFID）记录每个商品的信息。

    - 将商品分配到临时存储区或者直接送往指定的储存位置。

2\. **上架（Putaway）**

- **定义**：将收到的商品放置到合适的存储位置。

- **流程**： 

    - 根据预先设定的规则（例如 FIFO 先进先出、FEFO 先到期先出）选择最佳存放地点。

    - 更新 WMS 中的位置信息以反映新的库存状态。

    - 可能涉及使用自动化设备如自动导引车 \(AGV\) 或堆垛机。

3\. **配拣（Picking）**

- **定义**：根据客户的订单从仓库中取出所需的商品。

- **流程**： 

    - 接收订单并生成拣选清单。

    - 拣选员按照清单指示前往各个存储点取货。

    - 使用手持终端或其他技术确认所取商品正确无误。

    - 收集完成后，将商品集中在一个区域准备打包发货。

4\. **分拣（Sorting）**

- **定义**：对已拣选的商品进行分类整理，确保每个包裹包含正确的物品组合。

- **流程**： 

    - 在流水线上根据目的地或客户类型对商品进行分组。

    - 自动化系统可以根据标签或扫描数据自动分拣。

    - 确保每一批次的商品都被准确地分配给相应的运输批次。

5\. **包装（Packing）**

- **定义**：将分拣后的商品装入适当的容器中以便运输。

- **流程**： 

    - 选择适合尺寸和类型的包装材料。

    - 在包装过程中附上必要的文档，如发票、装箱单等。

    - 对完成的包裹进行称重、测量体积，并贴上运单标签。

6\. **发货（Shipping）**

- **定义**：将包装好的商品交给承运人进行配送。

- **流程**： 

    - 确认所有包裹都已正确标记并与运输文件匹配。

    - 安排运输方式（快递、货运等）。

    - 更新 WMS 和 ERP 系统中的发货记录，以便后续跟踪。

7\. **退货处理（Returns Processing）**

- **定义**：处理退回的商品，检查其状况并决定如何处置。

- **流程**： 

    - 接收退货并核对相关信息。

    - 检验商品质量，确定是否可以重新入库销售。

    - 如果适用，则修复或销毁商品。

    - 更新库存记录，调整财务账目。

## 16、MES系统的主要功能和流程

MES（Manufacturing Execution System，制造执行系统）是连接企业资源计划（ERP）和车间生产的中间管理系统，主要目的是监控和控制车间的生产过程，以确保生产效率、质量和订单的准确执行。MES系统的主要业务流程通常包括以下几个核心环节：



1\. **生产订单管理**

- **定义**：生产订单管理是MES系统中的基础业务流程，它主要负责生产计划和生产订单的创建、分配、调度和跟踪。

- **流程**：

    1. 从ERP系统接收生产订单，包含生产数量、交货日期、生产工艺等信息。

    2. 生成生产任务并将任务分配到具体的生产线或车间。

    3. 跟踪生产订单的执行状态，包括生产进度、质量数据等。



2\. **物料管理**

- **定义**：物料管理是指在生产过程中，对原材料、半成品、成品以及各类消耗品的管理，包括物料的采购、存储、领用、发放及消耗。

- **流程**：

    1. 根据生产计划，MES系统会从仓库管理模块获取所需物料。

    2. 发放物料到生产线，确保生产顺利进行。

    3. 物料的消耗会实时反馈到系统中，以便进行库存管理和物料补充。



3\. **生产调度管理**

- **定义**：生产调度管理是指对生产过程中的设备、人员、物料等资源的安排和协调，以确保生产计划的顺利执行。

- **流程**：

    1. 根据生产订单的需求，调度生产线的设备和人员。

    2. 对生产进度进行实时监控，调整生产计划和资源配置。

    3. 生产中出现的任何异常情况（如设备故障、物料短缺等）都会触发调整和优化调度。



4\. **车间数据采集**

- **定义**：车间数据采集是指通过各种设备和传感器自动收集生产过程中产生的各类数据（如生产数量、设备状态、工艺参数等），并将其上传到MES系统进行实时监控和分析。

- **流程**：

    1. 生产过程中的设备通过自动化采集装置获取数据。

    2. 数据实时上传到MES系统，系统分析当前生产状况，生成生产报表。

    3. 在生产过程中，操作员可以实时查看数据反馈，及时做出调整。



5\. **质量管理**

- **定义**：质量管理是指在生产过程中，对产品的质量进行实时监控和检验，确保生产出来的产品符合质量标准。

- **流程**：

    1. 生产过程中，质量检测点会进行质量抽查或全检。

    2. 质量数据实时反馈到MES系统，系统记录并生成质量报告。

    3. 当发现不合格品时，MES系统会通知相关人员进行处理，如停产、返工或废弃。

    4. 质量问题的追溯功能帮助企业对不合格产品进行分析，定位根本原因。



6\. **生产过程监控与追溯**

- **定义**：生产过程监控与追溯是指对生产过程进行全面监控，并记录下所有与生产过程相关的信息，以便在后期对问题进行追溯和分析。

- **流程**：

    1. MES系统实时跟踪生产线上的每一项生产任务、设备运行状态及每道工序的执行情况。

    2. 生产的每一个工艺环节、每一批次产品、每台设备的工作状况、使用的物料等都会被记录在案，形成完整的生产追溯数据。

    3. 当出现质量问题或生产异常时，可以通过追溯功能快速定位问题源，进行纠正和改进。



7\. **设备管理**

- **定义**：设备管理是指对车间生产设备的维护、维修、保养、运行监控等活动的管理，确保设备处于良好的工作状态。

- **流程**：

    1. 通过MES系统监控设备的实时状态（如运行、故障、维护等）。

    2. 定期进行设备维护保养，并通过系统记录设备维修和保养历史。

    3. 当设备出现故障时，系统会自动生成维修请求，安排维修人员进行处理。



8\. **生产绩效管理**

- **定义**：生产绩效管理是对生产过程的效率进行评估和管理，包括生产速度、质量、设备利用率、人工效率等方面的考核。

- **流程**：

    1. MES系统通过采集车间数据（如生产数量、生产时间、设备利用率等）生成生产绩效报告。

    2. 根据生产绩效数据，分析生产瓶颈、人员表现及设备效率。

    3. 通过优化生产计划、设备调度和人员配置，提升生产效率和降低生产成本。



9\. **生产报告与分析**

- **定义**：生产报告与分析是指在生产过程中对各类生产数据进行汇总、分析和报告生成，帮助管理者做出科学的决策。

- **流程**：

    1. 根据生产过程中收集到的各种数据，MES系统生成定期或实时的生产报告。

    2. 分析生产数据，找出效率提升的机会，或发现潜在的问题（如质量下降、设备故障频繁等）。

    3. 通过数据分析结果，为企业的生产决策提供依据，优化生产流程。

## 3、DeepSeek低成本且能力强

1. **混合专家模型 \(Mixture of Experts, MoE\)**：DeepSeek采用了MoE架构，这种技术允许模型根据输入动态选择不同的“专家”子模型进行处理。这意味着整个网络并非每次都全量激活，而是仅激活与当前任务相关的部分，从而显著减少了计算资源的需求。

2. **多标记预测 \(Multi\-Token Prediction, MTP\) 技术**：这项技术使模型能够同时预测多个连续的标记（token），提高了训练效率，使得在相同时间内可以处理更多的数据，进而提升了性能。

3. **多头潜在注意力机制 \(Multi\-Head Latent Attention, MLA\)**：通过将高维特征压缩到低维潜在空间再恢复，这种方法不仅减少了计算负担，还保持了模型的表现力，有助于提高处理速度和效率。

4. **FP8混合精度训练**：利用比常规更低精度的数据格式（如FP8）进行训练，可以减少存储需求和计算量，但仍然能维持较高的准确性和效率，这有助于降低成本。

5. 动态电压调节技术：该技术让硬件在计算间隙自动进入低功耗状态，类似于呼吸一样节省电力消耗，从而降低运行成本。

6. **数据增强技术**：DeepSeek开发的技术可以从少量数据中生成大量有效的训练样本，这种方式类似于用有限的原材料创造出丰富的菜肴，极大降低了数据获取和处理的成本。

7. **乐高式训练法**：这种方法首先训练好基础模块，然后根据具体任务快速组装成新模型，避免了从头开始训练整个模型所需的高昂成本。

## 4、什么是数据蒸馏

**数据蒸馏（Data Distillation）**是机器学习中的一种技术，旨在通过从大模型或大量数据中提取精华，以生成一个更小、更高效的模型。这个概念有时也被称为知识蒸馏（Knowledge Distillation）。

数据蒸馏通过将复杂的大模型或大量的训练数据“压缩”成一个较小的模型，或者将大量无标注数据转化为有标注的数据，用来提升模型的性能。它通常分为以下几个步骤：

1. **大模型训练**：首先训练一个非常复杂的、计算资源消耗较大的大模型（通常是深度神经网络）。

2. **生成蒸馏数据**：从大模型中提取出关键的信息（例如概率分布、模型的中间表示或注意力机制等），这些信息可以帮助小模型更好地学习。

3. **训练小模型**：使用这些蒸馏数据来训练一个较小的模型。这个小模型通过学习从大模型中得到的知识，尽可能保留大模型的能力，但它通常在推理时速度更快，计算资源需求更低。

## 5、各大模型调用时候的多少B是什么意思

大模型的API调用时，提到的“B”通常是指请求或响应中的一个参数或限制条件，尤其是在涉及到处理文本生成、补全或是对话等任务时。这里的“B”指的是**最大上下文长度（也称为最大token数量）**，即模型能够处理的最大输入和输出的总长度。Token可以是一个单词、一个标点符号或者根据模型定义的一个子词单元。



具体来说，很多自然语言处理模型在进行文本生成、补全或对话时，都会受到输入文本的上下文长度限制。这个上下文长度是通过“tokens”来计算的，而“B”常常代表了这个上下文的**最大 token 数量**，也就是模型在一次调用中能处理的文本量。

**token**是指**模型处理的最小单位，通常一个字或词会被拆解成多个 token**。因此，如果文本非常长，它可能会被拆分成多个 token，而大模型的上下文限制（"B"）决定了模型在一次推理过程中能够“记住”多少个 token。

例如：

- 如果模型的最大上下文长度是 4096 tokens，那么“B”可能就是 4096，意味着模型最多能够处理包含 4096 tokens 的**输入和生成的输出总和**。

- 这对于长文本的处理尤其重要，因为如果输入文本超过这个限制，部分文本可能会被截断，或者你可能需要分多次调用来处理。

- **原因**：ThreaLocal使用之后没有及时删除；导致ThreadLocal类的`ThreadLocalMap` 中的对象一直被被强引用，无法回收，这样的话，垃圾回收后空间还是被占用，到最后空间不足，触发垃圾回收越来越频繁，cpu就一直居高不下。

- **解决**：排查的比较久；后来在系统中找到CPU占用高的java的PID，然后使用 jmap \-dump  导出线程日志文件；使用IDEA直接可以打开分析里面的 大对象 ；发现用户信息拦截器类中的ThreaLocal类的ThreadLocalMap属性比较大；定位到问题的类之后去排查，也确实发现了我们的同事在拦截器中的前置方法中获取了请求头中的用户信息到 ThreadLocal中之后；没有释放删除用户信息，导致这些用户信息一直留在ThreadLocalMap中，越积越大；出现的问题。 后来我在这个拦截器中添加了完成时方法afterCompletion中，添加了移除了用户的信息的代码，最终测试且更新上去后；发现不会出现系统使用几天就CPU越来越高的问题。



为什么开发时候没有发现？  这个问题如果不是用户使用量上来了的话是很难发现的，我们开发并不会每个功能都会压测那么多的用户访问系统，所以当时没有发现这个问题。 另外；这个功能并非我做的，不清楚同事为什么没有去删除。不是我做的功能我也不会去进行测试啥的，所以算是遗留问题吧。

## 7、在高并发场景下，如何保证雪花算法生成的id唯一

雪花算法（Snowflake Algorithm）是一种分布式 ID 生成算法，它能够高效地生成全局唯一的64位**整数**ID。

雪花算法生成的64位ID结构如下：

- **1位符号位**：始终为0，表示这是一个正数。

- **41位****时间戳**：记录了从一个自定义的纪元时间（通常是2022年1月1日或更早的一个时间点）到当前时间的毫秒数，可以支持约69年的时间范围。

- **10位****机器ID**：用于**区分不同的机器实例**，一般由数据中心ID（5位）和工作器ID（5位）组成。

- **12位****序列号**：在同一毫秒内生成多个ID时，用于区分这些ID。

**如何保证唯一性**

1. **时间戳递增**：

    - 每次生成新的ID时，都会检查当前时间是否大于上次生成ID的时间戳。如果是，则使用当前时间；如果不是，则等待直到时间前进。

    - 这样可以确保即使是在极高的并发情况下，只要时间是向前推进的，就不会有重复的时间戳部分。

2. **机器ID唯一性**：数据中心ID\+工作ID

    - 在部署应用时，需要确保每个节点都有一个唯一的机器ID。可以通过配置文件、环境变量或者配置中心来分配机器ID。

3. **序列号管理**：

    - 当同一毫秒内产生多个ID时，通过原子操作增加序列号来保证这一毫秒内的ID不重复。

    - 如果同一毫秒内的请求数超过了序列号的最大值（即2^12 = 4096），则会阻塞请求直到下一毫秒开始，从而防止溢出导致的ID重复。

## 8、数据库查询分页查询最后一页很慢怎么优化

**问题**：查数据的最后一页，查了一千页数据发现查询太慢，你会怎么办



我会采用 覆盖索引 \+ 临时表的做法来优化。也就是先使用覆盖索引快速查询出符合条件的最后一页数据，然后再连表返回这最后一页的数据的全部信息就可以了。

类似如下：

```SQL
/* 
查询第1000页，每页1000条员工（用户id，姓名，部门名称） */
/*耗时1秒451毫秒
explain 后发现只用到了一个dep_id的非唯一索引
*/
select e.id, e.name, d.deptName
        from employee e, department d
        where e.dep_id = d.id
        limit 999000,1000;
       
/*
使用子查询，利用覆盖索引减少回表的方式进行分页
耗时：239ms
*/
select e.id, e.name, d.deptName
from (
select e1.* from employee e1,(select id from employee limit 999000,1000 ) e2 where e1.id = e2.id) e, department d
where e.dep_id = d.id;
```

## 10、MySQL从数据库同步很慢怎么解决

**问题**：数据库做主从，有一个表比较大，数据量接近千万级别，要去给他在里面一些字段做加密，在这个动作里面呢本身这个库是做了主从的，在主库做加密的动作，实际上就是一条条去查，在从库上出现了问题，写进去的速度非常非常慢，怎么去解决？

1. 批量处理

- **分批更新**：将更新操作分成多个小批次来执行，而不是一次性处理所有记录。这可以减少单次事务的大小，降低锁定时间，并减轻从库的压力。

- **并行处理**：如果表结构允许，可以根据某些条件（如主键范围、日期区间等）分割任务，让多个线程同时处理不同的数据子集。

2. 优化索引和查询

- **确保索引有效**：确认用于过滤记录的字段上有适当的索引，以便快速定位需要加密的数据行。

- **简化查询逻辑**：尽量避免复杂的JOIN、子查询等操作，使用更直接的SQL语句来提升效率。

3. 也可以直接将主库的数据库表导出来dump文件；然后以导出文件再导入到从库中

## 21、在后端开发中如何处理前端的跨域请求

    ```YAML

            add-to-simple-url-handler-mapping: true

              '[/**]':

                  - GET

                  - OPTIONS
                allowedHeaders: "*"
                allowCredentials: true
    ```

```Java
@RestController
public class MyController {
    // 对所有来源开放 CORS
    @CrossOrigin(origins = "*")
    @GetMapping("/data")
    public String getData() {
        return "This is CORS-enabled for all origins.";
    }

    // 只对指定来源开放 CORS
    @CrossOrigin(origins = "http://example.com")
    @GetMapping("/specific-data")
    public String getSpecificData() {
        return "This is CORS-enabled for a specific origin.";
    }
}
```

## 28、线上排查问题的工具有哪些

    `-Xloggc:/tmp/gc.log -XX:+PrintGCDetails -XX:+PrintGCDateStamps -XX:NumberOfGCLogFiles=10 -XX:GCLogFileSize=2M`，各参数项含义如下：

    - `-Xloggc:/tmp/gc.log` 日志文件的输出路径

    - `-XX:+PrintGC` 输出GC日志

    - `-XX:+PrintGCDetails` 输出GC的详细日志

    - `-XX:+PrintGCTimeStamps` 输出GC的时间戳（以基准时间的形式）

    - `-XX:+PrintGCDateStamps` 输出GC的时间戳（以日期的形式，如`2013-05-04T21:53:59.234+0800`）

    - `-XX:+PrintHeapAtGC` 在进行GC的前后打印出堆的信息

    - `-XX:NumberOfGCLogFiles=10` 控制GC日志文件个数

    - `-XX:GCLogFileSize=2M` 设置单个GC日志文件大小

## 29、Arthas（阿尔萨斯）作用

- **解决线上问题**：假设你遇到了某个接口响应缓慢的问题，可以使用`trace`命令追踪这个接口的方法调用链路，找出耗时较长的环节。

- **分析异常日志**：如果应用程序抛出了未处理的异常，可以通过`exception`命令捕获最近发生的异常，并进一步调查原因。

- **性能优化**：利用`watch`命令观察方法输入输出，结合`trace`命令分析性能热点，进而优化代码逻辑或调整配置参数。

## 30、要模糊查询加密之后的数据怎么做

倒排索引的思路；对原文进行分词加密；每个词和词句分拆加密存放在数据库中，这样搜索时候就对比加密的字符串即可。

例如：搜索身份证号；输入 440111类似这样的搜索关键字 

那么在保存身份证号的时候就会对：4、44、440、4401、44011、440111、类似这样的进行加密存储到数据中；搜索时就使用关键字对应的加密字符串去对比上面加密后的字符即可
