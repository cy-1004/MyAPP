## 一、这是什么项目

一个**单人自用的 Android 原生 App**，把日常记录（纪念日 / 经期 / 待办 / 记账）、
个人知识库、行业资讯聚合在一个入口里。

**四条硬约束，任何时候都不能违反：**

| 约束 | 含义 |
|---|---|
| **仅安卓原生** | 不用 Flutter / RN / KMP |
| **无自建服务器** | 所有数据本地，只直连公开网页与 RSS |
| **单人自用，不上架** | 所以 `USE_EXACT_ALARM` 这类 Play 严管权限可以用 |
| **拓展性是一等需求** | 加一个 feature 不该改动已有模块，见第四节 |

另外两条同样重要：

- **数据丢了基本找不回** → 严禁 `fallbackToDestructiveMigration()`，每次改表必须写
  Migration 并提交 `schemas/` 下的 JSON。云备份（PRD 3.13）已落地但**默认关闭、每天才跑一次、
  且不含图片附件**，不能当成迁移出错的免死金牌。
- **UI 走 Claude 风格**：暖色、简洁、克制。不用纯白/纯黑，层级用 1px 描边不用阴影，
  一屏最多一个 Accent 焦点。

目标设备：**realme GT Neo5 SE**（realme UI 7.0 / Android 16 / 144Hz），
minSdk 35 · targetSdk 36 · compileSdk 36。

## 二、先把环境跑通（有坑）

### 命令行构建的 JDK 是个陷阱

这台机器上有两个 JDK，**只有一个能用**：

| 路径 | 版本 | 结果 |
|---|---|---|
| `C:\Program Files\Android\Android Studio\jbr` | 25.0.2 | ❌ Gradle 8.13 / AGP 8.9 不支持 |
| `%USERPROFILE%\.jdks\jbr-21.0.11` | 21.0.11 | ✅ |

用错时 Gradle 的报错**只有孤零零一行 `25.0.2`**，没有任何说明，极容易往别处排查。

> **这个项目在两台电脑上开发**，家目录不一样（`C:\Users\cy-10` / `C:\Users\Lenovo`）。
> 所以本文档里的命令一律写 `$HOME`（Git Bash）或 `%USERPROFILE%`，**不要把绝对路径写死**，
> 否则换一台机器照抄就跑不起来。两台机器上 JDK 与 Gradle 的相对位置是一致的。

仓库里没提交 `gradle-wrapper.jar`，命令行走已缓存的发行版：

```bash
export JAVA_HOME="$HOME/.jdks/jbr-21.0.11"
GRADLE="$HOME/.gradle/wrapper/dists/gradle-8.13-bin/5xuhj0ry160q40clulazy9h7d/gradle-8.13/bin/gradle.bat"

"$GRADLE" :app:compileDebugKotlin --console=plain   # 只验编译，最快
"$GRADLE" testDebugUnitTest                         # 跑全部单测
"$GRADLE" :app:assembleDebug                        # 出 APK
```

产物：`app/build/outputs/apk/debug/app-debug.apk`

> 哈希目录名会随 Gradle 版本变，对不上时 `ls ~/.gradle/wrapper/dists/` 重新找。

### 真机调试

设备通过 USB 连着，`adb` 在 `%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe`。

```bash
export MSYS_NO_PATHCONV=1
ADB="$HOME/AppData/Local/Android/Sdk/platform-tools/adb.exe"

"$ADB" install -r app/build/outputs/apk/debug/app-debug.apk   # -r 保留数据
"$ADB" shell am start -n com.myapp.debug/com.myapp.MainActivity
"$ADB" logcat -d -s AndroidRuntime:E          # 查崩溃
```

**在 Git Bash 里跑 adb 要加 `export MSYS_NO_PATHCONV=1`**，
否则 `/sdcard/xxx` 会被转成 Windows 路径。

> ⚠️ **绝对不要用 `adb uninstall` 或 `adb shell pm clear` 验证首启逻辑**
> --这会清掉用户全部数据（纪念日、待办、经期记录），且 `allowBackup="false"`
> 没有云端备份，丢了就是永久丢了。要验证首启向导，在一台没有用户数据的
> 测试机或模拟器上做，或者接受「老用户升级跳过」这条路径就够覆盖了。

无 UI 自动化框架时，可以用 `uiautomator dump` + `input tap` 做确定性的点击验证：

```bash
export MSYS_NO_PATHCONV=1
"$ADB" shell uiautomator dump /sdcard/ui.xml
"$ADB" exec-out cat /sdcard/ui.xml > ui.xml   # 从里面读 text 和 bounds，算出坐标再 tap
```

### 依赖规则（不可违反）

1. `:feature:*` **之间永远不互相依赖**
2. `:feature:*` 只依赖 `:core:*`
3. 跨 feature 协作 → 在 `core/common/contract/CrossFeatureContracts.kt` 定义接口，
   提供方实现 + Hilt 绑定，调用方只注入接口

### 新增一个 feature 的完整步骤

**只需改 3 个已有文件**：`settings.gradle.kts`、`app/build.gradle.kts`、`AppNavHost.kt`。

1. `feature/xxx/build.gradle.kts`——只有 6 行：
   ```kotlin
   plugins { alias(libs.plugins.myapp.android.feature) }
   android { namespace = "com.myapp.feature.xxx" }
   ```
   约定插件已把 library + Compose + Hilt + 序列化 + 全部 core 依赖配好。
2. `settings.gradle.kts` 加 `include(":feature:xxx")`
3. 数据层：在 `:core:database` 的 `model/` `dao/` 加文件，
   `MyAppDatabase` 里加实体、**版本号 +1**、`Migrations.kt` 里补迁移并加进 `ALL_MIGRATIONS`
4. 首页卡片（可选）：实现 `HomeCard` + `@Binds @IntoSet` 绑定。**首页代码一行都不用改**
5. 路由：`:core:ui` 的 `Route` 里加类型，自己模块里写 `NavGraphBuilder.xxxGraph()`
6. `app/build.gradle.kts` 加依赖，`AppNavHost` 加一行注册

> 实体集中放 `:core:database` 而不是各 feature，是刻意的（与 PRD 4.7.1 有偏差）：
> Room 的 `@Database` 需要编译期拿到完整实体列表，
> 坚持分散会让 `:core:database` 反向依赖所有 feature，依赖方向就乱了。

### 写迁移 SQL 的正确姿势

手写的 `execSQL` 必须和 Room 生成的建表语句**逐字符一致**（反引号、`NOT NULL` 位置、索引名），
差一个字符 Room 启动时的 schema 校验就崩。

验证方法：改完实体先编译一次，Room 会把新版本导出到
`core/database/schemas/<版本>.json` 的 `createSql` 字段，拿它比对。

## 五、已经踩过的坑（别再踩一遍）

### 1. `letterSpacing` 绝不能用 `.em` ★ 这个坑崩掉过整个 App

`Type.kt` 里所有 `letterSpacing` / `fontSize` **一律用 `.sp`**，且 15 个排版样式必须全部显式定义。

原因：`OutlinedTextField` 的 label 聚焦时会在 `bodyLarge` 与 `bodySmall` 之间做 `TextStyle.lerp`，
而 lerp **无法在 Em 与 Sp 之间换算**，直接抛：

```
IllegalArgumentException: Cannot perform operation for Em and Sp
    at androidx.compose.ui.text.TextStyleKt.lerp
    at androidx.compose.material3.internal.TextFieldImplKt$CommonDecorationBox
```

后果是**每一个带 label 的输入框一进页面就崩**。编译期查不出，Preview 里也未必触发（要聚焦才插值）。
`TypographyTest` 已经把规则钉死，改 `Type.kt` 后务必跑 `:core:designsystem:testDebugUnitTest`。

### 2. Material 3 Expressive 需要**两个** opt-in 开关

`MotionScheme` 在 `material3 1.4.0-alpha13` 里已经有了，但需要
`ExperimentalMaterial3ExpressiveApi`，它和 `ExperimentalMaterial3Api` 是**两个独立开关**，
只开后者会报「This material3 API is experimental」编译错误。
已统一加在 `build-logic` 的 `configureKotlinAndroid` 里。

（顺带纠正一个常见误解：`1.4.0-alpha13` 在语义化版本里排在 `1.4.0` **之前**，alpha 是预发布。）

### 3. Kotlin 不对跨模块的 public 属性做智能转换

```kotlin
// ❌ 编译不过：dueAt 是 :core:database 里的 public 属性，
//    Kotlin 无法保证对方不是自定义 getter
isOverdue = dueAt != null && dueAt < now

// ✅ 先取到局部变量
val due = dueAt
isOverdue = due != null && due < now
```

### 4. `rememberSwipeToDismissBoxState` 的回调只捕获一次

`confirmValueChange` 在创建 state 时捕获闭包，直接传回调会永远拿到第一帧的旧引用。
必须用 `rememberUpdatedState` 包一层。参考 `TodoListScreen.kt` 的 `SwipeableTodoRow`。

另外 `confirmValueChange` **一律返回 `false`**：让数据流去驱动列表变化，卡片滑回原位。
返回 `true` 会让条目停在「已划走」状态，撤销恢复后位置就错了。

### 9. Room 2.7+ 不允许 `@TypeConverters` 与 `addTypeConverter()` 双重注册 ★ M3 上线即崩

`Converters` 类只要无依赖，`@TypeConverters(Converters::class)` 注解在 `MyAppDatabase` 上时 Room 会自动用 no-arg 构造实例化它。M3 阶段曾同时存在两套注册（注解 + `DatabaseModule` 里的 `.addTypeConverter(Converters())`），Room 2.7+ 在运行时直接抛：

```
IllegalArgumentException: Unexpected type converter com.myapp.core.database.Converters@...
Annotate TypeConverter class with @ProvidedTypeConverter annotation or remove this converter from the builder.
```

M3 上线时只跑了 `:core:database:assembleDebug` 编译通过就发了，没在真机上 `am start` 过，这条崩溃路径一直没被触发。M4 实施时第一次启动直接红屏，回溯排查才挖出来。

**最终修法**：只保留 `@TypeConverters(Converters::class)` 注解，删掉 `addTypeConverter(Converters())` 调用。`@ProvidedTypeConverter` 是给有依赖、需要 Hilt 注入的 Converter 用的，本项目 `Converters` 无依赖不需要。

教训：编译过 ≠ 跑得起来，Room 的 TypeConverter 校验是运行时检查；任何数据库改动必须真机 `am start` 一次，不能只看 `assembleDebug` 绿了就发。

### 10. Haze 1.5.0 + `Scaffold.bottomBar` 不兼容 ★ 底栏毛玻璃直接失效

`Scaffold` 的 `bottomBar` slot 把底栏和 content 摆成兄弟节点，两者 bounds 不交叠。
Haze 的工作原理是 `hazeSource` 贴在内容上采样像素、`hazeEffect` 贴在底栏上读采样结果--
**两者必须在同一父容器里、bounds 交叠**，兄弟节点采样不到。

**必须放弃 `Scaffold.bottomBar` slot，改用 `Box` 叠层**：`AppNavHost`（带 `hazeSource`）
在底层占满，`MyAppBottomBar`（带 `hazeEffect`）叠在上方 `Alignment.BottomCenter`。
这样底栏的 bounds 完全覆盖在内容之上，Haze 能正确采样。FAB 同理叠在最上层。
参考 `app/src/main/kotlin/com/myapp/ui/MyApp.kt`。

### 11. Haze 1.5.0 的 `HazeStyle` 必须传 `backgroundColor` ★ 运行时崩溃

`HazeStyle` 的 `backgroundColor` 参数在 1.5.0 里是必填的，不传会在运行时（第一次 draw 时）抛：

```
IllegalStateException: backgroundColor not specified. Please provide a color.
    at HazeEffectNode.drawEffectWithGraphicsLayer
```

编译期查不出。`HazeStyle` 还有**两个构造函数重载**，签名很像：
- `(backgroundColor, tints: List<HazeTint>, ...)`
- `(backgroundColor, tint: HazeTint?, ...)`

只传 `backgroundColor + blurRadius` 时会触发**重载歧义**，Kotlin 解析不出该用哪个。
显式传 `tints = emptyList()` 选 List 版本，或传 `tint = HazeTint(...)` 选单值版本。
本项目 `MyAppBottomBar` 用 `tint = HazeTint(surfaceColor.copy(alpha=0.6f))`，
`MultiActionFab` 的遮罩用 `tints = emptyList()`（纯遮罩不需要 tint）。

### 12. `toRoute<Route>()` 不支持 sealed interface Route ★ 导航匹配崩溃

`Route` 是 `@Serializable sealed interface`，子类是 `@Serializable data object`/`data class`。
`NavController.currentBackStackEntryAsState()` 拿到 entry 后，`entry.toRoute<Route>()`
内部用 kotlinx.serialization 多态解码，会抛：

```
SerializationException: Polymorphic value has not been read for class null
```

**必须改用字符串匹配**：

```kotlin
val currentRouteStr = currentEntry?.destination?.route
val topLevelDest = currentRouteStr?.let { str ->
    TopLevelDestination.entries.firstOrNull { dest -> str == dest.route::class.qualifiedName }
}
```

`destination.route` 是类型安全导航生成的全限定类名（如 `com.myapp.core.ui.navigation.Route$Home`），
和 `dest.route::class.qualifiedName` 比较即可。过渡瞬间 `currentRouteStr` 可能为 null，
判空兜底（默认隐藏底栏与 FAB）。

### 13. 跨页面传值不要用 `previousBackStackEntry.savedStateHandle` ★ M5 记账 Snackbar 静默失效

官方文档「返回结果给上一页」的套路是编辑页 `previousBackStackEntry?.savedStateHandle?.set(key, value)`、
列表页 VM 注入的 `SavedStateHandle` 用 `getStateFlow(key)` 观察。**M5 记账真机实测这个方案会静默失效**：

- 现象：`set()` 执行成功（日志确认 prev 就是 Route.Ledger 的 entry、handle 非空），
  但列表页 VM 的 `getStateFlow` 永远收不到值，`LaunchedEffect` 一直拿到 null，Snackbar 不弹。
- 根因：`previousBackStackEntry.savedStateHandle` 与列表 VM 注入的 `SavedStateHandle`
  **不是同一个对象**（日志打印两个 handle 的 identity 不同）。进程被系统回收后恢复导航状态、
  以及底部 tab 的 `saveState/restoreState` 组合，会让同一个 `Route.Ledger` 在栈上出现
  **多个 NavBackStackEntry 实例**，各自持有独立的 SavedStateHandle。值写进了「另一个」handle。
- 修法：改用**进程内单例 Channel 事件总线**（`feature/ledger/data/LedgerSaveEvents.kt`，
  `@Singleton` + `Channel<Long>(BUFFERED)` + `trySend`），与 entry 身份完全无关。
  编辑页经 `EntryPointAccessors.fromApplication` 拿单例 `publish(amount)`，
  列表 VM `init` 里 `collect`。`Channel.BUFFERED` 无订阅者也能缓冲，等列表回来再收。
  （`MutableSharedFlow(extraBufferCapacity)` 不行——零订阅者时 `trySend` 直接丢。）
- 全局 FAB 从首页进编辑页时 `previousBackStackEntry` 是 Home：按 `prev.destination.route`
  判断只对 `Route.Ledger` 发布，首页不需要 Snackbar，保持原预期行为。

### 14. `getLongExtra` 对 Integer extra 静默抛 ClassCastException ★ 深链首次测试失效

`intent.getLongExtra(key, -1L)` 在 Bundle 里存的是 `Integer`（如 `adb shell am start --ei`）
时**不返回 -1，而是抛 ClassCastException 被 Bundle 内部吞掉**，logcat 只留一行
`W Bundle: Key ... expected Long but value was a java.lang.Integer`，调用方拿到默认值 -1，
看起来像「extra 没传进来」。通知 PendingIntent 用 `putExtra(key, Long)` 不会触发，
但深链是外部输入边界（adb 测试、未来其他入口），读法要兼容两种类型：

```kotlin
val id = intent?.extras?.get(key).let { raw ->
    when (raw) {
        is Long -> raw
        is Int -> raw.toLong()
        else -> return
    }
}
```

### 15. 微信 App 在前台时转账/支付不发系统通知

微信在**前台**时支付成功只弹应用内消息，不投系统通知，NotificationListenerService
收不到（真机验证：用户连转两笔 0.01 / 6.66 均无落库）。**扫码支付**（扫个人/商家
收款码）成功后切后台，微信才发「微信支付凭证」通知。聊天转账基本不发通知，

### 16. 白名单按包名过滤拦不住微信聊天消息 ★ 未识别队列被污染

白名单只查包名，微信的普通聊天通知（标题=联系人名，正文=消息）也会进监听器，
解析失败全部进未识别队列，未识别屏被聊天记录刷屏。修法：`PaymentParser.isLikelyPayment`
预过滤——标题+正文含 `¥` / `数字+元` / 支付动词（支付/付款/收款/到账/转账/入账/退款/
支出/消费/扣款/凭证/交易）才处理，否则直接忽略。注意「元」作为关键词太宽泛
（「一元复始」会误判），所以用正则 `\d+(?:\.\d{1,2})?\s*元` 匹配「数字+元」整体，
不用裸「元」字。

### 17. Glance 1.1.1 的 API 和官方文档示例（多为 1.2+）差很多 ★ 小组件编译反复失败

glance-appwidget 1.1.1 里：**没有** `androidx.glance.unit.dp/sp`（要用 compose 的）、
**没有** `weight(f)` / `fillMaxWidth(fraction)`（只有 `defaultWeight()`，且是 RowScope/
ColumnScope 成员，子 Composable 要当参数传进去）、`ColorProvider` 是 `androidx.glance.unit`
下的**接口**（工厂在 ColorProviderKt）、`Box` 的 content **没有默认值**（空 Box 要写
`content = {}`）、`Text` 没有 textAlign/overflow 参数（textAlign 走 `TextStyle`）。
进度条用「定宽轨道 + 按比例填充」的 Box 模拟。改代码前先 `javap` 缓存里的 AAR 确认 API，
别信文档。

### 18. `Intent(context, "com.xxx.MainActivity")` 是 ACTION 构造器 ★

Glance 小组件不能依赖 `:app`（PRD 4.7.1），按类名启动 MainActivity 时**不能用**
`Intent(context, String)`（那是 ACTION 构造器），要 `Intent().setClassName(context, ...)`。
同理小组件点击的 data URI 用 `myapp-widget://open/$screen` scheme 区分目标页，
避免固定 requestCode 下 extras 互相覆盖。

### 19. Glance 的 `updateAll` 是 suspend 函数

BroadcastReceiver 的 `onReceive` 不是协程环境，直接调 `updateAll` 编译报错。
用 `goAsync()` + `CoroutineScope(Dispatchers.Main).launch` 包起来，finally 里
`pendingResult.finish()`（见 `WidgetAlarmReceiver`）。

### 20. `LocalDate.toEpochMilliAtStartOfDay()` 会把时分秒盖成 00:00 ★ 记账时间 bug

`AppTime` 里 `LocalDate.toEpochMilliAtStartOfDay()` 返回的是**当天零点**的 epochMilli，
用来「指定某一天」时是对的。但 `LedgerEditScreen` 的「今天 / 昨天」快选和 DatePicker 确认
都拿它去覆盖 `occurredAt`--`occurredAt` 默认值是 `AppTime.now()`（带当前时分秒），
被它一盖就成了当天 00:00，列表页 `toLocalTime().format("HH:mm")` 自然显示 `00:00`。

用户场景里这是必现 bug：默认就是今天，用户看到「今天」chip 没高亮（旧实现 `selected = false` 永远），
下意识点一下「确认是今天」，时间就被清零。

**修法**：换日期时**只换日期保留原时分秒**：

```kotlin
val occurredTime = with(AppTime) { occurredAt.toLocalDateTime().toLocalTime() }
val newMillis = with(AppTime) { targetDate.atTime(occurredTime).toEpochMilli() }
viewModel.updateOccurredAt(newMillis)
```

附带把 chip 的 `selected` 改成反映 `occurredAt.toLocalDate()` 与今天/昨天的比较，
让用户看见默认就是今天，不必再点。日期下方文本同时显示 `yyyy年M月d日 HH:mm`，
时间不对能立刻发现。

普适规律：**`toEpochMilliAtStartOfDay` 只适合「只关心日期不关心时刻」的列**
（纪念日、经期起止、预算周期边界）。涉及具体时刻的字段（`occurred_at`、`due_at`、
提醒触发时间）换日期时必须保留原 `LocalTime`，否则会把真实时刻静默清零。

### 21. 顶级页面的列表底部必须加 `LocalBottomBarHeight` ★ 设置页「关于」被底栏挡住

底栏 `MyAppBottomBar` 不是任何 Scaffold 的 `bottomBar`，而是 `MyApp.kt` 里
**浮在 `Box` 上的覆盖层**（`Modifier.align(Alignment.BottomCenter)`）。
所以各页面自己 `Scaffold` 给出的 `innerPadding` 里**根本没有底栏的高度**，
`innerPadding.calculateBottomPadding()` 只有系统导航栏那点 inset（几十 dp），
而底栏实际高度是它的好几倍。

后果：列表最后一两项被底栏盖住，看起来像「划不下去」。
`SettingsScreen` 就是这么中招的——条目从 7 个加到 8 个（新增「云备份」）之后，
最后的「关于」整个看不见了。

正确写法（`BudgetScreen` 一直是对的，抄它）：

```kotlin
contentPadding = PaddingValues(
    bottom = LocalBottomBarHeight.current + Spacing.xxl,
)
```

`LocalBottomBarHeight` 是底栏 `onGloballyPositioned` 实测出来的高度，
且 `MyAppBottomBar` 内部已经 `windowInsetsPadding(WindowInsets.navigationBars)`，
**导航栏 inset 已经含在里面了，不要再叠加 `innerPadding.calculateBottomPadding()`**，
否则底部 inset 会算两遍、凭空多出一块空白。

判断依据：这个页面是不是 `TopLevelDestination`（底栏可见）。
是就必须处理，二级页面（有返回箭头的）不显示底栏，不用管。

### 22. 一行里塞太多固定宽度图标会把 `weight(1f)` 压成 0 宽 ★ M6 列表标题整个不可见

`KnowledgeSourceRowItem` 原来把「标题/URL 的 `Column(Modifier.weight(1f))`」和
「编辑/置顶/上移/下移/启停 5 个固定宽度图标」放在**同一个 `Row`** 里。
这 5 个图标加起来已经超过卡片可用宽度，`weight(1f)` 拿到的剩余空间是负的 → 被夹成 **0 宽**，
标题和 URL 整个不渲染。

排查时极具迷惑性：不是颜色问题、不是文字为空，`uiautomator dump` 里也**什么都看不到**；
标题长短、是否为空都会中招，看起来像「数据没读出来」。

- **Compose 编译期和 Robolectric 都测不出来**——要有真实宽度约束才会发生
- 修法：拆两行（第一行状态图标 + 标题/URL 占满宽度；第二行操作图标 `Arrangement.End` 右对齐），
  并给文本加 `TextOverflow.Ellipsis`
- 普适规律：**一行里超过 3 个固定宽度元素时，就不要再指望 `weight(1f)` 还有空间**。
  `:feature:feed` 的订阅源列表一开始就按两行写，没复现

### 23. `disallow-doctype-decl` 是 Xerces 专属 feature ★ 真机上所有 RSS 源一律拉取失败

`RssFeedParser` 用
`setFeature("http://apache.org/xml/features/disallow-doctype-decl", true)` 做 XXE 防护。
**桌面 JDK（单测环境）认识这个 feature，Android 真机自带的 Apache Harmony 实现不认识**，
`setFeature` 直接抛 `ParserConfigurationException` → 所有订阅源 100% 拉取失败。

单测全绿、真机必现。改用三个 Android/JDK 都支持的通用 feature 达到同等防护：
`external-general-entities` / `external-parameter-entities` / `load-external-dtd` 全设 false，
且 `setFeature` 调用包一层 `trySetFeature` 静默容错。

> 这和坑 #22、坑 #9 是同一个教训的三个变体：**桌面 JDK / 编译期 / Robolectric 都会掩盖
> Android 专属问题**。任何碰 XML 解析、WebView、布局约束、Room 运行时校验的改动，
> 单测绿不代表能跑，必须真机走一遍。


### 24. 覆盖安装会丢通知监听绑定，而权限开关仍显示已开启 ★ 自动记账静默失效好几天

**现象**：支付宝付款完全没有自动记账。系统设置里「通知使用权」的开关看着还是开的，
`NotificationManagerCompat.getEnabledListenerPackages` 也返回已授权，但一条通知都收不到。

**怎么定位到的**（这条路径值得复用）：
先查 `adb shell dumpsys notification`——服务出现在
「All notification listeners **enabled**」列表内，却**不在「Live notification listeners」列表内**。
再 dump 出 DataStore 里的未识别队列，发现是**空的**：如果通知送到了 App，
那条「你有一笔5.00元的支出」要么被通用兜底规则记成账、要么进未识别队列，两样都没有
＝ 通知从来没到过 App。到这里就能确定不是解析规则的问题。

**根因**：每次 `adb install -r`（或应用商店更新）都会断开旧的 listener 绑定。
标准 Android 会自动重连，ColorOS 不会。我们这几天反复覆盖安装，所以它一直是断的。

**修法**：
- `MyApplication.onCreate` 调一次 `PaymentNotificationListener.ensureBound(this)`，
  内部是 `NotificationListenerService.requestRebind(ComponentName)`——
  这就是 Android 为这个场景提供的 API，幂等，未授权时 no-op。
- 服务在 `onListenerConnected` / `onListenerDisconnected` 里把真实连接状态写进
  `core/common/keepalive/NotificationListenerConnection`（放 core 是因为写入方在 ledger、
  读取方在 settings，两个 feature 不能互相依赖）。
- 保活自检页与设置页读**连接状态**而不是授权状态，「已授权但未连接」单独报未通过，
  并写明唯一有效的手工解法：把通知使用权关掉再打开一次。

> **教训比修法重要**：「已授权」推不出「能收到通知」。只查授权的自检会永远显示「已通过」
> 而功能是死的——这比没有自检更糟，因为它给了错误的安全感。
> 任何「系统把回调给我们」的能力（listener / accessibility / device admin）都要
> **让被调用方自己上报活性**，不要用「权限查询」代替。

已验证：修完之后再做一次全新的 `install -r`，服务立刻出现在 Live 列表里。

### 25. 规则编辑器的预览把通知标题写死成空串 ★ 预览永远说规则是错的

`RuleDetailScreen` 里：

```kotlin

//                                 ^^ 标题写死空串

而 `PaymentParser.parse` 的匹配第一步就是「标题必须包含全部关键词」。

用户面对的是一个说谎的预览，自然会觉得「写完不知道对不对」——

> 顺带：`RuleMatchDiagnosis` 的复查顺序必须与 `PaymentParser.parse` 一致，

### 27. Gradle 构建缓存能产出「编译成功但 App 类全丢」的 APK ★ 一装就闪退，看着像代码 bug

现象：`assembleDebug` BUILD SUCCESSFUL，`install -r` Success，一启动就退回桌面，
`logcat -b crash` 里是

```
Unable to instantiate application com.myapp.MyApplication:
ClassNotFoundException: Didn't find class "com.myapp.MyApplication"
```

排查路径（照着走一遍最快）：

1. 解包 APK，`dexdump <每个 classes*.dex> | grep 'Class descriptor'` 找这个类。
   **注意别用「在 dex 里搜字符串」的偷懒办法**——`Lcom/myapp/MyApplication;` 作为
   *被引用的类型* 也在字符串表里，搜得到不等于**定义**在里面。这一步我先搜字符串，
   得到「类在 classes18」的错误结论，白绕了十几分钟。
2. 真相是 `:app` 自己的 Kotlin 类**根本没进 APK**，dex 里只有 Hilt 生成的
   `MyApplication_GeneratedInjector` 之类。
3. 往回看中间产物：`app/build/tmp/kotlin-classes/debug/com/myapp/MyApplication.class` **在**，
   但 `app/build/intermediates/classes/debug/transformDebugClassesWithAsm/dirs/com/myapp/` 下**只有生成类**。
   即 ASM transform 那一步的输出是残缺的——而它被 Gradle 从**构建缓存**里恢复了
   （`:app:clean` + assembleDebug 只花 15 秒就是线索：清了 build 目录也没重编，全是缓存命中）。

解法：`:app:clean :app:assembleDebug --no-build-cache`。这次修完 APK 从 98MB 变 83MB，
类齐了，装上就正常。

> 教训：**「编译通过 + 安装成功」证明不了 APK 是完整的。** 装完必须真的启动一次；
> 闪退时先看 `logcat -b crash`（普通 `logcat -d` 里翻不到，会被系统日志淹没）。
> 另外这台设备上 `am start -n .../MainActivity` 有时会假成功（返回 Complete 但进程立刻没了），
> 用 `monkey -p <pkg> -c android.intent.category.LAUNCHER 1` 更可靠。

### 28. KDoc 里写 `filesDir/notes/**` 会让整个文件编译不过

Kotlin 的块注释**可以嵌套**，`/**` 之后再出现一个 `/*`（`notes/` 紧跟 `**` 就凑出了这个序列）
会开一层新注释，于是文件末尾的 `*/` 只关掉内层，报出来的错是莫名其妙的
`Missing '}'` 加 `Unclosed comment`，指的行还离得很远。注释里写路径通配符时避开 `/*`。

## 七、`ReminderScheduler` 已落地

### 实现在哪

  `rescheduleAll()` 真正调用的那一刻，循环就断开了（第一次接的时候踩过这个坑）。
- `core/common/reminder/ReminderAlarmReceiver.kt`：闹钟触发落地点，渲染通知。
  声明在 `core/common/src/main/AndroidManifest.xml` 里（**不在 :app**——提醒能力是 core 层的东西，
  :app 只负责组装，不该反过来知道这个 receiver 的存在，manifest 会自动合并进最终 APK）。
- `core/common/reminder/ReminderModule.kt`：`@Binds ReminderScheduler`。
- 通知小图标 `core/common/res/drawable/ic_reminder.xml`：占位单色剪影，后续可以换正式设计。
- `app/system/BootCompletedReceiver.kt`：`goAsync()` + `ApplicationScope` 协程调 `rescheduleAll()`。
- `app/MainActivity.kt`：首启请求 `POST_NOTIFICATIONS`（API 33+），拒绝也不阻塞——
  提醒闹钟照样注册，只是不弹通知。

### 稍后提醒（PRD 3.3，2026-08-17 落地）

`ReminderScheduler.schedule()` 与 `ReminderRequest` 都加了 `snoozable: Boolean = false`——
默认不影响纪念日/经期两个既有调用方，只有 `:feature:todo` 两处 `schedule()` 调用传 `true`。

- `ReminderAlarmReceiver` 触发时若 `snoozable=true`，往通知上加三个 `NotificationCompat.Action`
  （15 分钟 / 1 小时 / 明天），各自的 `PendingIntent` 打到新增的 `SnoozeActionReceiver`，
  `requestCode = key.hashCode() * 31 + delayMinutes` 保证三个按钮的 PendingIntent 互不覆盖。
- `SnoozeActionReceiver`（`core/common/reminder/`，`@AndroidEntryPoint`）：撤销当前通知
  （`NotificationManagerCompat.cancel(key.hashCode())`），再用 `AppTime.now() + delayMinutes`
  调 `reminderScheduler.schedule(key, ..., snoozable = true)`——复用「同 key 覆盖式重排」的
  既有语义，没有另起一套调度逻辑。「明天」就是 `+24h`，不是「明天固定某个时刻」。
- 已注册进 `core/common/src/main/AndroidManifest.xml`。

真机验证（2026-08-17）：建一条 4 分钟后到期的待办，等真实 `AlarmManager` 触发
（没有用 `adb shell am broadcast -n` 模拟——历史上这条路径在这台 ColorOS 机器上不可靠，
见第五节坑 #M7 相关记录），通知正确带三个按钮；点「15分钟」后通知立即消失，
`dumpsys alarm` 核对新触发时间精确等于点击时刻 + 15 分钟。验证完把测试用的待办删了，
闹钟随之取消，没留测试数据。

### 三个 `ReminderSource` 实现

| Feature | 提醒键 | 触发时机 |
|---|---|---|
| `:feature:todo` | `todo:$id` | `TodoRepository` 实现；`TodoEditViewModel.save()` 里按 `dueAt` 注册/取消；重复任务生成下一条时（`spawnNextOccurrence`）一并注册 |
| `:feature:anniversary` | `anniversary:$id` | `AnniversaryRepository` 实现；`save()`/`delete()` 里注册/取消，触发时间 = `nextDate - remindDaysBefore` 天，当天上午 9 点 |
| `:feature:period` | `period:next`（固定键，只追踪「下一次」） | `PeriodRepository` 实现；`recordStart`/`update`/`delete`/`restore` 后都会重算预测并覆盖式重排，提前天数读 `AppPreferences.periodReminderLeadDays`（默认 2 天，PRD 3.2 默认值，设置页可改），当天上午 9 点提醒 |

`AnniversaryDao` 新增了 `getAllActive()` 一个查询方法（供 `pendingReminders()` 用），
**不是 schema 变更**，没有加字段/加表，不需要新迁移。

## 八、保活自检向导（PRD 9.3）

ColorOS 后台管理是国产 ROM 里最激进的之一，会直接冻结未加白名单的应用，
导致提醒闹钟不响、通知监听失效、小组件不刷新。光有 AlarmManager 不够，
还需要引导用户关闭 OEM 层的后台限制。

### 实现在哪

- `core/common/keepalive/KeepAliveStatusChecker.kt`：检测电池白名单、通知权限、
  精确闹钟、首装判定（`firstInstallTime == lastUpdateTime`）。
- `feature/settings/keepalive/`：向导 UI（Screen + ViewModel + Item 模型）。
- `core/datastore/AppPreferences.kt`：`keepAliveChecked`（完成标志）+
  `keepAliveManualDone`（手动项勾选状态，`stringSetPreferencesKey` 持久化）。
- `app/MainActivity.kt`：splash 挂住读 onboarding 标志，决定 `initialRoute`。
  老用户升级（`!checked && !isFirstInstall()`）直接写 `true` 跳过向导。

### 检测项分四类

| 类别 | 项 | 处理 |
|---|---|---|
| AUTO（自动检测） | 电池优化白名单、通知权限、通知使用权 | API 检测 + 跳转系统设置 / 向导内请求权限 |
| READONLY（只读） | 精确闹钟 | `USE_EXACT_ALARM` 安装即授予，恒通过，只展示 |
| MANUAL（手动引导） | 自启动、后台活动、锁任务 | 无 API，路径文字 + 「我已设置」勾选框 + 「尝试直达」私有 Intent |

通知使用权在 M5 Phase 2 已升级为 AUTO 项：`isNotificationListenerEnabled()` 真实检测 +
「去开启」按钮跳 `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`（注意 action 常量带
`ACTION_` 前缀，拼成 `android.settings.NOTIFICATION_LISTENER_SETTINGS` 在 ColorOS 上
resolve 不到 Activity）。TEXTONLY 类别当前无用例，保留类别定义。

手动项勾选状态持久化到 DataStore--这些代表用户在系统设置里做的物理操作，
不会因为离开 App 就消失，复查时应保持已勾选。

### 首启时序（MainActivity）

1. `installSplashScreen()` 在 `super.onCreate()` **之前**
2. `super.onCreate()`（Hilt 在此填充 `@Inject lateinit`）
3. `appScope.launch` 读 `keepAliveChecked`；若 `!checked && !isFirstInstall()`
   写 `true`（老用户升级免打扰）
4. `splash.setKeepOnScreenCondition { keepAliveChecked == null }`
5. 非首启时请求 `POST_NOTIFICATIONS`；首启由向导内请求，避免同时弹两个框
6. `setContent` 的 `initialRoute` 由 `keepAliveChecked` 决定

### 首启返回拦截

首启时 `KeepAliveCheckScreen` 用 `BackHandler` 拦截系统返回键、隐藏 TopAppBar
返回箭头，防止用户跳过自检。`firstRun` 标志由 `AppNavHost` 根据
`startDestination == KeepAliveCheck` 传入。

### 完成导航

`onKeepAliveComplete` 做 `navigate(Home) + popUpTo(KeepAliveCheck){inclusive=true}`。
首启时栈为 `[KeepAliveCheck]`，popUpTo 后清空再 navigate；复查时栈为
`[Home, Settings, KeepAliveCheck]`，popUpTo 只清 KeepAliveCheck，
`launchSingleTop` 复用栈里已有的 Home。

### 项目内 dev 签名

`keystore/debug.keystore` 提交到仓库，`app/build.gradle.kts` 里 debug 和 release
统一用它签名。换电脑不再因 `~/.android/debug.keystore` 漂移导致无法覆盖安装。
`.gitignore` 里 `*.keystore` 忽略所有 keystore，但 `!debug.keystore` 放行这一个。

- 首次安装（uninstall + install）-> 进向导，不进 Home ✅
- 系统返回键被拦截，不退出 App ✅
- 老用户升级（保留数据 install -r）-> 跳过向导进 Home ✅
- Home 齿轮 -> Settings -> 保活自检，复查路径可达 ✅

## 九、各模块的关键设计决定（改代码前先看这里）

### `:core:common` — 农历

`LunarCalendar.kt`：自己实现的 1900~2100 查表换算，离线、零依赖。

**改那张 `LUNAR_INFO` 表之前先跑 `:core:common:testDebugUnitTest`。**
测试覆盖 40 个已知春节日期、13 个已知闰月，以及**全范围逐日往返校验**
（公历→农历→公历 必须严格相等，7 万余天）。

农历算错了 UI 照样显示一个像模像样的日期，肉眼根本看不出来，只能靠测试守。

两个必须容错的边界（不处理的话农历生日每隔几年就「消失」一次）：
- 当年没有对应闰月 → 退回同月份的平月
- 生日是三十而当月只有 29 天 → 落到当月最后一天

### `:core:database` — 日期怎么存

- 只有「日」语义的列（纪念日、经期起止）存 **epochDay**
- 有真实时刻的列（待办截止时间、各种 `*_at`）存 **epochMilli**

存毫秒表示纯日期会带上一个假的时刻，跨时区或夏令时时可能整体偏一天。

全局字段约定（为将来同步预留，现在就要有，后补代价极大）：
`uuid` / `created_at` / `updated_at`，需要软删除的表另加 `deleted_at`。
软删除还有个免费的好处：撤销删除是无损的。

### `:feature:todo` — 参考实现

新增 feature 照抄这个模块的目录结构：`data/` `list/` `edit/` `home/` `navigation/` `ui/`。

- 新建与编辑**共用一个页面**，`id = 0` 表示新建，不值得为此多一条路由
- 重复任务完成后生成**新条目**而不是改旧条目日期，这样「已完成」视图能看到完整历史
- 下一次从**原定截止时间**推算，不是完成时间——否则拖延几天会把整条链往后推
- 保存走**读改写**而非整体 REPLACE：`uuid` / `createdAt` / `done` 不属于表单，
  整体构造会把它们悄悄清掉（uuid 丢了将来同步就对不上）
- **完成动作有三层 API**（2026-08-12 主页交互改造后）：`TodoToggleWriter.setDone(id, done)`
  跨模块契约（widget 用，签名永不动）-> 内部分流到 `TodoRepository.complete(id, note)`
  （主页带备注完成）或私有 `uncomplete(id)`（撤销完成）。`spawnNextOccurrence` 只在
  `complete` 里调，所以 widget 简单 toggle 也最终走到这条，重复任务生成下一次的行为不会
  分叉。`uncomplete` 必须清空 `completionNote` + `doneAt`，否则下次再完成时旧备注会残留。
  Kotlin override 不能加默认参数，所以「带备注的完成」必须开新方法，不能给 `setDone` 加
  `completionNote: String? = null` 参数。

### `:feature:anniversary`

- 重复类型存字符串不存枚举（`ONCE` / `YEARLY` / `CUMULATIVE`），加新类型不用做迁移
- 农历纪念日：`date` 列存**用户输入那天的公历日期**，农历月日在读取时换算。
  只需一个日期字段，用户切换公历/农历也不用重新输入
- 排序在**内存里**做不在 SQL：排序键要经过农历换算与「每年重复」推算，写不成 SQL 表达式。
  几十条的量级，代价可忽略
- 累计型的下一个里程碑：**整百天与周年取更近的那个**。
  只倒数整百天会漏掉「三周年」，只倒数周年会错过「在一起 1000 天」
- 置顶是**单选**，写入后统一收敛，避免出现两条置顶

### `:feature:period`

预测算法刻意保持简单（PRD 3.2 V1）：`下次开始 = 最近一次开始 + round(近 6 次周期均值)`。
不做加权、不做复杂建模——样本量本来就只有个位数，复杂模型只会放大噪声，
却让用户以为结果更准。

三处加固（都有测试覆盖，`PeriodPredictionTest` 9 条）：

1. **「进行中」设 15 天上限**。忘记点「结束」远比经期真的持续半个月常见，
   不设上限的话一次漏记会让首页永远显示「经期第 87 天」
2. **可靠性阈值比 PRD 下限严一档**：要求至少 3 个间隔才算 `reliable`。
   只有 1 个间隔时「平均」就等于那一次本身，把单次波动原样当预测，仍然该提示「样本不足」
3. 剔除 10~90 天之外的异常间隔（补录历史时录错年份的典型症状）

日历上**实际记录用实心色块、预测用虚线圈**——这两者绝不能长得像，
否则用户会把预测当成已发生的事实。

**每日异常记录 + 周期分期（PRD 3.2，2026-08-14 新增）**

- **`period_day_log` 是独立的一张表，不挂在 `period_record` 下面**：排卵期出血、经期之外的
  异常同样要能记，挂在「某一次月经」下面这些日子就没地方放。两张表靠日期在 UI 层对齐。
  日期上有唯一索引，一天一条，重复记录就是覆盖。
- **标签存 id 不存文案**（`DayLogTag.id`）：id 一旦发布就不能改，改文案只动 `label`。
  认不出的 id 在 `parse` 时直接丢弃，降级安装或将来删标签都不会崩。
- **V1 不做自定义标签**：标签是「可统计」的那一半，开放自定义之后同一件事会被写成五种说法，
  统计立刻失去意义；写不进标签的情况有自由文本兜底。
- **标签与文本都空 = 删除这一天**，不留空记录（月历上会多一个什么都点不出来的标记）。
- **分期口径是「下次预计开始日 − 14 天」，不是周期中点**（`CyclePhases.kt`，纯函数、13 条测试）。
  中点法在周期偏长时错得离谱：35 天周期会算到第 17.5 天，实际大约在第 21 天。
  易孕窗口是排卵日**前 5 天到后 1 天**（往前开是因为精子存活期）。
- **`reliable == false` 时 `computePhases` 直接返回 null，月历什么都不画**，
  只在下面写一句「样本不足，暂不推算排卵期」。分期是从预测倒推的，预测不准分期只会更不准，
  画一个没依据的排卵日比不画更糟——用户可能拿它当避孕依据。页面上另有一句明确的免责。
- **经期还进行中（没点结束）时不给卵泡期**：没有结束日就没有起点，拿开始日凑一个
  会把经期本身算进卵泡期。
- **月历不能只靠颜色区分**（深色模式 + 色觉障碍）：排卵日 = 浅底 + **实线圈**，
  易孕期 = 浅底，黄体期/卵泡期 = 数字下方**细横线**（深浅不同），今日记录 = **右上角**小点
  （刻意与「今天」的底部圆点错开位置）。黄体期与卵泡期不铺底色——整月铺满会变成一张色块图，
  反而看不出经期在哪；「今天在哪一段」由状态卡的一行文字补上。

### AI 分析（PRD 3.14，2026-08-14）

全 App 第二个联网依赖（第一个是云备份），也是**唯一一处把用户手写的私密文字送出设备**的地方。
所有设计决定都围着这一点转。

**落点**：`:core:network/deepseek/`（客户端、DTO、峰谷判定）+ `:feature:period/data/PeriodAiPrompt|PeriodAiRepository`
（业务编排）+ `:feature:period/ui/PeriodAiCard`（展示）+ `:feature:settings/ai/`（开关与 key）。
**没有抽 `:core:ai`**：只有一个使用者，抽出来会得到一个假抽象（同云备份那次 `SyncProvider` 的教训）。

- **`SecretStore` 从 `:feature:settings` 挪到了 `:core:common/security/`**。写入方是设置页、
  读取方是 DeepSeek 客户端，两个 feature 不许互相依赖，公共密钥仓库只能放 core 层。
  挪的时候**没有改 `PREFS_NAME` 与 `KEY_ALIAS`**——它们决定落盘文件名与 Keystore 别名，
  一改就等于把用户已存的云账号弄丢。`:core:network` 对 `:core:common` 的依赖也顺势从
  `implementation` 改成了 `api`：`DeepSeekClient` 的构造参数里有 `SecretStore`，
  而 Hilt 的组件代码是在 `:app` 里生成的，那边必须能看见这个类型。
- **`SecretStore` 增加了 `revision: StateFlow<Int>`**（每次写入/清空自增）。密钥本身不能做成 Flow
  （那等于把明文一路传下去），但「存没存」必须能响应式观察——**这是真机上抓到的 bug**：
  在设置页填完 key 返回经期页，那边的 ViewModel 没被销毁，一次性快照让卡片一直显示
  「还差一个 API Key」，看起来就像保存没生效。
- **走 Responses API（`/responses`）而不是对话补全**。这是查官方文档后对 PRD 的修正：
  `/chat/completions` 的 `tools` 只支持自定义 function，服务端执行的内置 `web_search`
  只有 Responses API 有。联网搜索是硬需求，接口选型跟着它走。
  请求体 `tools: [{"type": "web_search"}]`。
- **超时用 `callTimeout` 而不是 `readTimeout`**。后者管的是两个数据包之间的间隔，
  模型慢吞吞地吐字时永远不会触发；要的是「整次调用 30s 封顶」。客户端由共享的 OkHttp
  `newBuilder()` 派生，复用连接池，不是新开一个。
- **失败不重试**。用户正盯着屏幕等，静默重试只会把 30s 变成 60s（PRD 明确要求）。
  失败分 5 类给不同文案，**其中「鉴权失败」这条绝不能带上 key 本身**；
  HTTP 非 2xx 时也不把响应体原样带进 UI——它可能回显请求内容，而请求里全是私密记录。
- **`PeriodAiPrompt` 是纯函数且有 11 条测试**。「到底发了什么出去」不能靠读一遍调用链去推断，
  必须能被测试钉死。只发近 6 次经期 + 这段时间内的日记录，更早的不发（对最近的节律没有
  解释力，发出去只是白白多暴露一段隐私）；不发姓名、设备号、账号。
- **指纹不含 `today`**。指纹用来实现「数据没变就不重复调用」，若把当天日期算进去，
  这条会在每天零点自动失效，等于没有缓存。想要一份新的解读时走「强制刷新」按钮。
  用 SHA-256 而不是 `hashCode()`：后者只有 32 位且不保证跨版本稳定，撞一次的后果是
  「明明改了记录却拿到旧结论」。
- **峰价拦截在 UI 层，不在仓库层**。拦截需要用户二次确认，是 UI 决策；仓库层认「叫我发我就发」，
  否则会出现「ViewModel 以为发了、仓库偷偷没发」这种最难查的状态。
  峰谷窗口是 UTC 小时的**左闭右开**区间，只写在 `DeepSeekPricing.PEAK_WINDOWS_UTC` 一处。
  提示语里带「几点转谷价」：只说「现在是峰价」而不给出口，只是在制造焦虑。
- **总开关兼知情同意，默认关闭**，开启动作固定绑一个说明弹窗（关闭则不弹，随时可关）。
  **关闭时连缓存的分析结果一起清掉**——留着一段用私密数据换来的文字，与用户「我不想再用了」
  的意思相悖。清空 key 时同理。
- **结果缓存在 DataStore 不在 Room**：一段随时可重新生成的派生文本，没有查询/关联需求，
  为它开一张表和一次迁移不划算。请求正文与原始响应都不落盘，只存最终那段文字。
- **模型 id 是代码常量，不是用户可配项**（对 PRD 原文的第二处偏差）。给自用 App 加一个
  「随便填模型名」的输入框，填错的代价（一次 400 + 一头雾水）高于它省下的那次改代码。
  「是否联网」倒是做成了设置页开关——联网会额外产生 token 费用且明显更慢，值得留个省钱的口子。
- **系统指令里禁止诊断与用药**，有测试盯着措辞不被顺手删掉。一个自用记录 App 给出
  「你可能是子宫内膜异位症」会造成真实伤害：要么把人吓坏，要么让人拿它当结论而延误就医。
  需要留意时只说「建议找医生看看」。

### `:feature:note` - M3 笔记

- **FTS 用 contentEntity 模式而不是 standalone 表**：`NoteFtsEntity` 通过 `@Fts4(contentEntity = NoteEntity::class)` 关联主表，Room 自动建外部内容表 + 触发器同步主表到 FTS。改 NoteEntity 不需要手动维护 FTS 同步逻辑。搜索时用 `rowid MATCH` JOIN 回主表，不是普通 SELECT
- **Photo Picker 不申请权限**：`PickVisualMedia` 是系统级 Activity，返回的 `content://` Uri 默认只对当前进程有效。要持久化（重启后还能读）必须 `contentResolver.takePersistableUriPermission(uri, FLAG_GRANT_READ_URI_PERMISSION)`，否则重启后 Uri 失效图片就丢。读取时 `BitmapFactory` 配 `inSampleSize` 防 OOM
- **MarkdownRenderer 是纯字符串解析器**：不依赖 Compose，输入 Markdown 文本输出 `AnnotatedString`，可以单测。`NoteMarkdownTest` 14 条覆盖各种语法边界（标题/粗体/斜体/列表/代码块/链接/分割线）
- **撤销删除走 Channel 而不是 StateFlow**：Snackbar 的显示是一次性事件，用 `Channel<UndoEvent>` + `receiveAsFlow()`，避免配置变更后重复弹
- **图片路径列表用 `` (U+0001) 分隔**：ASCII Unit Separator，文件名禁用字符，路径里不会出现，分隔安全。不用 JSON 序列化库，`:core:database` 没引入 kotlinx.serialization，为这一个字段拉依赖不划算

### `:feature:question` - M4 疑问收集箱

### `:feature:ledger` - M5 Phase 3 分类管理 UI（PRD 3.6）

- **三条不变式写在 `CategoryRepository` 的类注释里，改代码前先读**：保留项不可删/停用/改名；
  删除一律软删；改名要同步商户学习映射
- **为什么必须软删**：`TransactionDao` 的 JOIN 是 `INNER JOIN category ON c.id = t.category_id`，
  **不带** `c.deleted_at IS NULL`，所以软删后历史账目照常显示原分类名；真 DELETE 会让
  那些账目从列表里**整行消失**（JOIN 不上）。这是「停用而非删除」设计意图之外的第二道保险
- **改名同步学习映射**：`LedgerPrefsStore.merchantCategoryMap` 的 value 存的是分类**名**
  （`recordExpense` 契约按名查库），改名不同步的话自动记账按旧名查不到，静默落「未分类」。
  `renameLearnedCategory` 在 save 检测到名字变化时调用
- **排序走整表重排不走 `sortOrder ± 1`**：种子灌的是 1..10，用户删几个再加就会跳号，
  算术加减在跳号时会错位。`move()` 取当前顺序算出目标下标后把全表重写成 1..n。

- **重名拦截返回 `CategorySaveResult.DuplicateName` 而不是抛异常**：分类名是 `LedgerWriter`

- **入口有两个**：设置页「分类管理」+ 记账页 TopBar 分类图标（改分类多半是记账时才想起来的）
- **顺手修的 bug**：`LedgerPrefsStore.learnMerchantCategory` 里 `prefs[KEY] ?: return@edit`

  整个学习功能静默失效。改成缺 key 时按空 map 起步
- **真机验证（2026-08-11，realme GT Neo5 SE）**：列表渲染含真实笔数（餐饮 6 笔 / 交通 10 笔）；

### `:feature:ledger` - M5 Phase 3 预算视图（PRD 3.6.2）

- **派生指标全在 `data/BudgetInsights.kt`，是纯函数，`BudgetInsightsTest` 12 条钉死**。
  这些数字用户拿来做花钱决策：显示「日均还能花 ￥120」而实际只剩 ￥30 会直接害人超支，
  比不显示更糟，所以边界一条条测
- **周期天数按日历天算不按毫秒差**：跨夏令时毫秒差会少一小时，整除后可能少一天，
  「还剩几天」必须和日历一致
- **今天算在剩余天数里**（`remainingDays` 最小是 1）：用户今天要花钱，今天的额度还能用。
  按 `total - elapsed` 算会在周期最后一天给出 0，日均可用直接除零
- **匀速理想值按已过天数算不按剩余天数**：周期第 1 天就该允许花掉 1/30，
  用剩余天数算会把周期初的所有人都判成「花得偏快」
- **节奏容差 5%**：差距在预算的 ±5% 内算「节奏正常」。不留容差的话每天都在
  「偏快/偏省」之间跳，警示就失去意义了
- **超支时日均可用返回 0 而不是负数**：「日均还能花 -￥50」没有指导意义，
  超支这件事由节奏卡片单独说
- **`flatMapLatest` 而不是 combine**：预算（含发薪日）变了以后，下游的区间查询要跟着换。
  直接 combine 会一直用第一次算出来的区间——首页卡片 `LedgerCardViewModel` 踩过同样的坑
- **分类汇总的 JOIN 不带 `c.deleted_at IS NULL`**：分类被软删后历史账目仍要统计进来，
  否则删一个分类会让「本期支出去向」的明细和总额对不上（与列表页 JOIN 同口径）
- **`BudgetDialog` 提到 `ui/BudgetDialog.kt` 共用**：记账列表页的齿轮改成跳预算页，
  对话框由预算页持有。两处各写一份的话，改校验规则（如发薪日上限 28）必然漏改一处
- **入口**：记账页 TopBar 齿轮 → 预算页；首页记账卡片没预算时的「设置预算」也直达预算页
- **预算是有版本的**（2026-08-13 补，PRD 3.6.2 历史回顾）：`setBudget` 从「upsert 单行」改成
  「旧行 `effective_to` 落时间戳 + 插新行」。**改之前历史预算从来没被记录过**，
  近 12 期回顾这个功能在数据上就不成立——这类「不做就一直在丢数据」的欠账要优先补，
  晚一天就少一天历史。两步写在 `BudgetDao.replaceCurrent`（`@Transaction`）里：
  中途崩溃会留下「一行生效的都没有」的库，App 会显示「还没设预算」，用户以为预算丢了。
  Room 接受 Kotlin 接口里带默认实现的 `@Transaction` 方法，不必把 DAO 改成 abstract class
- **值没变时直接返回不产生新版本**：打开对话框看一眼就确认是很常见的操作，
  每次都插一行的话历史会塞满一堆内容相同的版本
- **「那一期该跟哪份预算比」取期末**（`BudgetHistoryInsights.budgetForCycle`）：
  取该期结束前最后一次设定的那份。用户中途把预算从 3000 改成 5000，心里的目标就是 5000，
  按期初取会拿到一个他自己都放弃了的数字。**该期开始前一份预算都没有 → 返回 null**，
  这一期不判达成/超支——拿现在的预算去追认当时根本没设过预算的月份，是伪造历史
- **柱高的分母是这 12 期里的最大支出**，不是各期自己的预算：用各自预算当分母的话，
  预算调整过的期之间高度就不可比，而这张图的用途恰恰是横向比
- **12 根柱子只标月份数字**不标「8月」——两个字并排会挤在一起
- **加 DAO 查询不改 schema**：这次只加了 `observeAll`/`closeCurrent`/`replaceCurrent` 三个方法，
  `budget` 表结构一个字段没动（`effective_to`/`effective_from` 建表时就有，一直空着没用），
  所以**不需要迁移**，`schemas/` 无 diff
- **真机验证（2026-08-13）**：改 ￥11000 → ￥12000，库里旧行 `effective_to` 落时间戳、
  新行接上；改回 ￥11000 再原样确认一次，确认只多一行、没有第四行（值没变的去重生效）；
  近 12 期柱状图正常渲染，无崩溃

### `:feature:knowledge` - md 面试题库（PRD 3.7.1，2026-08-14 改版）

用户要求把知识库主体从飞书网页换成打包进 App 的 md 面试题库，飞书降级为只读书签。

**为什么换**：知识库真正要承载的是「随时抽一道面试题复习」。飞书方案依赖网络、
依赖飞书前端 DOM 不改版、正文提取还经常拿不全，用来支撑每日抽题太脆。md 是本地的、
结构确定的、离线绝对可用的。

**内容与版本**：md + 图片放 `feature/knowledge/src/main/assets/interview/<docKey>/`
（`doc.md` + `img/`）。目录名用 ASCII（`backend`/`llm`）而不是中文原名——
源文件叫「火箭🚀.md」，文件名里的 emoji 在打包与跨平台构建里是不必要的风险，
显示名单独放在 `INTERVIEW_DOCS` 里。加一篇新题库 = 放文件 + 加一行 + `INTERVIEW_ASSETS_VERSION` 加一。

**几个关键决定**：

- **切分粒度**：`#` = 章节，`##` = 一道题，`###` 及更深留在答案正文里。
  代码围栏内的一切不参与标题识别（坑 #26，这是最容易把整份题库解析歪的地方）。
- **稳定 key 而不是自增 id**。章节 key = `sha1(docKey|章节标题)`，
  题目 key = `sha1(docKey|章节标题|序号|题干)`。题库文档以后会更新、重新导入，
  自增 id 每次都变，挂在 id 上的「在池状态」和「复习进度」会全部失联。
  重新导入是整篇替换（`InterviewDao.replaceDoc`，一个事务），但按 key 沿用旧的 `in_pool`，
  复习进度存在独立表、本次导入完全不碰它。
  - 题目 key **带序号**是有意的：同一章里题干可能重名（两篇文档里都有若干道
    「场景题」「补充」）。只用标题做 key 会让它们撞成一条，唯一索引一冲突后面那道
    就把前面那道顶掉，**题库凭空少题**。代价是「在某章中间插入一道新题」会让它后面
    所有题的 key 变、复习进度重置——相比「静默丢题」这是可接受的一侧。
- **知识池的开关粒度是章节**，不是题目也不是整篇文档。494 道题一条条勾不现实，
  而「这阵子只复习 Redis 和 Spring」是真实需求，章节这一级刚好。整篇也提供一键全选/全不选。
- **另起 `interview_review` 表而不是给 `knowledge_review` 加类型列**：
  那张表的 key 是飞书知识源的 Long id，面试题的稳定标识是字符串，类型都不一样，
  硬塞进一张表要么加冗余列要么改唯一索引，得不偿失。飞书退出抽题后 `knowledge_review`
  自然停止增长，保留原表只是为了不动已有数据。
- **抽题算法完全复用 M7 的 `KnowledgeReviewSelector`**：那套「没推过的优先、
  之后按 1/3/7/15/30 天到期重排」与知识源无关，是纯粹的调度算法，换个候选集就能直接用。
  `InterviewRepository.pickDaily` 只负责在「题目 id」与「稳定 key」之间翻译一次。
- **正文渲染自己写，不复用 `:feature:note` 的 `MarkdownRenderer`**：
  一是 feature 之间不能互相依赖；二是那个渲染器把所有块拼成一个 `AnnotatedString`，
  没有图片，代码块也只能靠 background span 表现、拿不到块状底色与横向滚动。
  面试题正文里代码块和配图是主要内容，必须按块渲染。
  代码块**不换行、横向滚动**是刻意的——折行之后缩进全乱，比左右滑更难读。
- **图片走 `file:///android_asset/...`**，Coil 原生支持这个 scheme，
  不需要先拷到 filesDir。md 里的 `图片和附件/image%201.png` 在解析时就改写成 `img/image 1.png`
  （换目录 + 解 `%20`）。
- **摘要必须走 `plainTextPreview` 而不是 `body.take(n)`**：直接截原文会把
  `- `、`**` 和换行符原样露在首页卡片上（真机上先犯了一次）。

**飞书这边的处置**：知识源仍可收藏、分组、WebView 阅读、FTS 搜索已缓存正文，
但退出知识池、不再参与抽题，正文提取链路（无头 WebView + JS 注入）随之停用——
那条链路本来就是为抽题提供摘要的。入口从「知识」tab 顶栏齿轮进（`Route.KnowledgeSources`）。

### 云备份（PRD 3.13）

- **建表要走控制台**：CloudBase 的 PostgREST 接口只能增删改查，**DDL 跑不了**。建表 SQL 存在
  `docs/云数据备份.md`；改表后记得 `notify pgrst, 'reload schema'`，否则接口一直 404
  （`DATABASE_PGRST205`）。账号凭证在不入库的 `docs/云数据备份.local.md`（`.gitignore` 加了 `*.local.md`）
- **单表存整份快照，不做逐表镜像**：Room 表结构随迁移一直变，「每张 Room 表镜像一张远程表」
  等于每写一次 Migration 都要同步改远程 schema
- **数据流**：`DatabaseSnapshot`（`core/database/backup/`）→ JSON → GZIP → AES-256-GCM → Base64。
  密钥由「备份密码」经 PBKDF2-HMAC-SHA256（21 万次迭代）派生，**云端只有密文**。
  压缩必须在加密之前（密文是高熵数据压不动）
- **⚠️ 新增业务表时必须去 `BackupDao` 补一组方法**，否则新表不进备份，**且没有任何编译错误提醒**
- **有意不复用各业务 DAO 的 `getAll()`**：它们都带 `deleted_at IS NULL`，会把软删除墓碑丢掉，
  恢复后已删数据会「诈尸」
- **`rss_article` 不备份**（实测后的决定）：它一张表占整份备份的 99.99%——5469 篇文章正文+摘要
  近 8MB，其余 11 张表的全部个人数据合计只有几百字节，而这 5469 篇里只有 1 篇收藏、12 篇已读。
  实测单份备份从 4.2MB 降到 15KB。**但恢复时仍要清空本机 `rss_article`**：`rss_source` 是整表
  覆盖的，留着旧文章会让 `source_id` 指向对不上的源
- **不维护 refresh_token，直接重新登录**：`access_token` 只有 24 小时有效期，而每日备份是无人
  值守任务，醒来时 token 基本都过期了。密码本来就必须存（否则任务无法自愈），多存一个
  refresh_token 没有收益。`username` 用**昵称或邮箱，手机号会被拒**
- **每日一次不是实时同步**：`CloudBackupWorker` + 1 天周期 `PeriodicWorkRequest`；但 ColorOS 会
  冻结周期任务，所以 `MainActivity` 启动时还会查一次「距上次成功备份是否超 24 小时」，
  超了就补一次（`ensureDailyBackup`）。云端只留最近 14 份
- **失败原因写进 DataStore**（`backup.lastError`）：后台失败时没人看着，不落盘的话用户永远
  不知道备份早断了
- **`WorkManager` 的 Hilt 绑定在 `:core:common`**：SingletonComponent 里同一类型只能有一个绑定，
  第二个 feature 用 WorkManager 时会直接编译失败（当初从 `:feature:knowledge` 挪过来的）
- **没有实现 `SyncProvider` 契约**（PRD 4.7.4 已相应更新）：它的 `push()/pull()` 是无参签名，
  装不下「恢复哪一份」「备份密码」，硬套只会得到假抽象
- **要做破坏性验证时的回滚办法**（直接抄）：先把真机 `databases/` 下的 `myapp.db` + `-wal` + `-shm`
  三个文件 `run-as` 拉到本地当底牌，**并先验证过回滚本身可用再动手**，否则等于没有底牌。
  回滚：`adb push` 到 `/data/local/tmp` + `chmod 666`，再
  `adb shell run-as com.myapp.debug cp /data/local/tmp/myapp.db databases/myapp.db`
  （app 私有目录 `adb push` 进不去，但 `run-as` 能从 `/data/local/tmp` 读）
- **两个坑**：① PostgREST 返回的 `created_at` 带时区偏移（`2026-08-13T14:24:03+08:00`），
  `Instant.parse` 只认 `Z` 结尾会抛异常，必须用 `OffsetDateTime.parse`；
  ② **核对行数时必须把 `-wal` 一起拉下来**——只拉 `myapp.db` 单文件会漏掉还在 WAL 里没
  checkpoint 的写入（实测同一时刻单读 db 是 34 笔、db+wal 是 35 笔），差点误判成恢复丢了数据。
  另外用 sqlite3 打开带 `-wal` 的库会触发 checkpoint 把 WAL 合并进主文件并删掉 `-wal`，
  所以「读一下」这个动作本身会改动快照文件

### 本地备份（PRD 4.6，2026-08-14）

代码在 `feature/settings/backup/`（`LocalBackupArchive` / `LocalBackupRepository`，
加解密在 `BackupCrypto` 里跟云备份共处一个文件）+ `feature/settings/localbackup/`（页面）。
入口：设置 → 本地备份。

- **和云备份的分工**：结构化数据两条路共用 `DatabaseSnapshot` 和 `BackupDataSource.restore`
  这条覆盖恢复路径，本地这条只多做两件事——落到用户选的文件（SAF）、**带上 `filesDir/notes` 下的图片**。
  云备份有意不含图片（PRD 3.13 说明了原因），所以**本地导出是笔记插图唯一的迁移路径**。
- **先 zip 再整体加密**，不是 zip 里逐条目加密：后者要么每张图各推一次 PBKDF2（210k 次迭代，
  慢到不能用），要么共用 key 还得自己管 iv；而且整体加密把**文件名**（有几张图、笔记 uuid）
  也一起藏了，那本身也是隐私。归档内容 = `manifest.json` + `snapshot.json` + `files/notes/<uuid>/<图片>`。
- **加密换成分帧**（`BackupCrypto.encryptingStream/decryptingStream`，格式 magic `MYAPZP01`，
  与云备份那条单块的 `MYAPBK01` 区分开）。两个原因，都不是洁癖：
  - 云备份那种「一口气全在内存里」的做法，遇上几十上百 MB 的图片会直接 OOM；GCM 解密天然要
    缓完整份密文才能验 tag，所以必须自己切块。每帧 512KB，内存恒定。
  - `CipherInputStream` 在部分实现上会把 `AEADBadTagException` 当流结束**静默吞掉**，
    那等于「密码错了却返回半截数据」——备份场景里这是最坏的失败方式。所以没用它，自己写。
  - 帧序号与「是否末帧」进 AAD：既防重排，也让**截断的文件一定报错**（缺末帧）。
    对应 `BackupCryptoStreamTest` 里那条「前面的帧都能解开，但仍然拒绝」。
- **恢复顺序不能反**：整份归档先读完并落进 `filesDir/.restore-<ts>` → 事务内覆盖数据库 →
  最后才替换 `filesDir/notes`。中途任何一步失败，本机数据都还是原样。
- **暂存目录放 `filesDir` 而不是 `cacheDir`**：图片最终要 rename 进 `filesDir/notes`，
  同一目录树内 rename 才保留正确的属主/SELinux 标签。第一版放 cacheDir，真机上恢复出来的
  图片带着 `_cache` 组标签（同 uid 仍能读，但没必要留这个隐患）。
- **归档条目名当不可信输入**（Zip Slip）：备份文件在设备之间传递，`files/../../databases/myapp.db`
  这种条目必须拒绝。`LocalBackupArchiveTest` 有专门用例。
- **备份密码不落盘**：它是「这个文件的密码」，与云备份存在 `SecretStore` 的长期密码不是一回事。
- **真机验证（2026-08-14）**：导出「158 条记录、2 张图片（14 KB）」→ 删掉 `files/notes` 模拟丢失 →
  导入 →「已恢复 158 条记录、2 张图片」，图片路径与字节数都对得上。
- **两个真机上才知道的事**：① ColorOS 的保存对话框会把我们建议的 `.myapbk` 扩展名换成 `.bin`
  （MIME 用的 `application/octet-stream`），所以导入侧的 `OpenDocument` 必须收 `*/*`，
  按扩展名过滤会让用户在选择器里根本看不见自己的备份；② 这份备份文件写在 `/sdcard` 上是**明文可见的密文**，
  没有密码打不开，但也别指望它自动过期。
