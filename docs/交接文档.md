## 一、这是什么项目

一个**单人自用的 Android 原生 App**，把日常记录（纪念日 / 经期 / 待办 / 记账）、
个人知识库、行业资讯聚合在一个入口里。

**四条硬约束，任何时候都不能违反：**

| 约束 | 含义 |
|---|---|
| **仅安卓原生** | 不用 Flutter / RN / KMP |
| **无自建服务器** | 所有数据本地，只直连公开网页与 RSS |
| **单人自用，不上架** | 所以 `USE_EXACT_ALARM` 这类 Play 严管权限可以用 |
| **拓展性是一等需求** | 加一个 feature 不该改动已有模块，见第四节 |

另外两条同样重要：

- **数据无云端备份，丢一次就永久没了** → 严禁 `fallbackToDestructiveMigration()`，
  每次改表必须写 Migration 并提交 `schemas/` 下的 JSON。
- **UI 走 Claude 风格**：暖色、简洁、克制。不用纯白/纯黑，层级用 1px 描边不用阴影，
  一屏最多一个 Accent 焦点。

目标设备：**realme GT Neo5 SE**（realme UI 7.0 / Android 16 / 144Hz），
minSdk 35 · targetSdk 36 · compileSdk 36。

## 二、先把环境跑通（有坑）

### 命令行构建的 JDK 是个陷阱

这台机器上有两个 JDK，**只有一个能用**：

| 路径 | 版本 | 结果 |
|---|---|---|
| `C:\Program Files\Android\Android Studio\jbr` | 25.0.2 | ❌ Gradle 8.13 / AGP 8.9 不支持 |
| `C:\Users\cy-10\.jdks\jbr-21.0.11` | 21.0.11 | ✅ |

用错时 Gradle 的报错**只有孤零零一行 `25.0.2`**，没有任何说明，极容易往别处排查。

仓库里没提交 `gradle-wrapper.jar`，命令行走已缓存的发行版：

```bash
export JAVA_HOME="/c/Users/cy-10/.jdks/jbr-21.0.11"
GRADLE="/c/Users/cy-10/.gradle/wrapper/dists/gradle-8.13-bin/5xuhj0ry160q40clulazy9h7d/gradle-8.13/bin/gradle.bat"

"$GRADLE" :app:compileDebugKotlin --console=plain   # 只验编译，最快
"$GRADLE" testDebugUnitTest                         # 跑全部单测
"$GRADLE" :app:assembleDebug                        # 出 APK
```

产物：`app/build/outputs/apk/debug/app-debug.apk`

> 哈希目录名会随 Gradle 版本变，对不上时 `ls ~/.gradle/wrapper/dists/` 重新找。

### 真机调试

设备通过 USB 连着，`adb` 在 `%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe`。

```bash
export MSYS_NO_PATHCONV=1
ADB="/c/Users/cy-10/AppData/Local/Android/Sdk/platform-tools/adb.exe"

"$ADB" install -r app/build/outputs/apk/debug/app-debug.apk   # -r 保留数据
"$ADB" shell am start -n com.myapp.debug/com.myapp.MainActivity
"$ADB" logcat -d -s AndroidRuntime:E          # 查崩溃
```

**在 Git Bash 里跑 adb 要加 `export MSYS_NO_PATHCONV=1`**，
否则 `/sdcard/xxx` 会被转成 Windows 路径。

> ⚠️ **绝对不要用 `adb uninstall` 或 `adb shell pm clear` 验证首启逻辑**
> --这会清掉用户全部数据（纪念日、待办、经期记录），且 `allowBackup="false"`
> 没有云端备份，丢了就是永久丢了。要验证首启向导，在一台没有用户数据的
> 测试机或模拟器上做，或者接受「老用户升级跳过」这条路径就够覆盖了。

无 UI 自动化框架时，可以用 `uiautomator dump` + `input tap` 做确定性的点击验证：

```bash
export MSYS_NO_PATHCONV=1
"$ADB" shell uiautomator dump /sdcard/ui.xml
"$ADB" exec-out cat /sdcard/ui.xml > ui.xml   # 从里面读 text 和 bounds，算出坐标再 tap
```

## 四、架构：加一个 feature 要动哪些文件

```
:app                    组装层。唯一知道「所有 feature 都存在」的地方
:core:common            时间工具、农历、Result、Dispatcher、跨模块契约、提醒、保活检测
:core:designsystem      色彩、字体、形状、动效令牌、通用组件
:core:database          Room 实例、全部实体与 DAO、迁移
:core:datastore         偏好设置（含 onboarding 标志）
:core:network           OkHttp 基建
:core:ui                导航契约 Route、首页卡片插槽 HomeCard
:feature:home           首页。只做卡片编排，不认识任何具体业务
:feature:todo           待办。**新增 feature 的参考实现，照抄它**
:feature:anniversary    纪念日
:feature:period         经期
:feature:note           笔记（M3）。FTS 全文搜索 + Photo Picker 插图
:feature:question       疑问收集箱（M4）。三态状态机 + 转为笔记
:feature:ledger         记账（M5 Phase 1）。手工记账 + 预算设置 + 首页进度卡片
:feature:settings       设置页 + 保活自检向导
```

### 依赖规则（不可违反）

1. `:feature:*` **之间永远不互相依赖**
2. `:feature:*` 只依赖 `:core:*`
3. 跨 feature 协作 → 在 `core/common/contract/CrossFeatureContracts.kt` 定义接口，
   提供方实现 + Hilt 绑定，调用方只注入接口

### 新增一个 feature 的完整步骤

**只需改 3 个已有文件**：`settings.gradle.kts`、`app/build.gradle.kts`、`AppNavHost.kt`。

1. `feature/xxx/build.gradle.kts`——只有 6 行：
   ```kotlin
   plugins { alias(libs.plugins.myapp.android.feature) }
   android { namespace = "com.myapp.feature.xxx" }
   ```
   约定插件已把 library + Compose + Hilt + 序列化 + 全部 core 依赖配好。
2. `settings.gradle.kts` 加 `include(":feature:xxx")`
3. 数据层：在 `:core:database` 的 `model/` `dao/` 加文件，
   `MyAppDatabase` 里加实体、**版本号 +1**、`Migrations.kt` 里补迁移并加进 `ALL_MIGRATIONS`

## 五、已经踩过的坑（别再踩一遍）

### 1. `letterSpacing` 绝不能用 `.em` ★ 这个坑崩掉过整个 App

`Type.kt` 里所有 `letterSpacing` / `fontSize` **一律用 `.sp`**，且 15 个排版样式必须全部显式定义。

原因：`OutlinedTextField` 的 label 聚焦时会在 `bodyLarge` 与 `bodySmall` 之间做 `TextStyle.lerp`，
而 lerp **无法在 Em 与 Sp 之间换算**，直接抛：

```
IllegalArgumentException: Cannot perform operation for Em and Sp
    at androidx.compose.ui.text.TextStyleKt.lerp
    at androidx.compose.material3.internal.TextFieldImplKt$CommonDecorationBox
```

后果是**每一个带 label 的输入框一进页面就崩**。编译期查不出，Preview 里也未必触发（要聚焦才插值）。
`TypographyTest` 已经把规则钉死，改 `Type.kt` 后务必跑 `:core:designsystem:testDebugUnitTest`。

### 2. Material 3 Expressive 需要**两个** opt-in 开关

`MotionScheme` 在 `material3 1.4.0-alpha13` 里已经有了，但需要
`ExperimentalMaterial3ExpressiveApi`，它和 `ExperimentalMaterial3Api` 是**两个独立开关**，
只开后者会报「This material3 API is experimental」编译错误。
已统一加在 `build-logic` 的 `configureKotlinAndroid` 里。

（顺带纠正一个常见误解：`1.4.0-alpha13` 在语义化版本里排在 `1.4.0` **之前**，alpha 是预发布。）

### 3. Kotlin 不对跨模块的 public 属性做智能转换

```kotlin
// ❌ 编译不过：dueAt 是 :core:database 里的 public 属性，
//    Kotlin 无法保证对方不是自定义 getter
isOverdue = dueAt != null && dueAt < now

// ✅ 先取到局部变量

isOverdue = due != null && due < now
```

### 4. `rememberSwipeToDismissBoxState` 的回调只捕获一次

`confirmValueChange` 在创建 state 时捕获闭包，直接传回调会永远拿到第一帧的旧引用。
必须用 `rememberUpdatedState` 包一层。参考 `TodoListScreen.kt` 的 `SwipeableTodoRow`。

另外 `confirmValueChange` **一律返回 `false`**：让数据流去驱动列表变化，卡片滑回原位。
返回 `true` 会让条目停在「已划走」状态，撤销恢复后位置就错了。

### 9. Room 2.7+ 不允许 `@TypeConverters` 与 `addTypeConverter()` 双重注册 ★ M3 上线即崩

`Converters` 类只要无依赖，`@TypeConverters(Converters::class)` 注解在 `MyAppDatabase` 上时 Room 会自动用 no-arg 构造实例化它。M3 阶段曾同时存在两套注册（注解 + `DatabaseModule` 里的 `.addTypeConverter(Converters())`），Room 2.7+ 在运行时直接抛：

```
IllegalArgumentException: Unexpected type converter com.myapp.core.database.Converters@...
Annotate TypeConverter class with @ProvidedTypeConverter annotation or remove this converter from the builder.
```

M3 上线时只跑了 `:core:database:assembleDebug` 编译通过就发了，没在真机上 `am start` 过，这条崩溃路径一直没被触发。M4 实施时第一次启动直接红屏，回溯排查才挖出来。

**最终修法**：只保留 `@TypeConverters(Converters::class)` 注解，删掉 `addTypeConverter(Converters())` 调用。`@ProvidedTypeConverter` 是给有依赖、需要 Hilt 注入的 Converter 用的，本项目 `Converters` 无依赖不需要。

教训：编译过 ≠ 跑得起来，Room 的 TypeConverter 校验是运行时检查；任何数据库改动必须真机 `am start` 一次，不能只看 `assembleDebug` 绿了就发。

### 10. Haze 1.5.0 + `Scaffold.bottomBar` 不兼容 ★ 底栏毛玻璃直接失效

`Scaffold` 的 `bottomBar` slot 把底栏和 content 摆成兄弟节点，两者 bounds 不交叠。
Haze 的工作原理是 `hazeSource` 贴在内容上采样像素、`hazeEffect` 贴在底栏上读采样结果--
**两者必须在同一父容器里、bounds 交叠**，兄弟节点采样不到。

**必须放弃 `Scaffold.bottomBar` slot，改用 `Box` 叠层**：`AppNavHost`（带 `hazeSource`）
在底层占满，`MyAppBottomBar`（带 `hazeEffect`）叠在上方 `Alignment.BottomCenter`。
这样底栏的 bounds 完全覆盖在内容之上，Haze 能正确采样。FAB 同理叠在最上层。
参考 `app/src/main/kotlin/com/myapp/ui/MyApp.kt`。

### 11. Haze 1.5.0 的 `HazeStyle` 必须传 `backgroundColor` ★ 运行时崩溃

`HazeStyle` 的 `backgroundColor` 参数在 1.5.0 里是必填的，不传会在运行时（第一次 draw 时）抛：

```
IllegalStateException: backgroundColor not specified. Please provide a color.
    at HazeEffectNode.drawEffectWithGraphicsLayer
```

编译期查不出。`HazeStyle` 还有**两个构造函数重载**，签名很像：
- `(backgroundColor, tints: List<HazeTint>, ...)`
- `(backgroundColor, tint: HazeTint?, ...)`

只传 `backgroundColor + blurRadius` 时会触发**重载歧义**，Kotlin 解析不出该用哪个。
显式传 `tints = emptyList()` 选 List 版本，或传 `tint = HazeTint(...)` 选单值版本。
本项目 `MyAppBottomBar` 用 `tint = HazeTint(surfaceColor.copy(alpha=0.6f))`，
`MultiActionFab` 的遮罩用 `tints = emptyList()`（纯遮罩不需要 tint）。

### 12. `toRoute<Route>()` 不支持 sealed interface Route ★ 导航匹配崩溃

`Route` 是 `@Serializable sealed interface`，子类是 `@Serializable data object`/`data class`。
`NavController.currentBackStackEntryAsState()` 拿到 entry 后，`entry.toRoute<Route>()`
内部用 kotlinx.serialization 多态解码，会抛：

```
SerializationException: Polymorphic value has not been read for class null
```

**必须改用字符串匹配**：

```kotlin
val currentRouteStr = currentEntry?.destination?.route
val topLevelDest = currentRouteStr?.let { str ->
    TopLevelDestination.entries.firstOrNull { dest -> str == dest.route::class.qualifiedName }
}
```

`destination.route` 是类型安全导航生成的全限定类名（如 `com.myapp.core.ui.navigation.Route$Home`），
和 `dest.route::class.qualifiedName` 比较即可。过渡瞬间 `currentRouteStr` 可能为 null，
判空兜底（默认隐藏底栏与 FAB）。

### 13. 跨页面传值不要用 `previousBackStackEntry.savedStateHandle` ★ M5 记账 Snackbar 静默失效

官方文档「返回结果给上一页」的套路是编辑页 `previousBackStackEntry?.savedStateHandle?.set(key, value)`、
列表页 VM 注入的 `SavedStateHandle` 用 `getStateFlow(key)` 观察。**M5 记账真机实测这个方案会静默失效**：

- 现象：`set()` 执行成功（日志确认 prev 就是 Route.Ledger 的 entry、handle 非空），
  但列表页 VM 的 `getStateFlow` 永远收不到值，`LaunchedEffect` 一直拿到 null，Snackbar 不弹。
- 根因：`previousBackStackEntry.savedStateHandle` 与列表 VM 注入的 `SavedStateHandle`
  **不是同一个对象**（日志打印两个 handle 的 identity 不同）。进程被系统回收后恢复导航状态、
  以及底部 tab 的 `saveState/restoreState` 组合，会让同一个 `Route.Ledger` 在栈上出现
  **多个 NavBackStackEntry 实例**，各自持有独立的 SavedStateHandle。值写进了「另一个」handle。
- 修法：改用**进程内单例 Channel 事件总线**（`feature/ledger/data/LedgerSaveEvents.kt`，
  `@Singleton` + `Channel<Long>(BUFFERED)` + `trySend`），与 entry 身份完全无关。
  编辑页经 `EntryPointAccessors.fromApplication` 拿单例 `publish(amount)`，
  列表 VM `init` 里 `collect`。`Channel.BUFFERED` 无订阅者也能缓冲，等列表回来再收。
  （`MutableSharedFlow(extraBufferCapacity)` 不行——零订阅者时 `trySend` 直接丢。）
- 全局 FAB 从首页进编辑页时 `previousBackStackEntry` 是 Home：按 `prev.destination.route`
  判断只对 `Route.Ledger` 发布，首页不需要 Snackbar，保持原预期行为。

### 14. `getLongExtra` 对 Integer extra 静默抛 ClassCastException ★ 深链首次测试失效

`intent.getLongExtra(key, -1L)` 在 Bundle 里存的是 `Integer`（如 `adb shell am start --ei`）
时**不返回 -1，而是抛 ClassCastException 被 Bundle 内部吞掉**，logcat 只留一行
`W Bundle: Key ... expected Long but value was a java.lang.Integer`，调用方拿到默认值 -1，
看起来像「extra 没传进来」。通知 PendingIntent 用 `putExtra(key, Long)` 不会触发，
但深链是外部输入边界（adb 测试、未来其他入口），读法要兼容两种类型：

```kotlin
val id = intent?.extras?.get(key).let { raw ->
    when (raw) {
        is Long -> raw
        is Int -> raw.toLong()
        else -> return
    }
}
```

### 15. 微信 App 在前台时转账/支付不发系统通知

微信在**前台**时支付成功只弹应用内消息，不投系统通知，NotificationListenerService
收不到（真机验证：用户连转两笔 0.01 / 6.66 均无落库）。**扫码支付**（扫个人/商家
收款码）成功后切后台，微信才发「微信支付凭证」通知。聊天转账基本不发通知，
不是自动记账能覆盖的路径，测试时用扫码支付。

### 16. 白名单按包名过滤拦不住微信聊天消息 ★ 未识别队列被污染

白名单只查包名，微信的普通聊天通知（标题=联系人名，正文=消息）也会进监听器，
解析失败全部进未识别队列，未识别屏被聊天记录刷屏。修法：`PaymentParser.isLikelyPayment`

不用裸「元」字。

### 17. Glance 1.1.1 的 API 和官方文档示例（多为 1.2+）差很多 ★ 小组件编译反复失败

glance-appwidget 1.1.1 里：**没有** `androidx.glance.unit.dp/sp`（要用 compose 的）、

### 18. `Intent(context, "com.xxx.MainActivity")` 是 ACTION 构造器 ★

Glance 小组件不能依赖 `:app`（PRD 4.7.1），按类名启动 MainActivity 时**不能用**

避免固定 requestCode 下 extras 互相覆盖。

### 19. Glance 的 `updateAll` 是 suspend 函数

BroadcastReceiver 的 `onReceive` 不是协程环境，直接调 `updateAll` 编译报错。
用 `goAsync()` + `CoroutineScope(Dispatchers.Main).launch` 包起来，finally 里
`pendingResult.finish()`（见 `WidgetAlarmReceiver`）。

### 20. `LocalDate.toEpochMilliAtStartOfDay()` 会把时分秒盖成 00:00 ★ 记账时间 bug

`AppTime` 里 `LocalDate.toEpochMilliAtStartOfDay()` 返回的是**当天零点**的 epochMilli，
用来「指定某一天」时是对的。但 `LedgerEditScreen` 的「今天 / 昨天」快选和 DatePicker 确认
都拿它去覆盖 `occurredAt`--`occurredAt` 默认值是 `AppTime.now()`（带当前时分秒），
被它一盖就成了当天 00:00，列表页 `toLocalTime().format("HH:mm")` 自然显示 `00:00`。

用户场景里这是必现 bug：默认就是今天，用户看到「今天」chip 没高亮（旧实现 `selected = false` 永远），
下意识点一下「确认是今天」，时间就被清零。

**修法**：换日期时**只换日期保留原时分秒**：

```kotlin
val occurredTime = with(AppTime) { occurredAt.toLocalDateTime().toLocalTime() }
val newMillis = with(AppTime) { targetDate.atTime(occurredTime).toEpochMilli() }
viewModel.updateOccurredAt(newMillis)
```

附带把 chip 的 `selected` 改成反映 `occurredAt.toLocalDate()` 与今天/昨天的比较，
让用户看见默认就是今天，不必再点。日期下方文本同时显示 `yyyy年M月d日 HH:mm`，
时间不对能立刻发现。

普适规律：**`toEpochMilliAtStartOfDay` 只适合「只关心日期不关心时刻」的列**
（纪念日、经期起止、预算周期边界）。涉及具体时刻的字段（`occurred_at`、`due_at`、
提醒触发时间）换日期时必须保留原 `LocalTime`，否则会把真实时刻静默清零。

## 八、保活自检向导（PRD 9.3）

ColorOS 后台管理是国产 ROM 里最激进的之一，会直接冻结未加白名单的应用，
导致提醒闹钟不响、通知监听失效、小组件不刷新。光有 AlarmManager 不够，
还需要引导用户关闭 OEM 层的后台限制。

### 实现在哪

- `core/common/keepalive/KeepAliveStatusChecker.kt`：检测电池白名单、通知权限、
  精确闹钟、首装判定（`firstInstallTime == lastUpdateTime`）。
- `feature/settings/keepalive/`：向导 UI（Screen + ViewModel + Item 模型）。
- `core/datastore/AppPreferences.kt`：`keepAliveChecked`（完成标志）+
  `keepAliveManualDone`（手动项勾选状态，`stringSetPreferencesKey` 持久化）。
- `app/MainActivity.kt`：splash 挂住读 onboarding 标志，决定 `initialRoute`。
  老用户升级（`!checked && !isFirstInstall()`）直接写 `true` 跳过向导。

### 检测项分四类

| 类别 | 项 | 处理 |
|---|---|---|
| AUTO（自动检测） | 电池优化白名单、通知权限、通知使用权 | API 检测 + 跳转系统设置 / 向导内请求权限 |
| READONLY（只读） | 精确闹钟 | `USE_EXACT_ALARM` 安装即授予，恒通过，只展示 |
| MANUAL（手动引导） | 自启动、后台活动、锁任务 | 无 API，路径文字 + 「我已设置」勾选框 + 「尝试直达」私有 Intent |

通知使用权在 M5 Phase 2 已升级为 AUTO 项：`isNotificationListenerEnabled()` 真实检测 +
「去开启」按钮跳 `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`（注意 action 常量带
`ACTION_` 前缀，拼成 `android.settings.NOTIFICATION_LISTENER_SETTINGS` 在 ColorOS 上
resolve 不到 Activity）。TEXTONLY 类别当前无用例，保留类别定义。

手动项勾选状态持久化到 DataStore--这些代表用户在系统设置里做的物理操作，
不会因为离开 App 就消失，复查时应保持已勾选。

### 首启时序（MainActivity）

1. `installSplashScreen()` 在 `super.onCreate()` **之前**
2. `super.onCreate()`（Hilt 在此填充 `@Inject lateinit`）
3. `appScope.launch` 读 `keepAliveChecked`；若 `!checked && !isFirstInstall()`
   写 `true`（老用户升级免打扰）
4. `splash.setKeepOnScreenCondition { keepAliveChecked == null }`
5. 非首启时请求 `POST_NOTIFICATIONS`；首启由向导内请求，避免同时弹两个框
6. `setContent` 的 `initialRoute` 由 `keepAliveChecked` 决定

### 首启返回拦截

首启时 `KeepAliveCheckScreen` 用 `BackHandler` 拦截系统返回键、隐藏 TopAppBar
返回箭头，防止用户跳过自检。`firstRun` 标志由 `AppNavHost` 根据
`startDestination == KeepAliveCheck` 传入。

### 完成导航

`onKeepAliveComplete` 做 `navigate(Home) + popUpTo(KeepAliveCheck){inclusive=true}`。
首启时栈为 `[KeepAliveCheck]`，popUpTo 后清空再 navigate；复查时栈为
`[Home, Settings, KeepAliveCheck]`，popUpTo 只清 KeepAliveCheck，
`launchSingleTop` 复用栈里已有的 Home。

### 项目内 dev 签名

`keystore/debug.keystore` 提交到仓库，`app/build.gradle.kts` 里 debug 和 release
统一用它签名。换电脑不再因 `~/.android/debug.keystore` 漂移导致无法覆盖安装。
`.gitignore` 里 `*.keystore` 忽略所有 keystore，但 `!debug.keystore` 放行这一个。

### 真机验证结果（realme GT Neo5 SE，2026-08-07）

- 首次安装（uninstall + install）-> 进向导，不进 Home ✅
- 系统返回键被拦截，不退出 App ✅
- 老用户升级（保留数据 install -r）-> 跳过向导进 Home ✅
- Home 齿轮 -> Settings -> 保活自检，复查路径可达 ✅
- 「尝试直达」跳 ColorOS 私有设置页，`resolveActivity` 兜底到应用详情页 ✅
- 手动项勾选 -> 离开向导 -> 重新进入，勾选状态保留 ✅
- 全部满足 -> 完成按钮启用 -> 点击进 Home ✅

## 九、各模块的关键设计决定（改代码前先看这里）

### `:core:common` — 农历

`LunarCalendar.kt`：自己实现的 1900~2100 查表换算，离线、零依赖。

**改那张 `LUNAR_INFO` 表之前先跑 `:core:common:testDebugUnitTest`。**
测试覆盖 40 个已知春节日期、13 个已知闰月，以及**全范围逐日往返校验**
（公历→农历→公历 必须严格相等，7 万余天）。

农历算错了 UI 照样显示一个像模像样的日期，肉眼根本看不出来，只能靠测试守。

两个必须容错的边界（不处理的话农历生日每隔几年就「消失」一次）：
- 当年没有对应闰月 → 退回同月份的平月
- 生日是三十而当月只有 29 天 → 落到当月最后一天

### `:core:database` — 日期怎么存

- 只有「日」语义的列（纪念日、经期起止）存 **epochDay**
- 有真实时刻的列（待办截止时间、各种 `*_at`）存 **epochMilli**

存毫秒表示纯日期会带上一个假的时刻，跨时区或夏令时时可能整体偏一天。

全局字段约定（为将来同步预留，现在就要有，后补代价极大）：
`uuid` / `created_at` / `updated_at`，需要软删除的表另加 `deleted_at`。
软删除还有个免费的好处：撤销删除是无损的。

### `:feature:todo` — 参考实现

新增 feature 照抄这个模块的目录结构：`data/` `list/` `edit/` `home/` `navigation/` `ui/`。

- 新建与编辑**共用一个页面**，`id = 0` 表示新建，不值得为此多一条路由
- 重复任务完成后生成**新条目**而不是改旧条目日期，这样「已完成」视图能看到完整历史
- 下一次从**原定截止时间**推算，不是完成时间——否则拖延几天会把整条链往后推
- 保存走**读改写**而非整体 REPLACE：`uuid` / `createdAt` / `done` 不属于表单，
  整体构造会把它们悄悄清掉（uuid 丢了将来同步就对不上）

### `:feature:anniversary`

- 重复类型存字符串不存枚举（`ONCE` / `YEARLY` / `CUMULATIVE`），加新类型不用做迁移
- 农历纪念日：`date` 列存**用户输入那天的公历日期**，农历月日在读取时换算。
  只需一个日期字段，用户切换公历/农历也不用重新输入
- 排序在**内存里**做不在 SQL：排序键要经过农历换算与「每年重复」推算，写不成 SQL 表达式。
  几十条的量级，代价可忽略
- 累计型的下一个里程碑：**整百天与周年取更近的那个**。
  只倒数整百天会漏掉「三周年」，只倒数周年会错过「在一起 1000 天」
- 置顶是**单选**，写入后统一收敛，避免出现两条置顶

### `:feature:period`

预测算法刻意保持简单（PRD 3.2 V1）：`下次开始 = 最近一次开始 + round(近 6 次周期均值)`。
不做加权、不做复杂建模——样本量本来就只有个位数，复杂模型只会放大噪声，
却让用户以为结果更准。

三处加固（都有测试覆盖，`PeriodPredictionTest` 9 条）：

1. **「进行中」设 15 天上限**。忘记点「结束」远比经期真的持续半个月常见，
   不设上限的话一次漏记会让首页永远显示「经期第 87 天」
2. **可靠性阈值比 PRD 下限严一档**：要求至少 3 个间隔才算 `reliable`。
   只有 1 个间隔时「平均」就等于那一次本身，把单次波动原样当预测，仍然该提示「样本不足」
3. 剔除 10~90 天之外的异常间隔（补录历史时录错年份的典型症状）

日历上**实际记录用实心色块、预测用虚线圈**——这两者绝不能长得像，
否则用户会把预测当成已发生的事实。

### `:feature:note` - M3 笔记

- **FTS 用 contentEntity 模式而不是 standalone 表**：`NoteFtsEntity` 通过 `@Fts4(contentEntity = NoteEntity::class)` 关联主表，Room 自动建外部内容表 + 触发器同步主表到 FTS。改 NoteEntity 不需要手动维护 FTS 同步逻辑。搜索时用 `rowid MATCH` JOIN 回主表，不是普通 SELECT
- **Photo Picker 不申请权限**：`PickVisualMedia` 是系统级 Activity，返回的 `content://` Uri 默认只对当前进程有效。要持久化（重启后还能读）必须 `contentResolver.takePersistableUriPermission(uri, FLAG_GRANT_READ_URI_PERMISSION)`，否则重启后 Uri 失效图片就丢。读取时 `BitmapFactory` 配 `inSampleSize` 防 OOM
- **MarkdownRenderer 是纯字符串解析器**：不依赖 Compose，输入 Markdown 文本输出 `AnnotatedString`，可以单测。`NoteMarkdownTest` 14 条覆盖各种语法边界（标题/粗体/斜体/列表/代码块/链接/分割线）
- **撤销删除走 Channel 而不是 StateFlow**：Snackbar 的显示是一次性事件，用 `Channel<UndoEvent>` + `receiveAsFlow()`，避免配置变更后重复弹
- **图片路径列表用 `` (U+0001) 分隔**：ASCII Unit Separator，文件名禁用字符，路径里不会出现，分隔安全。不用 JSON 序列化库，`:core:database` 没引入 kotlinx.serialization，为这一个字段拉依赖不划算

### `:feature:question` - M4 疑问收集箱

- **状态机存 TEXT 字符串不存枚举**：`QuestionStatus` 枚举有 `stored: String` 属性，存 `"OPEN"` / `"RESOLVED"` / `"ARCHIVED"`。加新状态不需要迁移（与 `AnniversaryEntity.repeatType` 同一套约定）。`from(s: String?)` 容错未知值回退到 `OPEN`
- **状态转换的不变式**（关键，Repository 用读改写强制）：
  - 进入 RESOLVED 时 `resolved_at = now`；离开 RESOLVED 时 `resolved_at = null`
  - `answer` 字段一旦写入**永不清空**——切回 OPEN 时 answer 保留（只是 UI 禁用），再切回 RESOLVED 不丢已写答案
  - `convertToNote` 后**状态保持 RESOLVED**，不自动归档（用户可能想多次转笔记或自己手动归档）
- **`canSave` 是唯一的硬约束**：content 非空 + RESOLVED 必须有 answer。其他状态转换全部允许，不强加业务规则
- **「转为笔记」走 NoteWriter 契约**：`QuestionRepository` 注入 `NoteWriter`（在 `:core:common` 定义，`:feature:note` 的 `NoteModule` 里 `@Binds` 到 `NoteRepository`）。`:feature:question` 不依赖 `:feature:note`，Hilt 在运行时自动解析。生成的笔记内容是 `# 疑问\n\n${content}\n\n# 解答\n\n${answer}`，标签追加 `"疑问"` 便于将来反查
- **首页随机卡片用 refresh trigger 模式**：`ORDER BY RANDOM() LIMIT 1` 只在表变更时重新 emit，点 refresh icon 必须通过 `_refresh.value++` + `flatMapLatest` 重订阅触发，否则点完没反应。从编辑页返回时也会自动刷新（用户可能已解决该疑问）
- **列表分组在内存里做**：Repository 一次查全部（不过滤 `deleted_at`），ViewModel 按 status 分组。一次查询比三条分支查询少 IO，量级小（预期不超过几百条）代价可忽略
- **FTS 全文搜索**（2026-08-12 补）：`MIGRATION_5_6` 加了 `question_fts`（FTS4 外部内容表，同 `note_fts`），`QuestionDao.search()` 改用 `MATCH`；`QuestionRepository.observe()` 用 `escapeFtsQuery` 转义。只索引 `content`，不含 `context`/`answer`/`tags`。**这条迁移比 note_fts 多一步**：question 表从 v4 就有历史数据，迁移里执行了 `INSERT INTO question_fts(question_fts) VALUES('rebuild')` 补建旧疑问的索引——note_fts 当年是和 note 表同一条迁移一起建的，没有这个历史数据问题，复制这个模式到别的表时留意

### `:feature:ledger` - M5 记账（Phase 1 手工记账）

- **金额一律存「分」Long**（PRD 4.2 严禁浮点）：`parseAmountCents` 把用户输入文本解析成分，
  容错「23.5」「23」「023」「.5」「23.」等写法（正则 `^\d*\.?\d{0,2}$` + BigDecimal 语义的整数运算），
  上限 1 亿元防溢出，非法输入返回 null。展示侧 `yuanWithSymbol()` 分转元文本。
  13 条单测钉死（`ParseAmountCentsTest`）
- **direction / status / source 存字符串不存枚举**（与 `AnniversaryEntity.repeatType` 同一套约定）。
  手工记账 `CONFIRMED` + `MANUAL`；`PENDING`/`AUTO` 留给 Phase 2 自动记账
- **`category_id` 不用 @ForeignKey**：与项目其他实体一致，引用完整性在 Repository 层保证
  （`LedgerWriter.recordExpense` 按分类名查 id，查不到落「未分类」保留项）
- **分类种子走 `RoomDatabase.Callback.onOpen` 而非 `onCreate`**：每次打开数据库检查
  `category` 表是否为空，空则从 `assets/categories.json` 灌 10 个内置分类。
  `onCreate` 只在 DB 文件首次创建时触发，老用户 v4->v5 升级时迁移建出空表、onCreate 不跑，
  会漏掉种子——`onOpen` 同时覆盖新装与升级两种场景（`DatabaseModule.kt`）
- **预算 V1 单行**：`budget` 表只有一行生效记录（`effective_to IS NULL`），改预算直接 upsert。
  预算周期 = 发薪日 `cycleStartDay` 起、到下月同日的前一天（`BudgetCycle.currentCycleRange`，
  9 条单测覆盖 8/10 边界、闰年 2/28、cycleStartDay=1 自然月等）
- **保存后 Snackbar 走单例 Channel 事件总线**（见第五节坑 #13）：编辑页 publish 金额 →
  列表 VM 查当前预算 + 周期内支出算「本期剩余」→ Snackbar。不用 savedStateHandle 跨页传值
- **首页卡片经 `@Binds @IntoSet` 注入**（PRD 4.7.2）：`LedgerHomeCard` 实现 `HomeCard`，
  无预算时显示「设置预算」按钮（点击跳 `Route.Ledger`），有预算时进度条按
  `>=90%` 危险 / `>=70%` 警示 / 其余正常分色。`LedgerCardViewModel` 用
  `flatMapLatest` 在「无预算 / 有预算」两种数据流之间切换
- **软删除**：`deleted_at` 置位，撤销恢复无损（与 todo/note 同套路）
- **列表分组在内存里做**：`groupByDate` 按本地日期分组、当日支出小计，倒序展示
- **日期选择保留时分秒**（2026-08-12 修 bug）：`TransactionDraft.occurredAt` 默认 `AppTime.now()`，
  编辑页「今天 / 昨天 / 选日期」三处快选**只换日期保留原时分秒**（`date.atTime(occurredTime).toEpochMilli()`），
  不能用 `toEpochMilliAtStartOfDay()`--那会把 `occurredAt` 盖成当天 00:00，列表页显示 `00:00`。
  「今天 / 昨天」chip 的 `selected` 反映 `occurredAt.toLocalDate()`，让用户看见默认就是今天不必再点。
  日期下方文本同时显示 `HH:mm` 便于核对。详见第五节坑 #20

### `:feature:ledger` - M5 Phase 2 自动记账（PRD 3.6.1）

- **数据流**：`PaymentNotificationListener`（NotificationListenerService，白名单 8 个支付 App
  包名）→ `PaymentParser` 规则引擎（纯函数 JVM 可测）→ `AutoCategorizer`（学习映射优先 →
  内置关键词兜底）→ `LedgerWriter.recordExpense`（PENDING + AUTO + rawText）→ 预算扣减 →
  `AutoLedgerNotifier` 通知栏「已记录 -￥X 商户，本期剩余 ￥Y」→ 点通知深链确认页
- **未识别队列 + 学习映射走 DataStore 不走新表**：`LedgerPrefsStore`（`ledger_preferences`）
  存未识别项 JSON 列表 + 商户→分类学习映射（上限 200 条，LinkedHashMap 淘汰旧条目）。
  不加数据库表 → 不需要 schema 迁移。未识别项绝不静默丢弃，UI 可查看/补录/忽略
- **深链走进程内单例 StateFlow**（`LedgerDeepLink`）：通知 PendingIntent 只带
  `com.myapp.extra.ledger_tx_id` extra 拉起 MainActivity，`onCreate`/`onNewIntent` 写入
  StateFlow，MyApp `LaunchedEffect` 收集后 `navigate(Route.LedgerDetail(id))` + consume。
  冷启动不丢目标（StateFlow 保留最新值）
- **PendingIntent 用字符串类名** `setClassName(context, "com.myapp.MainActivity")`：
  :feature:ledger 不依赖 :app，通知点击目标由 :app 提供（依赖方向单行道）
- **去重**：60s 窗口内同 rawText 的 PENDING 条目跳过，防微信重复投递
- **保存即确认**：PENDING 条目在编辑页保存 → `status=CONFIRMED` + 撤通知 +
  `categorizer.learn(merchant, category)`（下次同商户自动命中分类）
- **疑似支付预过滤**（`PaymentParser.isLikelyPayment`）：白名单只按包名过滤，
  微信大量普通聊天通知会混进来（真机踩坑），标题/正文含 ¥、`数字+元`、支付动词
  才处理，否则直接跳过不进未识别队列。5 条单测钉死
- **解析规则按渠道分**：WECHAT 支持「向 X 付款 ¥X 元」「已支付 ¥X 商户」（扫码支付凭证，
  2026-08-12 补）与「收款/到账 ¥X」三种句式（possessive quantifier `?+` 防金额组回溯吃掉
  商户组，与支付宝规则同写法）；ALIPAY「支付成功 ¥X 商户」；BANK「支出人民币 X 元」；
  通用兜底 ¥ / 元

### `:feature:ledger` - M5 Phase 3 规则编辑器（PRD 3.6.1）

- **存储走 DataStore JSON 不走 Room**：`RuleStore`（`rule_preferences` 独立文件，与
  `ledger_preferences` 分开）存 `customRules`（JSON `List<CustomRule>`）+ `disabledBuiltinIds`
  （JSON `Set<String>`）。规则量级小，加表要 v6 迁移不划算

  比 index 稳（不怕重排错位）
- **编辑页实时预览（关键交互）**：`remember(draft, previewText)` 直接调
  `PaymentParser.parse`，每改一个字段立刻展示 金额/方向/商户 或「未匹配」，保存前确认规则正确
- **未识别队列「存为规则」反向生成**：`UnrecognizedScreen` 每项加「存为规则」按钮 →

### `:feature:ledger` - M5 Phase 3 分类管理 UI（PRD 3.6）

- **三条不变式写在 `CategoryRepository` 的类注释里，改代码前先读**：保留项不可删/停用/改名；
  删除一律软删；改名要同步商户学习映射
- **为什么必须软删**：`TransactionDao` 的 JOIN 是 `INNER JOIN category ON c.id = t.category_id`，
  **不带** `c.deleted_at IS NULL`，所以软删后历史账目照常显示原分类名；真 DELETE 会让
  那些账目从列表里**整行消失**（JOIN 不上）。这是「停用而非删除」设计意图之外的第二道保险
- **改名同步学习映射**：`LedgerPrefsStore.merchantCategoryMap` 的 value 存的是分类**名**
  （`recordExpense` 契约按名查库），改名不同步的话自动记账按旧名查不到，静默落「未分类」。
  `renameLearnedCategory` 在 save 检测到名字变化时调用
- **排序走整表重排不走 `sortOrder ± 1`**：种子灌的是 1..10，用户删几个再加就会跳号，
  算术加减在跳号时会错位。`move()` 取当前顺序算出目标下标后把全表重写成 1..n。
  纯函数 `reorder()` 抽出来单测（`CategoryReorderTest` 10 条）
- **重名拦截返回 `CategorySaveResult.DuplicateName` 而不是抛异常**：分类名是 `LedgerWriter`
  的查找键，重名会让 `getByName` 命中哪条变成未定义。编辑页收到后**不退页**，弹 Snackbar
  让用户在原地改名，输入内容不丢
- **上移/下移用箭头不用拖拽排序**：分类量级最多几十条，箭头点击是确定性的、也好做 adb 验证；
  LazyColumn 拖拽排序要自己算偏移与滚动联动，投入产出不划算
- **入口有两个**：设置页「分类管理」+ 记账页 TopBar 分类图标（改分类多半是记账时才想起来的）
- **顺手修的 bug**：`LedgerPrefsStore.learnMerchantCategory` 里 `prefs[KEY] ?: return@edit`
  在**第一次**学习时（key 还不存在）直接返回，导致商户→分类学习映射永远建不起来、
  整个学习功能静默失效。改成缺 key 时按空 map 起步
- **真机验证（2026-08-11，realme GT Neo5 SE）**：列表渲染含真实笔数（餐饮 6 笔 / 交通 10 笔）；
  下移 → 顺序交换、上移回位；首行上移无效果（边界）；新建分类（名称 + fitness 图标 +
  松绿）保存后落到列表末尾；重名保存被拦 + Snackbar「已有同名分类，换一个名字」且不退页；
  左滑删除 + 撤销恢复（**撤销要在 4s 内点**，adb 验证时中间夹 dump 会超时，
  device 端 `input swipe; sleep 1; input tap` 一条命令跑才稳）；保留项「未分类」开关
  置灰不可切；删除的分类立刻从「记一笔」选择器消失。**真机上留了 3 条软删的测试分类
  （Gym / Tmp / Tw），deleted_at 已置位，UI 上看不见，不影响任何逻辑**

### `:feature:ledger` - M5 Phase 3 预算视图（PRD 3.6.2）

- **派生指标全在 `data/BudgetInsights.kt`，是纯函数，`BudgetInsightsTest` 12 条钉死**。
  这些数字用户拿来做花钱决策：显示「日均还能花 ￥120」而实际只剩 ￥30 会直接害人超支，
  比不显示更糟，所以边界一条条测
- **周期天数按日历天算不按毫秒差**：跨夏令时毫秒差会少一小时，整除后可能少一天，
  「还剩几天」必须和日历一致
- **今天算在剩余天数里**（`remainingDays` 最小是 1）：用户今天要花钱，今天的额度还能用。
  按 `total - elapsed` 算会在周期最后一天给出 0，日均可用直接除零
- **匀速理想值按已过天数算不按剩余天数**：周期第 1 天就该允许花掉 1/30，
  用剩余天数算会把周期初的所有人都判成「花得偏快」
- **节奏容差 5%**：差距在预算的 ±5% 内算「节奏正常」。不留容差的话每天都在
  「偏快/偏省」之间跳，警示就失去意义了
- **超支时日均可用返回 0 而不是负数**：「日均还能花 -￥50」没有指导意义，
  超支这件事由节奏卡片单独说
- **`flatMapLatest` 而不是 combine**：预算（含发薪日）变了以后，下游的区间查询要跟着换。
  直接 combine 会一直用第一次算出来的区间——首页卡片 `LedgerCardViewModel` 踩过同样的坑
- **分类汇总的 JOIN 不带 `c.deleted_at IS NULL`**：分类被软删后历史账目仍要统计进来，
  否则删一个分类会让「本期支出去向」的明细和总额对不上（与列表页 JOIN 同口径）
- **`BudgetDialog` 提到 `ui/BudgetDialog.kt` 共用**：记账列表页的齿轮改成跳预算页，
  对话框由预算页持有。两处各写一份的话，改校验规则（如发薪日上限 28）必然漏改一处
- **入口**：记账页 TopBar 齿轮 → 预算页；首页记账卡片没预算时的「设置预算」也直达预算页
- **真机验证（2026-08-12，realme GT Neo5 SE）**：预算 ￥11000 / 已花 ￥5.00 →
  剩余 ￥10995、日均 ￥379.13（10995/29）、匀速理想 ￥1064.51（11000×3/31）、
  「周期第 3/31 天」、分类排行「交通 ￥5.00 · 1 笔 · 占本期 100%」，
  与手算逐项一致；编辑对话框预填当前值（10 / 11000），取消后回到预算页无崩溃

### `:feature:ledger` - M5 Phase 3 统计图表（PRD 3.6.3）

- **月度趋势按自然月不按预算周期**：`data/StatisticsInsights.kt` 的派生逻辑独立于 `BudgetCycle`。
  统计页回答的是「每个月大概花多少」，换发薪日会挪动预算周期的边界，但日历月份不该跟着变——

- **补零对齐（`StatisticsInsights.fillGaps`）**：DAO 分组结果里没有支出的月份不会出现，
  直接渲染会让趋势图断档，用户会当成 bug（"这个月数据是不是丢了"）。单独抽成纯函数用
  `StatisticsInsightsTest` 钉死
- **趋势图与分类明细两条独立订阅**：趋势固定查最近 6 个月，不随选中月变化；
  分类占比单独用 `selectedMonth` 驱动（`flatMapLatest`）。硬凑一个 combine 源会让「切月份」
  把趋势图也重新查一遍，没必要
- **柱状图不用 Canvas**：固定高度容器 + `Dp * Float` 算出实际高度的 Box，同 `ProgressTrack` 一个思路，
  没引入图表库
- **未来月份不可选**：`canSelectNextMonth` 卡在当月，没发生的支出没有意义
- **`CategoryExpenseRow`/`ProgressTrack`/`progressColor` 从预算视图抽到 `ui/CategoryExpenseRow.kt` 共用**：
  两边都是「一个区间内按分类汇总的支出」，只是区间口径不同（预算周期 vs 自然月），没必要各写一份。
  抽出后行文案从「占本期 X%」改成更通用的「占比 X%」
- **入口**：记账页 TopBar 新增统计图标（在分类管理、预算之前）
- **真机验证（2026-08-12）**：8 月柱子（唯一有数据的月份）高亮橙色，切到 7 月正确显示空态
  「这个月还没有支出记录」，连续点两次「下个月」箭头在当月（8 月）停住不越界，
